# 工作稿保存性能评估（#186）

本轮授权为测量与归因，不重构保存器，不改变 5 秒自动保存间隔。结果分别记录浏览器输入、请求前处理和真实隔离 SQL 保存，不能把其中一项冒充端到端生产延迟。

## 数据与源码

- 保存器使用确定性 5／40／100 状态夹具，每状态 6 个 Tc 点及重复来源，固定随机性为零；原始规模分别约 0.58／4.66／11.65 MB。每种保存模式运行 8 次。
- 固定完整宿主浏览器使用 40 状态、240 点、3862 条摘要、2700 个字段；在生产构建中顺序测量。浏览器 API 是立即响应隔离替身，不调用真实模型或修改业务数据。
- 基线为 f3bcd280 的保存器和生产页面；本轮保存器及后端源码 SHA、夹具 SHA 见 results/。浏览器当前构建包含共享工作区已有界面改动，不能把差异全部归到单一 Issue。
- 后端使用本次专建并迁移的本机隔离 MySQL；不写业务库。只发送一个字段的变化列表，数据库仍需读取和保存权威工作稿。

## 请求前处理

100 状态、600 点、约 11.65 MB 的平均毫秒：

| 模式 | 基线 | 本轮 |
| --- | ---: | ---: |
| 单字段保存 | 69.8 | 71.8 |
| 整稿保存 | 49.4 | 55.1 |
| 自动保存处理 | 49.5 | 54.5 |
| 保存器无变化分支 | 35.7 | 41.3 |

复制、比较、单字段投影和序列化均有成本；单字段保存仍涉及整稿复制，不能因为写请求小就认定前处理便宜。自动保存测其处理过程，5 秒等待不算 CPU 时间。无变化保存器分支仍会复制；真实页面在没有变化时可直接返回，不能把辅助函数分支耗时说成页面必然发送请求。

## 输入、网络和后端

生产构建单轮浏览器输入：基线绘制延迟均值约 37.8 ms，本轮约 40.9 ms；两轮均为零长任务、零新增整表扫描、输入期间零 API 请求，等待自动保存后均只有一次元信息读取和一次局部 PATCH。DOM 节点为 25036／25898，字段数相同。样本有限，这些数值不用于宣称统计显著改善或把差异归因到保存器。

本机隔离 MySQL 的 40 状态单字段保存平均约 328.5 ms，其中 SQL 驱动及本机传输约 92.2 ms；其余包括 Python、JSON、缓存发布和事务提交，不能称为纯 CPU。浏览器真实 HTTP 网络未测，不能把替身的零等待解释成生产网络耗时。

## 结论

保存前整稿处理确有可复查开销，值得另行提出有边界的优化方案；本轮未授权实施该优化。输入期间没有保存请求，保存器入口也由显式／定时保存触发，因此不能仅凭保存时的 70 ms 把它定为输入卡顿原因。后续方案需要分别约束前端复制比较和后端大 JSON 读写，并保持 #185 的局部覆盖、稳定身份、失败恢复和零无意义请求。

- workdraft-input-benchmark.mjs：运行完整宿主；显式指定 FORM_CONTRACT_DRAFT、FORM_CONTRACT_SUMMARY、FRONTEND_URL、PLAYWRIGHT_MODULE 和 CHROMIUM_PATH。
- workdraft-backend-benchmark.py：仅接受 SCWIKI_PERF_DATABASE_URL 中本机且名称以 scwiki_issue139_test_six_ 开头的隔离库；WORKDRAFT_PERF_DRAFT 指向夹具，WORKDRAFT_BACKEND_OUTPUT 指定输出。
- results/：保存器前后、完整宿主前后及后端分层结果。源码 SHA 变化后须重新测量，不能把旧报告当作新代码的性能结论。
