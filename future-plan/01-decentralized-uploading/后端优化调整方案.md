# 01 去中心化超导数据上传：后端优化调整方案

## 核心目标

后端规划将晶体结构数据合并进超导参数记录数据，使每条超导记录同时表达压强、晶体结构、Tc 和配套超导参数。这样可以为后续 GNN 特征编码、数据集划分和模型训练提供稳定的数据单元。

## 目标记录形态

单条目标记录应包含：

- 化学式
- 元素组成
- 压强
- 晶体结构文本或结构引用
- 空间群
- 晶胞参数
- 临界温度 Tc
- lambda
- omega_log
- N(Ef)
- 计算方法和计算软件
- DOI
- 数据来源类型
- 审核状态

## 数据合并策略

当前代码中 `superconductor_records` 保存超导参数记录，`superconductors_structures` 单独保存晶体结构正文。两张表之间没有真正的外键绑定关系；现在所谓“按记录找结构”，本质是后端运行时用 `superconductor_id + pressure_gpa + space_group_symbol + space_group_number` 去查询最合适的结构。

未来最终版建议直接合并为一张以 `superconductor_records` 为核心的数据表，不再让“超导参数”和“晶体结构正文”分散在两张业务表中。也就是说，每条超导参数记录本身就保存或直接拥有对应的晶体结构字段。

### 最终表结构方向

在 `superconductor_records` 中补齐结构相关字段：

- `structure_format`：结构格式，例如 CIF 或 POSCAR。
- `structure_text`：晶体结构原文。
- `structure_fingerprint`：可选的文件级辅助指纹，只用于追踪完全相同的上传文件，不能作为判断晶体结构是否相同的依据。结构是否相同必须交给 StructurePrototypeAnalysisPackage 判断。
- `atom_count`：原子数量。
- `structure_elements_list`：结构中解析出的元素列表。
- `cell_parameters`：晶胞参数。
- `volume`：晶胞体积。
- `review_status`：整条超导记录的统一审核状态，同时覆盖参数数据和晶体结构数据。
- `structure_source_type`：结构来源类型。
- `structure_source_label`：结构来源说明。

### 结构来源字段定义

结构来源必须保留。原因是同一个材料、同一个压强下，晶体结构可能来自论文补充材料、用户上传、外部数据库、计算输出或管理员人工整理。如果不记录来源，后续审核、纠错、数据集划分和模型结果解释都会失去追溯依据。

建议把来源拆成两个层次：

- `structure_source_type`：结构来源类别，使用固定枚举，方便后端筛选和统计。
- `structure_source_label`：结构来源说明，使用人工可读文本，说明这份结构具体来自哪里。

#### `structure_source_type` 建议取值

| 取值 | 含义 | 使用场景 |
| --- | --- | --- |
| `paper_supplementary` | 论文补充材料 | 结构来自论文 supplementary information、supporting information 或附件 CIF/POSCAR。 |
| `paper_table_or_text` | 论文正文或表格整理 | 结构参数来自论文正文、表格或附录，需要管理员人工整理成 CIF/POSCAR。 |
| `user_upload` | 用户上传 | 注册用户在平台上传结构文件，但来源需要进一步审核确认。 |
| `admin_curated` | 管理员整理 | 管理员根据可信材料人工校正、补齐或整理结构。 |
| `external_database` | 外部数据库导入 | 结构来自 Materials Project、ICSD、OQMD、COD 等外部数据库。 |
| `calculation_output` | 计算输出 | 结构来自 VASP、Quantum ESPRESSO、ABINIT 等计算软件输出。 |
| `structure_prediction` | 结构预测结果 | 结构来自 USPEX、CALYPSO、AIRSS、PyXtal 或其他结构搜索 / 预测流程。 |
| `dataset_import` | 数据集批量导入 | 结构来自已有数据集、历史 CSV/JSON 或项目早期批量导入文件。 |
| `legacy_migration` | 旧表合并来源 | 结构来自旧 `superconductors_structures` 表，在合并两表时迁入。 |
| `unknown` | 来源未知 | 暂时无法确认来源，只能作为待补充或待审核数据。 |

#### `structure_source_label` 写法

`structure_source_label` 是给合作者、审核者和后续维护者看的说明。它应该尽量写清楚：

- DOI 或文献编号。
- 原始文件名。
- 外部数据库名称和材料 ID。
- 结构对应的化学式、压强和空间群。
- 上传者或整理者说明。
- 是否来自补充材料、计算输出或人工整理。

示例：

- `来自 DOI: 10.xxxx/xxxx 的 supplementary CIF，LaH10 200 GPa Fm-3m`
- `用户上传 POSCAR，声称来自 VASP 结构优化结果，待管理员审核`
- `管理员根据论文 Table S2 手动整理，原文给出晶胞参数和原子坐标`
- `旧 superconductors_structures 表迁入，原 structure_id=123`
- `USPEX 结构搜索输出，候选结构 rank=1，source_label=run_2026_07_01`

#### 是否需要继续拆字段

`structure_source_label` 可以作为第一阶段落地字段。如果后续需要更强的检索和审计能力，可以进一步拆成结构化字段：

- `structure_source_doi`：结构对应文献 DOI。
- `structure_source_url`：补充材料、外部数据库或下载链接。
- `structure_source_file_name`：原始结构文件名。
- `structure_source_database`：外部数据库名称。
- `structure_source_external_id`：外部数据库材料 ID。
- `structure_source_note`：管理员备注。

第一阶段不必一次性拆太多字段。建议先保留 `structure_source_type + structure_source_label`，确保每条结构至少能被人工追溯；等数据量变大后，再把 DOI、URL、数据库 ID 等高频字段拆出来。

这样一条记录可以直接表达：

- 某个材料体系
- 某个压强
- 某个晶体结构
- 某个 Tc
- 一组超导参数
- 对应文献来源

### 统一审核状态设计

最终合并两张表后，不再保留单独的 `structure_review_status`。`superconductor_records.review_status` 作为整条记录的唯一审核状态，直接表达“参数数据 + 晶体结构数据”整体是否可进入公开数据集。

统一状态规则如下：

| 参数审核结果 | 结构审核结果 | `review_status` |
| --- | --- | --- |
| 通过 | 通过 | `approved` |
| 待审核 | 通过 / 待审核 | `pending` |
| 通过 | 待审核 | `pending` |
| 拒绝 | 任意状态 | `rejected` |
| 任意状态 | 拒绝 | `rejected` |

该规则的含义是：

- 只有参数字段和结构字段都通过审核时，整条记录才是 `approved`。
- 只要参数或结构仍在审核中，整条记录就是 `pending`。
- 只要参数或结构任一关键部分被拒绝，整条记录就是 `rejected`。

这种设计让前端、后端和 API 都只读取一个审核字段，降低合作者理解成本。需要注意的是，虽然最终只存一个 `review_status`，后台审核时仍应在审核备注中写清楚是参数问题、结构问题，还是二者都有问题。

### 不需要迁移映射

本方案不设计迁移映射，也不设计长期共存的“结构表到记录表绑定关系”。最终目标就是直接合并 `superconductor_records` 和 `superconductors_structures` 两张表，把晶体结构字段直接并入超导参数记录表。

合并后的业务理解应当非常明确：一条 `superconductor_records` 就是一条完整的超导数据样本，包含材料、压强、晶体结构、Tc、超导参数和文献来源。后续所有上传、清洗、检索、导出和 GNN 建模都围绕这一张主表展开。

旧 `superconductors_structures` 表在最终版中不再作为业务表继续存在。若当前开发数据质量不足，可以直接清理或重新导入；若有少量可用旧数据，也只作为临时参考来源处理，不把“迁移映射”作为正式方案的一部分。

### 直接合并的落地步骤

1. 在 `superconductor_records` 中新增结构字段。
2. 从 `superconductors_structures` 中读取已审核结构。
3. 按 `superconductor_id + pressure_gpa + space_group_symbol + space_group_number` 找到对应超导参数记录。
4. 如果一条结构只匹配一条参数记录，直接把结构字段写入该记录。
5. 如果多条结构匹配同一条参数记录，必须在同一压强分组内调用 StructurePrototypeAnalysisPackage 判断是否为相同结构。
6. 如果 StructurePrototypeAnalysisPackage 判断为相同结构，只保留一条主记录，并把其他来源作为重复来源说明。
7. 如果 StructurePrototypeAnalysisPackage 判断为不同结构，则拆成多条 `superconductor_records`，每条记录对应一个明确结构。
8. 如果仍然无法稳定判断，不自动覆盖，标记为冲突数据，交给人工确认。
9. 合并完成并验证后，删除或归档 `superconductors_structures` 表。

### 关于“多个结构版本”

“多个结构版本”指的是：同一个材料、同一个压强、同一个空间群下，可能有人上传过多份 CIF/POSCAR。它们可能来自不同论文、不同用户、不同修订时间，或者只是重复上传。

最终合并为一张表时，不建议在主记录中保留多个结构版本。主记录只保留一个当前采用的结构。其他版本有两种处理方式：

- 如果只是重复结构，必须在同一压强下调用 StructurePrototypeAnalysisPackage 判断是否相同，不能用 hash 判断。
- 如果确实是不同结构，且都有价值，应拆成多条 `superconductor_records`，每条记录对应一个明确结构和来源，而不是在同一条记录里塞多个版本。

这样更适合后续 GNN 建模：一条样本只对应一个结构图、一个压强和一个 Tc 标签，不会出现一条训练样本对应多个结构输入的歧义。

### 结构相同判断方式

不能用 `structure_hash`、坐标四舍五入或简单文本规范化判断两个晶体结构是否相同。原因是 CIF/POSCAR 的文本格式、原子顺序、小数位和坐标微小误差都会影响文本结果，但这些差异不一定代表晶体结构真的不同。

最终方案指定使用 `chuanxun/StructurePrototypeAnalysisPackage` 判断结构是否相同。该工具面向结构原型分析，可进行对称性分析和结构相似性比较，适合用于判断同一条件下上传的多个结构是否属于同一种结构。

依赖仓库地址：

`https://github.com/chuanxun/StructurePrototypeAnalysisPackage.git`

后续落地时，需要先评估该仓库的安装方式、输入结构格式、批量比较接口、运行耗时和异常处理方式，再决定是直接作为 Python 依赖引入，还是封装成独立的结构比较服务。

判断边界必须固定为：

- 同一材料、同一压强下：调用 StructurePrototypeAnalysisPackage 判断两个结构是否相同。
- 同一材料、不同压强下：不调用 StructurePrototypeAnalysisPackage 做合并判断，天然视为不同结构样本。

不同压强下即使 StructurePrototypeAnalysisPackage 可能认为空间排布属于同一原型，也不应该合并。原因是压强会改变晶胞参数、键长和 Tc，压强本身也是后续建模的重要条件。对 GNN 建模来说，不同压强下的结构应该保留为不同样本。

### 推荐判重流程

1. 接收用户上传的 CIF/POSCAR。
2. 解析结构，确认结构文件有效。
3. 按 `superconductor_id + pressure_gpa` 获取同一材料、同一压强下已有结构。
4. 对同一压强组内的候选结构调用 StructurePrototypeAnalysisPackage。
5. 如果判断为相同结构，不新增重复样本，只记录新的来源或提示重复上传。
6. 如果判断为不同结构，新增一条 `superconductor_records`，让每条记录对应一个明确结构。
7. 如果工具无法给出稳定判断，进入人工确认，不自动合并。

### `structure_fingerprint` 的定位

可以保留 `structure_fingerprint`，但只能作为工程辅助字段：

- 判断是否上传了完全相同的原始文件。
- 帮助排查重复提交。
- 辅助缓存 StructurePrototypeAnalysisPackage 的比较结果。

它不能作为结构是否相同的业务判断依据。

### 合理性判断

直接合并两个表是合理的，前提是项目目标更偏向“结构化数据集”和“机器学习建模”，而不是维护一个多版本晶体结构仓库。对 SC-Wiki 当前需求来说，压强、结构、Tc 和超导参数应该天然属于同一条建模样本，因此合并能降低理解成本和查询复杂度。

主要复杂度不在表结构本身，而在旧数据处理：

- 有结构但没有对应超导参数记录。
- 有参数记录但没有结构。
- 同一条件下有多个结构候选。
- 结构文本解析失败。
- DOI 或来源缺失，无法判断哪份结构更可信。

如果可以接受清理或重新导入旧数据，直接合并会比长期维护两张表更简单。

## 数据清洗要求

清洗流程需要处理：

- 压强单位统一为 GPa。
- Tc 单位统一为 K。
- 化学式规范化。
- CIF/POSCAR 结构格式校验。
- 同一压强下重复结构去重。
- 同一材料不同压强结构分开保留。
- 缺失 DOI 或来源的数据进入待补充状态。

## 数据集划分要求

为了避免机器学习评估泄漏，数据集划分不能简单随机拆分记录。建议按以下边界划分：

- 同一化学式的近似结构尽量不同时进入训练集和测试集。
- 同一 DOI 下的数据尽量保持在同一数据集分区。
- 同一压强扫描序列需要整体评估是否拆分。
- 明确标记实验数据和理论数据。

## GNN 特征编码前置数据要求

GNN 模型需要结构图作为输入，因此后端必须准备：

- 可解析的晶体结构文本。
- 元素节点特征。
- 原子坐标和晶胞参数。
- 压强标签。
- Tc 标签。
- 超导参数描述符。
- 结构来源和审核状态。

## 验收标准

- 每条目标记录能同时追溯压强、晶体结构、Tc 和超导参数。
- 重复结构可以被识别。
- 冲突结构不会静默覆盖。
- 可导出用于 GNN 建模的清洗数据集。
