# Docker 镜像积累与本地、服务器开发部署

## 1. 结论与核验范围

**日常写代码使用热重载，发布和部署验收时才构建镜像；数据库独立持久化，调试环境使用独立数据副本。** 当前本地数据库可以继续使用，不需要为了减少镜像而迁回 Docker。

Docker 普通启动不会天然生成大量新镜像。当前 `docker/compose.yaml` 只有 `image:`，没有 `build:`；它使用已有镜像或按拉取策略下载镜像，不负责从本地源码构建。“每次启动镜像变多”需要结合实际命令及前后占用判断，可能是重建、更新镜像、构建缓存或数据卷被混在一起观察。

核验时间：2026-09-21。源码依据为当日 `mayuan` 分支的已跟踪文件；并行开发中的未提交文件不作为已实现能力。本文完成只读检查和文档分析，没有构建镜像、启停服务、清理资源、修改数据库或验证服务器部署。后文“建议”均不表示已实施。

## 2. 当前到底占用了什么

### 2.1 四种对象不能混为一谈

| 对象 | 可以怎样理解 | 什么操作会增加它 | 是否保存业务数据 |
| --- | --- | --- | --- |
| 镜像 | 一份应用及运行环境的模板 | 构建新版本、拉取不同版本 | 正常设计下不保存运行中数据库 |
| 容器 | 从镜像启动的一个服务实例 | 创建或重建服务实例 | 未挂载出去的文件留在容器可写层 |
| 构建缓存 | 下次构建可以复用的中间结果 | 执行构建 | 通常不是业务数据库，但清除会增加构建时间 |
| 数据卷、宿主机挂载目录 | 独立于容器的长期存储 | 初始化数据库、上传文件、创建新环境 | 是，需要识别内容并备份 |

多个标签可以指向同一个镜像 ID，多个镜像也可以共享底层文件层。不能把镜像列表每一行的 `SIZE` 相加，当成实际独占空间。

## 3. 项目当前如何构建和运行

### 3.1 Compose 部署

当前 Compose 定义 12 个服务，但仅使用 8 类镜像：

| 镜像 | 使用服务 |
| --- | --- |
| `mayuanmark/scwiki-frontend:mayuan` | `frontend` |
| `mayuanmark/scwiki-goserver:mayuan` | `goserver` |
| `mayuanmark/scwiki-python:mayuan` | `python`、`migrate`、`worker`、`news-worker`、`news-scheduler` |
| `mysql:8.4` | `mysql` |
| `redis:7-alpine` | `redis` |
| `neo4j:5` | `neo4j` |
| `lfoppiano/grobid:0.8.1` | `grobid` |
| `qdrant/qdrant:latest` | `qdrant` |

Python API、迁移和后台任务已经共用镜像，不需要为每个进程构建一份。`migrate` 是执行后退出的迁移任务，也不能要求 12 个服务一直全部处于运行状态。

工作流 `.github/workflows/docker-images.yml` 在推送 `mayuan`、推送 `v*` 标签或手动触发时构建三个应用镜像。它发布分支、`sha-*` 或版本标签，并使用 GitHub Actions 构建缓存。仓库里多出远端版本，不代表本机自动下载了所有版本。

`mayuan` 和 `latest` 等标签指向的内容可以变化。反复拉取更新会留下旧镜像或旧层；同样，重建后让同一标签指向新镜像，也不会自动删除所有旧内容。

### 3.2 本地开发

首次准备使用 `make deploy`，日常入口是 `make start`、`make stop`、`make status` 和 `make logs S=python`。应用、数据库和 GROBID 全部使用宿主机进程，本地安装与启停不需要 Docker；官方依赖下载仍需要可用网络。

- 前端使用 Vite 热更新；Python API 使用 Uvicorn 自动重载；Go 由文件监听触发重编译。
- 上传 Worker 使用 `watchfiles` 监听 Python 代码；资讯 Worker 和 Scheduler 没有同样的重载包装，修改后需要重启相应进程。
- 数据在仓库 `.data/`；二进制、PID 和日志等在 `.local/`。它们不会因为重建应用镜像而自动迁移到 Docker。
- `scripts/dev.sh` 启动 Python 前会运行数据库迁移，Compose 也有 `migrate` 服务。**启动开发环境并非只读操作，必须先确认数据库连接属于开发环境。**

本地开发说明见[现有使用文档](../../local-dev.md)。`make migrate` 当前指从旧 Docker 数据源迁移到本地，不能把它当成“把本地数据库发布到服务器”的通用命令。

## 4. 如何减少镜像和缓存持续增长

### 4.1 按操作目的选择命令

以下 Compose 示例以仓库根目录为工作目录，前提是配置和数据已经准备好。它们是使用说明，本次未执行；完整启动可能执行数据库迁移。

| 目的 | 方法 | 对镜像的影响 |
| --- | --- | --- |
| 日常修改代码 | 使用当前本地热重载环境 | 不为每次代码修改构建应用镜像 |
| 恢复已有且已停止的容器 | `docker compose -f "docker/compose.yaml" start` | 使用原有容器与镜像，不应用新配置 |
| 按现有配置启动服务 | `docker compose -f "docker/compose.yaml" up -d` | 当前文件不含构建定义；缺少镜像等情况仍可能下载 |
| 明确只用本机已有镜像启动 | `docker compose -f "docker/compose.yaml" up -d --no-build --pull never` | 禁止构建和拉取；缺镜像就失败 |
| 让既有应用进程重启 | `docker compose -f "docker/compose.yaml" restart frontend goserver python worker news-worker news-scheduler` | 不构建，也不会应用新镜像或新的容器环境变量 |
| 发布代码新版本 | 构建或拉取指定版本，再用 `up -d` 创建对应容器 | 有意保留新版本，随后按策略处理旧版本 |

单纯执行 `restart` 不会把新源码放进当前镜像。当前 Compose 没有 `build:`，加 `--build` 也不能代替缺失的源码构建定义；需要显式使用 Dockerfile 或使用已发布镜像。

例如仅验证前端源码的部署构建，可在单独验收环境使用：

```bash
docker build -f "docker/frontend.Dockerfile" -t mayuanmark/scwiki-frontend:mayuan "."
docker compose -f "docker/compose.yaml" up -d --no-deps --pull never frontend
```

这个例子会覆盖本机该标签的指向，只适合明确使用本机构建的验收环境；`--no-deps` 要求依赖已就绪。它不适合作为涉及数据库迁移的后端发布流程。修改 Python 镜像后，API 和相关 Worker 应使用同一版本，迁移与重建顺序需单独核验。

### 4.2 缓存应复用，而不是每次清空

当前前端和 Go Dockerfile 已采用多阶段构建：编译在构建阶段完成，只把运行所需产物放入最终镜像。三个 Dockerfile 都把依赖安装放在业务源码复制之前，因此单纯修改代码可以复用依赖层。

建议保留这套顺序，不把 `--no-cache` 作为日常默认选项。真正影响空间的是保留了多少版本和缓存，而非是否使用 Docker。

当前还有两处可以后续优化，但本次没有修改：

- `.dockerignore` 未明确排除仓库根 `.data/` 和 `.local/`。建议补充，缩小构建上下文并避免未来误复制；当前 Dockerfile 是定向 `COPY`，不能据此声称数据库已经进入镜像。
- Python Dockerfile 在一个 `RUN` 层安装编译工具，后续层才删除。后面的删除不会抹掉前一层体积；可评估合并安装与清理，或采用单独编译依赖的阶段。是否值得调整，应由镜像层大小和构建验证决定。

### 4.3 发布版本与保留策略

建议发布时记录三个应用镜像各自的 digest（镜像内容标识），或固定同一提交对应的 `sha-*` 标签。现有工作流已经生成提交标签，但当前 Compose 仍使用可变化的 `mayuan` 标签，尚未自动锁定版本。

保留“正在使用的版本 + 最近一两个验证可回退的版本”即可，具体数量按磁盘和发布频率调整。本机构建缓存、服务器旧镜像、镜像仓库远端标签应分别管理；清理其中一处不会自动清理其他两处。回退镜像也不等于回退数据库结构，破坏性迁移需要单独的恢复方案。

## 5. 本地数据库与镜像是什么关系

代码和数据有不同的生命周期。修改页面或 API 需要更新应用；已有数据库不应随每次代码修改重新初始化。

| 数据 | 当前本地开发 | 当前 Docker 部署 |
| --- | --- | --- |
| MySQL | 仓库 `.data/` 下的本地实例数据 | `mysql_data` 命名卷 |
| Redis | 本地持久化目录 | `redis_data` 命名卷，启用 AOF |
| Neo4j | 本地数据目录 | `neo4j_data` 与 `neo4j_logs` 命名卷 |
| Qdrant | 本地存储目录 | `docker/data/qdrant_storage` 绑定挂载 |
| 上传、解析、审核产物、头像等 | 仓库 `.data/` | `docker/data/` 下相应目录绑定挂载 |

这里的 `docker/data/` 来自当前 Compose 中的 `./data/...`：默认相对于 Compose 文件所在目录解析，并非仓库根 `.data/`。换目录、换 Compose 项目名、换连接配置，都可能使程序看到另一份存储；“页面突然没数据”不一定意味着旧数据被删除。

开发数据库留在本机、应用使用 Docker 在技术上可行，但当前 Compose 不是开箱即用的混合配置。容器内 `127.0.0.1` 指容器自己；不能把现有本地 `.env` 原样套进去。需要显式调整主机连接地址、监听权限和 Compose 依赖。当前本地链路已经能热重载，通常没有必要仅为调试再引入这一层。

## 6. 未来在服务器上如何写代码和调试

### 6.1 推荐选择

| 场景 | 建议方式 | 主要代价 |
| --- | --- | --- |
| 继续在本机写代码 | 保留当前本地数据库和热重载，提交后构建部署版本 | 本地仍需维护开发依赖 |
| 需要服务器算力或远程开发 | 独立开发机或虚拟机，通过 SSH 远程编辑，运行热重载服务 | 多维护一套开发环境和数据副本 |
| 验证生产构建、Nginx、上传等行为 | 独立验收环境运行固定版本镜像 | 构建一次并做真实链路检查 |
| 正式服务 | 固定版本镜像、独立持久数据和备份 | 发布与迁移需要可回退方案 |

推荐让远程开发机像当前本机一样工作：代码变化直接触发重载，确定版本后才构建部署镜像。无需每次保存文件都构建 Docker。

远程访问可使用 VS Code Remote SSH，并把开发页面转发到本机。示例中的用户和主机是占位值：

```bash
ssh -N -L 15173:127.0.0.1:5173 devuser@dev-host
```

之后访问本机 `http://127.0.0.1:15173`。SSH 转发不等于已经限制服务器其他端口；开发服务仍应绑定回环地址，并核验服务器防火墙及云安全组。当前 WSL 的防火墙特殊处理不能直接照搬到服务器。

### 6.2 只有一台服务器时，必须分开哪些东西

至少分开代码目录、数据库、Redis 与任务队列、文件目录、端口及配置凭据。还需限制开发进程的 CPU、内存和磁盘使用，避免构建或 GROBID 挤占正式服务。

| 边界 | 原因 |
| --- | --- |
| MySQL 与 `RAG_DATABASE_URL` | 防止调试迁移、删除或查询意外作用于正式库 |
| Redis 和 Worker | 防止开发 Worker 消费正式上传任务，或调度器重复入队；优先使用独立 Redis 实例 |
| Qdrant、Neo4j | 防止开发数据写入正式检索索引；最直观的是独立实例与存储 |
| 上传、解析、审核产物、头像 | 防止测试上传、删除和清理影响正式文件 |
| 端口、容器名和运行目录 | 防止启动、健康检查和停止操作命中另一套服务 |
| 凭据与外部调用 | 开发邮件、模型调用和定时任务应使用明确的开发配置，避免误发及额外费用 |

**当前仓库尚未提供完整的同机多环境隔离。** `scripts/lib-local.sh` 固定了 MySQL 3307、Redis 6379、Python 8000、Go 8080、Vite 5173 和 GROBID 8070/8071 等端口。`scripts/gen-env.py` 也使用本地连接配置；仅复制仓库或换 `.env` 不能保证两套服务独立。本地 GROBID 已改用 PID/进程组管理，未知监听者会阻断启动，不再重建同名容器。

Compose 的 `-p` 项目名通常能分开默认网络与命名卷，但**不能自动分开相同的宿主机绑定目录和端口**。当前 Compose 发布 `80`、`3306`、`7474`、`7687`、`6333`，没有限定 `127.0.0.1`；在服务器上应按实际访问需求收窄数据库端口，不能直接把开发数据库暴露到公网。

如果以后采用“数据库容器化、源码挂载进开发容器”的模式，应另设开发编排和热重载命令，只在依赖变化时重建。当前仓库没有 `docker/compose.dev.yaml`，生产前端镜像运行 Nginx，单纯把源码挂进去不会获得 Vite 热更新。该方案属于后续选项，不是本次已交付能力。

### 6.3 当前本地数据如何进入服务器

部署代码与迁移数据库要分开处理。Git 和应用镜像不会包含当前本地数据库；服务器上的空库不会自动获得本机内容。

建议流程如下，实际恢复和迁移须在确认目标后实施：

1. 区分目标是开发副本还是正式数据迁移，记录数据库及应用版本；开发副本按需要去除敏感信息。
2. 使用数据库支持的一致性备份方式，并协调暂停应用写入、上传 Worker 和定时任务，保证数据库记录与附件来自一致时间范围。
3. 分别准备 MySQL 逻辑备份、Neo4j 备份或导出、Qdrant 快照，以及上传文件、解析结果、审核资料、头像和所需映射文件。不要直接复制运行中的数据库底层目录作为跨机器通用备份。
4. 单独判断 Redis 中需要保留的草稿和任务状态，不能一律当成可丢弃缓存；恢复历史队列前检查是否会重复执行任务。
5. 在目标环境新建独立存储并恢复，按目标机器生成配置。凭据通过私密渠道配置，不放进 Git 或镜像。
6. 确认 `DATABASE_URL`、`RAG_DATABASE_URL` 和所有存储地址，再执行与应用版本匹配的迁移；核对实际 Alembic 分支，不能假定总是只有一个 head。
7. 验证登录、论文与附件读取、上传队列、审核、检索以及 RAG 实际调用。恢复成功并经过观察后，再决定是否退役旧环境。

跨机器打包与部署已有 [Issue #112](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/112) 和 [Spec](../../specs/112-portable-local-deployment/spec.md)。本文不把其规划或并行开发产物视为可用命令，完成状态以 Issue 和真实验收为准。

## 7. 已有空间如何清理

先减少重复构建，再处理存量。清理是有删除效果的独立操作；以下命令仅作说明，本次没有执行，也不代表已确认本机资源可以删除。

### 7.1 先处理明确不需要的镜像与缓存

检查版本保留需求和所有共享项目后，可考虑交互式命令：

```bash
# 删除符合时间条件的悬空镜像；不带 -a，不扩大到所有未使用镜像。
docker image prune --filter "until=168h"

# 删除符合过滤条件的构建缓存，并尝试保留指定缓存空间。
docker builder prune --filter "until=168h" --keep-storage 10GB
```

镜像 `until` 按创建时间筛选，不是“已经闲置七天”；缓存时间过滤的具体语义按所用构建器核验。`--keep-storage` 是本次回收参数，不是持续生效的硬性磁盘上限。上述清理作用于对应 Docker daemon 或构建器，并非仅限 SC-Wiki；Buildx 自定义构建器需单独管理。

本机快照没有悬空镜像，默认 `image prune` 可能释放不了空间。也不能把 673.5 MB 的缓存大小当成可释放大小；当时 Docker 报告的可回收缓存只有 1.008 MB。

### 7.2 不把大范围清理当作日常启动步骤

- `docker image prune -a` 会删除所有符合条件且未被容器引用的镜像，包括准备用于离线部署或回退的版本。
- `docker container prune` 会删除停止容器及其可写层，里面可能还有未导出的文件和诊断信息。
- `docker compose down -v` 会删除该次命令所管理的非外部数据卷；`docker volume prune` 按选项删除未被容器引用的卷，不能用来判断旧数据库是否无用。
- 不把 `docker system prune -a --volumes` 作为统一解决方案，也不把“停用一两周”当作备份可以删除的充分条件。

当前 `make clean-docker` 只打印建议命令，并不自动执行，但其中“仅影响重建速度”的提示不适用于所有容器和镜像；判断应以上述实际删除范围为准。

删除任何旧数据卷前，应明确卷属于哪个环境、里面是什么、有无独立备份以及备份是否能恢复。镜像可以重新拉取，唯一数据库不能靠重新部署找回来。
