# Feature 规格：建立管理员文献处理历史并修复审核页元数据

**GitHub Issue**：[#87](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/87)

**创建日期**：2026-09-03

**状态**：已实现；目标回归通过（全量前端另有 3 项无关基线失败）

## 背景与目标

字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。

当前 `paper_review_events` 只记录审核人、审核结果、审核意见和时间。首次上传没有事件，
普通修改也没有历史；已通过论文的科学数据升版只留下单一“退回待审核”审核事件。管理员
无法从“记录”了解一篇文献由谁上传、谁修改以及每位审核人的意见。

本 Feature 建立每篇文献唯一、不可变的处理历史：上传、修改、审核。历史只记录操作类型、
操作者、时间、论文版本、审核结果和审核意见，不保存字段级差异或旧内容快照。论文当前表
仍只承载最终内容、当前审核状态和最新审核意见。

## 用户场景与验收

### 用户故事 1：审核前核对来源（优先级：P1）

管理员或超级管理员打开管理工作台论文列表，在审核前看到真实上传者。

**优先级理由**：上传者是审核人员核对文献来源的必要上下文。

**独立验收**：列表接口返回的上传者公开用户名可在论文列表显示；缺失上传者不伪造身份，
详情接口不返回无需求的物性数量统计。

**验收场景**：

1. **假如** 论文由 `author` 上传，**当** 论文列表加载，**那么** 在操作区域显示“上传者: author”，
   且用户名可点击进入 `/users/author`，列表不显示“记录”列。
2. **假如** 历史导入论文没有上传者，**当** 论文列表加载，**那么** 显示“上传者: -”，
   不显示空白、`undefined` 或虚构用户名。
### 用户故事 2：查看文献处理时间线（优先级：P1）

字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。

**优先级理由**：这是本 Feature 的核心价值，能让审核人员理解文献如何进入当前状态。

**独立验收**：时间线清楚显示每条事件的类型、操作者和时间；审核事件同时显示结果和
审核意见，空意见明确显示“未填写审核意见”。

**验收场景**：

1. **假如** 文献经历上传、修改、通过审核，**当** 点击“历史”，**那么** 依时间从早到晚
   显示三条对应事件。
2. **假如** 两位管理员先后退回和通过同一文献，**当** 查看时间线，**那么** 两人的审核结果、
   审核意见和时间分别保留。
3. **假如** 普通用户调用历史接口或尝试打开管理端历史视图，**当** 请求发出，**那么** 被权限层
   拒绝，不能读取完整内部历史。
4. **假如** 历史上传事件没有可确认的上传者，**当** 查看时间线，**那么** 显示“历史导入，
   上传者未知”。

### 用户故事 3：可靠追加处理历史（优先级：P1）

系统在新上传、实际修改和每次实际审核时追加一条历史，且不因一次编辑页保存的多段请求
产生重复修改事件。

**优先级理由**：错误或重复的时间线会直接削弱审核记录的可信度。

**独立验收**：一次有实际变更的“保存修改”产生一条修改事件；同值保存不产生事件；同一
审核请求重试不产生第二条审核事件。

**验收场景**：

1. **假如** 管理员一次保存同时修改论文元数据和科学数据，**当** 两段请求都成功，**那么**
   时间线只增加一条“修改”。
2. **假如** 管理员直接保存未变更的数据，**当** 请求完成，**那么** 不增加“修改”事件。
3. **假如** 审核请求因网络重试重复送达，**当** 使用相同操作标识处理，**那么** 仅保留一条
   审核事件。
4. **假如** 论文被物理删除，**当** 删除事务成功，**那么** 该论文的处理历史一并删除，
   不留下孤儿记录。

### 边界与异常场景

- 历史接口加载失败不阻塞编辑页；入口显示错误和重试操作。
- 审核意见允许为空，但时间线必须明确表达该审核人未填写意见。
- 账号更名后，新增事件记录当时的用户名快照；历史数据回填只能使用迁移时可获得的用户名。
- 历史修改无法由现有数据可靠归属操作者和时间，不得回填。
- 自动解析、AI 推理、文件下载和只读浏览不产生处理历史。

## 需求

### 功能需求

- **FR-001**：管理端论文列表接口必须返回 `uploader_name`；其值为上传者公开用户名或 `null`。
  管理端详情接口不得返回本 Feature 未使用的 `record_count`。
- 字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。
- **FR-003**：仅 active `admin` 与 active `superadmin` 可请求和查看
  `GET /api/admin/papers/:id/history`；上传者和匿名用户不得读取完整历史。
- **FR-004**：历史接口必须按 `occurred_at` 升序返回 `uploaded`、`modified`、`reviewed` 事件，
  每条包含事件类型、操作者展示名、时间、论文版本；`reviewed` 额外包含审核结果与审核意见。
- **FR-005**：新上传的待审论文必须在创建 `Paper` 的同一数据库事务中追加一条 `uploaded` 事件。
- **FR-006**：每次实际成功审核必须在更新论文最终状态的同一数据库事务中追加一条 `reviewed`
  事件；相同审核操作标识的重试必须幂等。
- **FR-007**：一次实际成功的编辑保存必须至多追加一条 `modified` 事件。编辑页发送同一
  `history_operation_id` 给论文级和科学数据级写入；服务端只在检测到实际数据变化时尝试追加，
  由操作标识唯一性合并多段请求。
- **FR-008**：系统必须把 `paper_review_events` 演进为唯一的 `paper_history_events` 事实来源，
  并把既有审核事件迁为 `reviewed` 事件；不得保留两个并行写入的审核历史来源。
- **FR-009**：迁移必须为每篇既有论文回填一条 `uploaded` 事件；有
  `uploaded_by_user_id` 时显示该用户，没有时标记为“历史导入，上传者未知”。迁移不得创建
  无法证实的 `modified` 事件，且不得丢失既有审核意见。
- **FR-010**：审核贡献榜只能统计 `reviewed` 事件；`uploaded` 与 `modified` 不得计入审核数。
- **FR-011**：论文物理删除必须在既有级联删除顺序中删除 `paper_history_events`，并保持没有
  孤儿历史记录。
- **FR-012**：审核成功后必须立即返回当前角色工作台：`admin` 到 `/admin`，`superadmin` 到
  `/superadmin`；审核失败时留在编辑页并显示失败提示。
- **FR-013**：新增接口和界面必须提供中英文文案，且不得向普通用户泄露内部审核意见。

### 关键实体

- **文献处理历史 (`PaperHistoryEvent`)**：一条不可变的上传、修改或审核动作。它只描述谁在
  何时对哪个论文版本完成了哪类处理，不保存字段差异。
- **操作标识 (`history_operation_id`)**：编辑页一次保存生成的 UUID。论文级与科学数据级请求
  共享它，以使同一次业务操作在历史中只出现一次。
- **操作者用户名快照 (`actor_username_snapshot`)**：事件发生时的公开用户名。账号后续改名不会
  改写新事件的历史显示；旧数据回填使用迁移时能查到的名称。

## 成功标准

- **SC-001**：真实管理端列表和详情接口在有上传者和无上传者时返回正确元数据；论文列表显示
  上传者或稳定占位，且列表、编辑页和管理工作台均不出现 `record_count` 或“物性记录”。
- **SC-002**：管理员和超级管理员能从论文列表操作区域打开时间线；普通用户访问该接口返回 403。
- **SC-003**：新上传、一次有变更的保存、一次审核各产生一条相应事件；同值保存和重试不重复。
- **SC-004**：迁移后，所有既有审核事件及其意见仍可读取，每篇论文均有一条上传事件，且无旧
  修改事件被伪造。
- **SC-005**：审核贡献统计仅计 `reviewed`，上传和修改事件不会改变审核排名。
- **SC-006**：删除论文后，数据库中没有指向该论文的历史事件。
- **SC-007**：审核成功后角色路由正确，审核失败不导航。
- **SC-008**：目标 Go、Python、Vitest 测试和前端生产构建均通过。

## 假设与依赖

- 现有 `review_comment` 继续保存论文的最新审核意见，供上传者读取；时间线保存每次审核意见。
- 现有论文物理删除语义保持不变，历史记录不提供单独恢复能力。
- 现有 `paper_review_events.classification_snapshot` 作为历史兼容字段迁移保留但不向时间线输出，
  新功能不新增字段级或分类快照。

## 范围外事项

- 字段级修改差异、旧版本正文/科学数据快照及差异对比。
- 上传者、普通用户或匿名用户查看完整处理时间线。
- 自动解析、AI 推理、文件上传中间状态、下载和只读查看的事件。
- 伪造无法从现有数据可靠恢复的历史修改。
- 恢复已经物理删除的论文或其历史。

## 澄清记录

### 2026-09-03

- 问：审核成功后提示停留后再返回，还是立即返回？ → 答：立即返回当前角色工作台，工作台不接收额外成功提示。
- 问：完整历史对哪些角色可见？ → 答：仅管理员和超级管理员可见；入口位于管理工作台论文列表。上传者只保留当前审核状态与最新审核意见。
- 问：当前“记录”数量与处理历史如何在界面区分？ → 答：原有物性数量展示不是本 Feature 需求，列表、编辑页和快速审核弹窗不再展示该数量；历史统一通过论文列表每行操作区域带历史图标的“历史”入口打开上传、修改和审核时间线。
- 问：已有论文的历史如何处理？ → 答：回填可可靠确认的上传与审核事件；不伪造历史修改。缺少上传者的上传事件显示“历史导入，上传者未知”。
- 问：一次保存修改如何记入历史？ → 答：一次成功的用户“保存修改”只追加一条修改事件；同值重复保存不产生事件；多段请求以同一操作标识合并。
- 问：现有审核事件机制如何承载完整处理历史？ → 答：通过数据库迁移演进为唯一的文献处理历史，保留原有审核意见；贡献审核榜只统计审核类型。

### 2026-09-04

- 字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。
- 问：上传者和历史入口如何交互？ → 答：有用户名的上传者可点击进入 `/users/:username`；“历史”仅显示图标，使用 Tooltip 和无障碍名称表达操作含义，与后续编辑、审核、删除图标保持一致。
