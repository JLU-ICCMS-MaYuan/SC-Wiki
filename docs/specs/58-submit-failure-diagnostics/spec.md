# Feature 规格：提交审核失败的可诊断性与必填定位

**GitHub Issue**：[#58](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/58)

**创建日期**：2026-08-26

**状态**：草稿

## 背景与目标

用户在校对页点击「提交审核」后，横幅只显示一句「提交审核失败」，没有原因也没有指出该改哪里。用户无法区分「自己漏填了字段」与「系统故障」，只能反复试错。

实测该次失败**不是校验失败**，而是后端 500：PDF 转 Markdown 时把正文段落误判成 `##` 章节标题，超长文本写入 `varchar(500)` 的 `paper_chunks.section_name` 触发 `DataError (1406)`。未捕获异常经 Starlette 默认处理返回纯文本，前端取不到结构化 `detail`，只能回退通用文案。

因此本 Feature 要同时解决三件独立的事：让这类解析噪声不再阻断提交且不丢正文、让任何后端异常都给出可理解原因、让真正的必填校验能定位到字段。

目标是用户提交失败后能立刻知道「是什么原因」以及「该改哪里」，而不是看到一句无信息量的话。

## 用户场景与验收

### 用户故事 1：解析噪声不再阻断提交，且正文不丢失（优先级：P1）

用户上传的 PDF 经转换后含被误判为章节标题的正文段落。用户完成校对后点击提交，提交成功，被误判的那段正文仍然可被搜索和 RAG 引用。

**优先级理由**：这是当前的硬阻塞。此类 PDF 完全无法提交，用户全部校对工作无法落地，后续任何提示优化都无从验收。实测全部已解析论文的 28 个 `##` 标题中有 6 个超长（21%），不是罕见边界。

**独立验收**：用当前失败的 ThH10 任务重新提交成功，且被误判段落的文字出现在某个文本块的正文内容中。

**验收场景**：

1. **假如** 论文 Markdown 含一个长度 1389 字符的 `##` 行（实为正文段落），**当** 用户提交审核，**那么** 提交成功，论文进入 `pending`。
2. **假如** 同一篇论文已完成分段，**当** 检查生成的文本块，**那么** 被误判段落的文字出现在某个块的正文内容中，且该块沿用其所属真实章节的章节名。
3. **假如** 论文含正常的短章节标题（实测真实标题为 65–204 字符），**当** 分段完成，**那么** 这些标题仍作为章节名，分段结果与修复前一致。
4. **假如** 某个章节名在归类后仍超出存储列长度，**当** 写入数据库，**那么** 按列长度安全截断而不是抛出异常。

### 用户故事 2：后端异常给出可理解原因（优先级：P1）

用户遇到后端未预期异常时，横幅显示可理解的失败原因，而不是通用文案。

**优先级理由**：与 US1 同为 P1，但解决的是不同层面的问题——US1 修掉一个具体故障源，US2 保证下一个未知故障源不会再退化成「提交审核失败」这句无信息量的话。Overview 失败语义已要求「上传、抽取、LLM 和数据库错误必须返回或记录明确原因」，当前未预期异常不满足该约束。

**独立验收**：人为触发一个后端未预期异常，横幅显示可理解原因，且响应体不含堆栈、SQL 语句与内部路径。

**验收场景**：

1. **假如** 提交过程中发生未预期异常，**当** 前端收到响应，**那么** 响应体是结构化 JSON，含错误码与可读消息。
2. **假如** 前端收到该响应，**当** 渲染失败横幅，**那么** 显示该消息而不是「提交审核失败」。
3. **假如** 异常信息含数据库语句、堆栈或服务器文件路径，**当** 构造对外响应，**那么** 这些内容不出现在响应体中。
4. **假如** 后端已返回结构化 `detail`（如 400 校验错误），**当** 渲染横幅，**那么** 行为与修复前一致，不被兜底逻辑覆盖。

### 用户故事 3：必填校验定位到字段（优先级：P1）

提交因必填项缺失而失败时，页面展开对应材料状态卡片、滚动到第一个出错字段并聚焦，出错字段显示错误态与提示文字，横幅列出全部缺失项。

**优先级理由**：这是用户原始诉求的正面表达（「转化到必须要填的位置，然后提示我这些地方必须填写」）。列为 P1 而非 P2：即使 US1、US2 落地，只要校验反馈仍是单条无定位文案，用户在长表单里依然找不到该改哪里，原始问题没有解决。

字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。

**验收场景**：

1. **假如** 第 3 个材料状态缺少「材料」，**当** 用户提交，**那么** 第 3 张卡片自动展开、该输入框获得焦点并显示错误态与提示文字。
2. **假如** 多处必填项缺失，**当** 用户提交，**那么** 横幅列出全部缺失项，而不是只报第一条。
3. **假如** 出错字段位于默认折叠的材料状态卡片内（卡片数 >2 时仅第一张展开），**当** 提交失败，**那么** 该卡片被展开使字段可见。
4. **假如** 校验规则只存在于后端（如材料家族缺失、压强区间倒置），**当** 后端返回 400 与错误码，**那么** 前端按错误码定位到对应材料状态并给出同样的展开与聚焦行为。
5. **假如** 用户修正全部缺失项后再次提交，**当** 提交成功，**那么** 错误态与横幅清除。

### 边界与异常场景

- 整篇论文没有任何 `##` 标题：现有行为是整体作为「全文」一段，保持不变。
- 全部 `##` 行都被判为正文：至少产出一个可检索文本块，不得产出零块。
- 被误判段落位于首个真实章节之前：没有可沿用的上级章节名时使用「全文」。
- 后端返回 400 但错误码未被前端识别：退回展示后端消息，不做静默丢弃，也不阻断提交按钮恢复可用。
- 校验通过但提交仍失败（如 DOI 重复 409、一致性确认 409）：保持既有专门处理，不被新的兜底逻辑覆盖。
- 同一次提交同时存在前端可见缺失与后端专属规则违反：前端先报可见缺失，修正后再由后端报出其专属规则。

## 需求

### 功能需求

- **FR-001**：系统必须在分段时按长度阈值判定 `##` 行是否为真实章节标题；超出阈值的行归为正文内容，沿用其所属真实章节的章节名。
- **FR-002**：系统必须保证被判为正文的 `##` 行文字进入文本块的正文内容，可被搜索与 RAG 引用，不得仅存在于章节名中。
- **FR-003**：系统必须在写入前按存储列长度安全截断章节名与标题字段，使解析噪声不能导致提交失败。
- **FR-004**：系统必须为未捕获异常返回结构化错误响应，含错误码与面向用户的可读消息。
- **FR-005**：系统必须在对外错误响应中排除堆栈、数据库语句与服务器内部路径。
- **FR-006**：前端必须在后端返回结构化错误时展示其消息；仅在确实无结构化信息时才回退通用文案。
- **FR-007**：前端校验必须返回错误清单而非单条消息，每项含所属材料状态序号与字段标识。
- **FR-008**：提交失败时前端必须展开包含出错字段的材料状态卡片，滚动到第一个出错字段并使其获得焦点。
- **FR-009**：出错字段必须显示错误态与说明文字，横幅必须汇总全部缺失项。
- **FR-010**：前端必须能按后端校验错误码定位到对应材料状态，并给出与前端校验一致的展开与聚焦行为。
- **FR-011**：用户修正后重新提交成功时，系统必须清除全部错误态与横幅。

### 关键实体

- **校验错误项**：一次校验发现的单个问题。含材料状态序号（论文级问题为空）、字段标识、面向用户的说明文字。用于横幅汇总与字段定位，不持久化。
- **章节判定结果**：分段过程中对每个 `##` 行的判定，取值为「真实标题」或「正文内容」。仅存在于分段过程内，不持久化；影响文本块的章节名与正文内容归属。

## 成功标准

- **SC-001**：当前失败的 ThH10 任务（12 个 `##` 标题、最长 1389 字符）能提交成功并进入 `pending`。
- **SC-002**：该论文被误判的 3 段正文文字全部出现在文本块正文内容中，探针检索命中率 100%。
- **SC-003**：实测真实标题（65–204 字符）的分段结果与修复前一致，无回归。
- **SC-004**：后端未预期异常时横幅显示可理解原因而非「提交审核失败」，且响应体不含堆栈、SQL 与内部路径。
- 字段提示规则及相关历史已迁移至 [#220](../220-field-red-marking/spec.md)，本处不再独立定义。
- **SC-006**：既有后端与前端测试全部通过，提交成功路径、DOI 重复 409 与一致性确认 409 行为不变。

## 假设与依赖

- 长度阈值取 300 字符：实测真实标题最长 204、被误判正文最短 389，300 落在两者之间且两侧各有余量。该阈值是启发式判定，不是精确语义识别。
- 分段逻辑变更只影响此后新解析或重新解析的论文，不回溯改写已入库的 `paper_chunks`；已入库数据的补正不在本 Feature 范围。
- `paper_chunks.section_name` 与 `heading` 保持 `varchar(500)`，不改列宽——问题在于写入未受控，不在于列太窄。
- 依赖既有 `_upload_error(status_code, code, message)` 错误契约与前端 `backendErrorReason` 提取逻辑，沿用不重建。
- 前端校验与后端 `_validate_draft` 规则集不完全重合是既有事实（后端独有 `material_family_required`、`invalid_pressure_range`、`dedicated_property_required`、`invalid_tc_result_kind` 等）。本 Feature 不统一两侧规则集，只保证两侧错误都能定位到字段。

## 范围外事项

- 不引入 OCR 或更换 PDF 转 Markdown 工具：本 Feature 只让下游对解析噪声鲁棒，不改进解析本身。
- 不做精确的标题语义识别（如模型判定）：YAGNI，长度阈值已能分离实测数据中的两类。
- 不回溯修正已入库论文的 `paper_chunks` 章节名与正文归属：需要独立的数据迁移决策。
- 不统一前后端校验规则集：属于更大的契约收敛工作，与本 Feature 的「失败可诊断」目标不同。
- 不改动详情页与校对表单的字段一致性问题：见 [#59](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/59)。
- 不改动后端读取契约中的字段缺失与恒零值问题：见 [#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57)。

## 澄清记录

### 2026-08-26

- 问：被 PDF 转换工具误判为 `##` 章节标题的正文段落该如何处理？截断章节名是最小改动，但实测 `_split_by_h2` 不把标题行放入正文内容，因此截断会永久丢失该段文字（最长 1389 字符），搜索与 RAG 均无法引用。→ 答：认错的归为正文。超长 `##` 行不当标题，归入正文内容并沿用上一个真实章节名；写入层再加长度截断作为兜底。
- 问：US3 的优先级应为 P1 还是 P2？→ 答：定为 P1。US1、US2 修的是「为什么失败没说清」，US3 修的是「该改哪里没说清」，后者是用户原始诉求的正面表达，缺失则原始问题未解决。
- 事实查证（未询问用户）：用户报告「提交时提示失败但没有任何提示，是不是有什么值没填好」。实测该次失败与必填项无关，根因是 `DataError (1406)` 导致的 500。用户的推测不成立，但其诉求（失败后定位到必填位置）仍然有效，故保留为 US3。
- 事实查证（未询问用户）：前端 `validate()` 与后端 `_validate_draft` 规则集不重合，后端独有规则触发时前端无任何字段定位能力。据此增加 FR-010。
