# 修复规格：移除应用层双重响应压缩

**GitHub Issue**：[#118](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/118)

**创建日期**：2026-09-29

**状态**：已确认

## 背景与目标

上传解析记录中 `2014 H3S-段德芳.pdf` 的详情页显示 `The string did not match the expected pattern.`。
该文本是 Safari/WebKit 解析 JSON 失败时的原生报错；任务本身已解析完成。

浏览器经网关访问 Python 接口时，大于 1KB 的响应被压缩两次，响应头为 `Content-Encoding: gzip, gzip`，
浏览器无法还原出 JSON。两层压缩均无需求来源；[#19](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/19)
曾遇到同一现象，只在生产 nginx 的两个上传路由绕开。

本次目标：应用层不再压缩 HTTP 响应，一并删除为绕开压缩而存在的配置与说明，使所有入口返回可直接解析的正文。

## 用户场景与验收

### 用户故事 1：解析详情正常显示（优先级：P1）

上传者打开已完成的上传解析记录，看到分段与汇总内容，而不是浏览器解析报错。

**优先级理由**：直接解除当前可见故障。

**独立验收**：打开 `2014 H3S-段德芳.pdf` 的解析详情，内容正常显示。

**验收场景**：

1. **假如**解析详情响应超过 1KB，**当**浏览器经前端入口请求，**那么**正文可被直接解析为 JSON 并显示。
2. **假如**客户端声明支持 gzip，**当**经任一入口请求任意 JSON 接口，**那么**响应不带内容编码，正文为原文。

### 用户故事 2：不再保留压缩相关绕过（优先级：P2）

维护者阅读代码、部署配置与文档时，不再看到响应压缩及其绕过配置，本地与生产链路在此项上没有差异。

**优先级理由**：避免后续有人重新引入或误以为需要维护该差异。

**独立验收**：检索源码、配置、测试和当前文档，不存在应用层响应压缩或 `Accept-Encoding` 清空。

**验收场景**：

1. **假如**检索仓库源码与部署配置，**当**查找响应压缩实现与绕过，**那么**没有结果。
2. **假如**阅读部署与本地开发文档，**当**查看本地与生产差异，**那么**不再列出 `Accept-Encoding` 差异项。

### 边界与异常场景

- 删除后响应体积变大；本地和内网部署不以带宽为瓶颈，不再保留任何接口的压缩兼容。
- 上游若自行返回已编码正文（如静态资源），原样透传，不在应用层重新编码。
- 已下载的前端静态资源由 Vite 或 nginx 提供，本次不改变其行为。

## 需求

### 功能需求

- **FR-001**：Python 服务不得压缩 HTTP 响应。
- **FR-002**：Go 网关不得压缩自身或代理转发的 HTTP 响应。
- **FR-003**：生产 nginx 配置不得保留为绕开压缩而清空 `Accept-Encoding` 的设置及相关注释。
- **FR-004**：仅为压缩行为存在的测试必须删除；其余测试不因删除压缩而失效。
- **FR-005**：当前功能文档必须删除 `Accept-Encoding` 差异项与压缩相关说明，Spec 与 Issue 双向关联。

## 成功标准

- **SC-001**：分别经 Python、Go、前端三个本地入口请求大于 1KB 的 JSON 接口（声明支持 gzip），响应均无内容编码且可解析为 JSON。
- **SC-002**：`2014 H3S-段德芳.pdf` 的解析详情接口经前端入口返回可解析 JSON。
- **SC-003**：源码、部署配置与测试中应用层响应压缩相关代码为零处；Go 全包测试与相关 Python 测试通过。

## 假设与依赖

- 本地与内网部署带宽不构成瓶颈，删除压缩不需要替代方案。
- 关联 #19：其“gzip 响应截断”验收项由本 Issue 从根因解决；#19 其余验收项不在本次范围。

## 范围外事项

- 在 nginx 或其他代理层新增压缩。
- 修改前端错误展示文案。
- #19 的 413、异步驱动、假成功等其他验收项。
