# 依据与取舍

## 指定讨论材料

以下摘录是用户指定的材料，技术内容不冒称逐字新指令或已实现。

第二项：长篇提取与重复输入优化

##### 目标与当前问题

用户希望首轮尽可能找准该填的内容，避免长篇 PDF 为寻找遗漏默认反复整篇提取；同时认可分段并发、优先按句子边界切分，以及给本段附上上一段末尾原文。目标是降低不必要的重复输入和等待，保留跨来源科学关系的正确性。

当前分段主提取顺序执行；窗口边界会在预算允许时保留前页，并补有限邻页非表格块；提取、科学整理和字段核对也可能反复读取相同内容。用户所举“10 页逐页附完整前页，共传相当于 19 页”的示例成立，但当前并非每页必然这样重复，实际重复量需测量。

与 LangExtract 的取舍应根据相同来源、模型及任务边界比较，不以代码复杂度判断优劣。它的 `extraction_passes` 默认 1；设为多轮时，同一配置重复提取，后轮不重叠的位置加入、重叠时早轮优先。它不是逐轮针对上轮纠错或最终 AI 投票；重复可能补漏，也可能没有增益，位置合并不负责科学归属冲突。依据见 [annotation.py](https://github.com/google/langextract/blob/main/langextract/annotation.py) 和 [参数说明](https://github.com/google/langextract/blob/main/langextract/extraction.py)。

SC-Wiki 的整理和核对与独立重提不同，但仍存在重复阅读和围绕已有答案判断的风险。本轮讨论时科学整理最多 4 轮交互、字段核对外层最多 3 轮，已有有效结果可复用；这不是全篇读了七遍，也不能证明已经消除遗漏或重复。

##### 已认可方向：分段、上下文与并发一起调整

1. **优先保留语义和科学结构。** 正文按完整段落、句子边界组织，避免机械截断；小数、缩写和公式标点不能一概当作句末。表格按完整行组保留相关表头、单位、表注和跨行单元格，图片与公式保留相应说明。原文与来源身份不为分段而改写，超大块的拆分需兼顾现有 [完整块和表行约束](../../specs/114-multimodal-pdf-upload-agent/spec.md)。
2. **用有限前文减少固定整页重叠。** 借鉴 `context_window_chars`：在本段请求前附上前段尾部原文，尽量保留完整句或块边界，而不等待上一段模型回答。LangExtract 该选项默认关闭，超长句仍可被拆开；有限前文不是语义完整保证，见 [chunking.py](https://github.com/google/langextract/blob/main/langextract/chunking.py) 和 [prompting.py](https://github.com/google/langextract/blob/main/langextract/prompting.py)。真正依赖表注、表头或其他页时仍保留必要资料，不能把所有关系压成短尾句。
3. **先准备各段输入，再受限并发。** 保留分段身份和输出契约，多段同时请求，结果按原编号归位。LangExtract 的 `batch_length` 控制每批段数、`max_workers` 控制并发请求数，见 [模型接口实现](https://github.com/google/langextract/blob/main/langextract/providers/openai.py)。本项目 [_read_chunk](../../../backend/ingest/upload_jobs.py) 不以先前模型回答为必要输入，具有并发基础；共享进度、制品清单、模型配置、token 统计及 [停止续跑](../../../backend/ingest/model_runtime.py) 需一起适配，多任务叠加也要受接口额度约束。
4. **只对实际缺口继续处理。** 不默认为提高召回多遍独立提取全文；遇到具体缺口、冲突或变化，再定向查源。跨正文／补充材料的材料、压力、物相、方法和软件范围，继续借鉴现有目录、查源工具、科学整理和字段核对。单轮主提取不是整篇只发一次请求，也不禁止技术重试或必要人工审核。

辅助上下文和本段主要提取内容要有清楚边界；重复来源使用稳定身份，防止同一事实重复收录。结果去重不能收回已经花掉的输入 token，减少重复必须落实到实际请求。

##### 避免把输入问题仅当作压缩问题

Peng 2017 的讨论揭示：分段完成后，论文级填写调用仍接收整包科学候选和覆盖审计，可能在单次 96,000 token 本地预算门停止；这是发送前超限，不能当作上游 503。传输编码可以无损压缩，但不能代替按职责组织输入；输出不允许写科学记录，也不意味着总结不需要关键科学事实。

因此，提取、整理和核对都需审查“本次究竟要读什么、输出什么、较前一步新增什么”。候选归属、来源定位、漏提与处理中丢失检查、科学语义核对各有职责；部分是程序检查，并不花模型 token。减少的是无新增信息的重复读取和判断，不能因为显示上步骤多就删除必要保护，也不另加一轮“再确认”。

##### 待定细节与实际效果边界

窗口大小、前文尾部长度、并发数和限流方式尚未定；先前建议的 2—3 段只是评估起点。并发可能缩短等待但不直接减少 token，短前文也不能保证全部远距离依赖成立。后续需要分别比较文档解析、模型提取及核对耗时，以及实际 token、重复输入、遗漏、关系错配和人工修改量；本轮不承诺倍数或节省比例。


## 工程选择

复用现有依赖和契约，保存起始工作区版本，只提交本次改动。不提高96k预算，不截断科学依据，不默认多遍全文提取；跨段必要依赖与现有防遗漏和语义核对保留。

## 本轮分组决策

用户明确要求材料表单少量一组、先填写再核对后进入下一组，采用默认2个状态，替代超限才拆和整稿后核对。状态规划及结构归属仍先完成，以免字段核对后改变结构依赖；分组不改变真实材料状态或科学标准键。

程序保留全稿，但模型只收本组候选/字段。核对原先每批默认附最多120000字符原文；材料组改为优先本组实际引用块。正式来源目录可能是Markdown窗口，故同文件唯一原句可用于选择预读窗口，不能赋予科学支持；缺资料继续用现有工具查找。本次不改变论文级核对、主动单字段核对或预算阈值。

固定材料数不能保证任意表单都小于预算；组内仍执行真实请求预算门，单状态必要输入仍放不下时停止，保留已完成前组，不默默裁剪或改发全稿。共享源码中原有#226变更不属于本任务，生成核对函数的本次增量单独投影验证和提交。
