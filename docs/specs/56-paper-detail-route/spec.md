# Feature 规格：已提交论文详情页持久入口

**GitHub Issue**：[#56](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/56)

**创建日期**：2026-08-26

**状态**：草稿

## 背景与目标

用户提交论文审核成功后，页面会跳转到只读的「论文详情」页，可以看到刚提交的内容。但一旦点击
「返回上传列表」，该详情页就再也打不开：

- 上传任务中心不再列出该论文（提交成功后 Redis 任务态已被清理）。
- 全站没有「我的论文」或已提交论文列表入口。
- 详情页没有独立 URL，无法收藏或分享，刷新与浏览器后退也无法回到。

用户诉求明确：正式记录提交后不可再修改是合理的，但**应当始终能够只读复查自己提交了什么**。
本 Feature 让论文详情页获得持久、可寻址的入口，使复查不再依赖一次性的页面内状态。

## 用户场景与验收

### 用户故事 1：提交后随时回到详情页复查（优先级：P1）

用户提交论文审核后，希望在离开详情页之后仍能回来核对自己提交的内容，而不必重新上传或求助管理员。

**优先级理由**：这是 Issue 报告的核心缺陷。没有它，用户提交后就永久失去了对自己数据的查看能力，
是数据可见性问题而非体验优化。

**独立验收**：提交成功后离开详情页，再通过浏览器返回或直接访问详情地址，仍能看到同一篇论文的
只读内容。

**验收场景**：

1. **假如** 用户刚提交论文审核成功并停留在详情页，**当** 用户刷新浏览器，**那么** 页面仍显示
   同一篇论文的只读详情，不回退到上传页。
2. **假如** 用户从详情页点击返回进入上传页，**当** 用户执行浏览器「前进」，**那么** 重新回到该
   论文的只读详情页。
3. **假如** 用户在别处保存了某篇论文详情的地址，**当** 用户在新标签页直接打开该地址，**那么**
   直接显示该论文的只读详情，无需先经过上传流程。

### 用户故事 2：无权访问时得到明确提示（优先级：P2）

论文详情地址可被直接输入或分享，因此必须在用户无权查看时给出清晰结果，而不是暴露内容或显示
含义不明的错误。

**优先级理由**：详情页从页面内状态升级为可寻址地址后，访问来源不再受上传流程约束，权限反馈成为
必需的配套行为。依赖 US1 的地址能力，故排在其后。

**独立验收**：用匿名身份或非上传者身份访问一篇待审核论文的详情地址，页面显示明确的无权提示，
且不出现论文任何字段内容。

**验收场景**：

1. **假如** 一篇论文处于待审核状态且访问者不是其上传者或管理员，**当** 访问者打开该论文详情
   地址，**那么** 页面显示明确的无权查看提示，不展示论文标题、摘要或任何字段。
2. **假如** 用户访问一个不存在的论文编号，**当** 页面加载完成，**那么** 显示明确的「论文不存在」
   类提示，并提供可返回的操作。
3. **假如** 用户未登录且论文尚未通过审核，**当** 用户打开该详情地址，**那么** 得到无权提示而非
   空白页面或加载失败。

### 用户故事 3：从列表入口找到自己提交的论文（优先级：P1）

用户希望不必记住或手工拼接网址，就能从界面上找到自己此前提交过的论文并进入只读详情。

**优先级理由**：与 US1 同为 P1。可寻址地址若没有界面入口，用户仍然只能手工输入网址，
原始诉求「始终能只读复查」未真正达成——US1 与 US3 合起来才构成完整能力。

**独立验收**：在用户页看到自己提交过的论文列表，点击任一条进入其只读详情页；提交成功后的
提示中可直接点击进入刚提交论文的详情。

**验收场景**：

1. **假如** 用户已提交过至少一篇论文，**当** 用户打开用户页，**那么** 看到「我的论文」列表，
   其中包含该论文的标题与审核状态。
2. **假如** 用户在「我的论文」列表中，**当** 点击某一条记录，**那么** 进入该论文的只读详情页。
3. **假如** 用户正在某篇论文的只读详情页，**当** 用户点击「我的论文」入口，**那么** 进入用户页的
   「我的论文」列表，并可从那里进入任意其他已提交论文。
4. **假如** 用户从未提交过论文，**当** 用户打开用户页的「我的论文」，**那么** 显示明确的空状态
   说明，而非空白区域或错误。

### 边界与异常场景

- 详情地址中的论文编号非数字或为负数时，视为无效地址并显示明确提示，不向后端发起查询。
- 访问任何未定义的前端地址（含以相对路径误拼出的地址，如 `/upload/papers/999999`）时，必须显示
  明确的「页面不存在」提示并提供返回操作，不得渲染空白页面。
- 「我的论文」列表加载失败时显示可重试的错误提示，不影响用户页其他区块。
- 后端服务不可用或网络失败时，显示可区分于「无权」和「不存在」的加载失败提示，并允许返回。
- 用户在详情页停留期间该论文被管理员审核通过或拒绝，本 Feature 不要求实时刷新；下次进入按最新
  状态展示。

## 需求

### 功能需求

- **FR-001**：论文详情页必须拥有基于论文编号的独立可寻址地址，页面内容由该地址唯一确定，不依赖
  任何一次性的页面内状态。
- **FR-002**：用户必须能够通过刷新、浏览器后退与前进、以及直接输入或分享地址，重新到达同一篇
  论文的只读详情页。
- **FR-003**：提交论文审核成功后，系统必须将用户导向该论文的详情地址，且此后离开详情页不会
  销毁再次访问该地址的能力。
- **FR-004**：详情页按合法站内来源返回，且返回后该论文详情地址仍然可用；搜索来源返回原检索条件、展示方式和页码，不再要求固定回到上传页。此为 [#178 后续需求](../178-search-results-navigation/spec.md) 的文档修订，功能代码尚待实施。
- **FR-005**：详情页的可见性判定必须沿用后端既有论文查看权限，前端不得放宽或自行判定权限。
- **FR-006**：当访问者无权查看、论文不存在、或地址中的论文编号无效时，系统必须分别显示可区分
  且明确的提示，且不展示论文任何字段内容。
- **FR-007**：系统必须在用户页提供「我的论文」列表，展示当前用户提交过的论文及其审核状态，
  每条记录可直接进入对应论文的只读详情页；无记录时显示明确空状态。
- **FR-008**：论文详情页必须提供前往「我的论文」列表的入口，使用户离开详情页后仍能通过界面回到
  任意一篇已提交论文，无需手工输入或拼接网址。
- **FR-009**：访问任何未定义的前端地址时，系统必须显示明确的「页面不存在」提示并提供返回操作，
  不得渲染空白页面。
- **FR-010**：「我的论文」列表不得置于上传页的活动任务区域内，以避免永久归档数据与受配额限制、
  24 小时后清理的临时任务混列。

### 关键实体

本 Feature 不新增、不修改任何持久化实体，仅改变前端页面的寻址方式与导航行为。论文数据的读取
沿用既有论文详情查询能力。

## 成功标准

- **SC-001**：提交审核成功后刷新页面，仍停留在同一篇论文的只读详情页，成功率 100%。
- **SC-002**：从详情页返回上传页后，通过浏览器前进或直接访问详情地址重新打开该论文详情，成功率
  100%。
- **SC-003**：对无权查看的论文、不存在的论文编号和无效论文编号三类访问，各自显示对应的明确提示，
  且响应中不出现论文标题、摘要或其他字段内容。
- **SC-004**：上传、解析、校对与提交流程的既有行为无回归，相关前端测试全部通过。
- **SC-005**：用户无需手工输入或拼接网址，即可从界面入口到达自己提交过的任意一篇论文的只读详情，
  路径不超过两次点击。
- **SC-006**：访问未定义地址时显示「页面不存在」提示，白屏出现率为 0。

## 假设与依赖

- 后端 `GET /api/papers/{id}` 已实现并正常工作，权限规则为：匿名仅可见 approved；登录用户可见
  approved 与 pending；上传者另可见自己的 rejected；管理员可见全部。本 Feature 直接依赖该规则，
  不做修改。
- 前端已使用客户端路由，新增论文详情地址属于既有路由体系的自然扩展。
- 详情页当前展示的字段存在缺失与恒零值问题，属 [#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57)
  范围；本 Feature 只解决可达性，不改变字段展示内容。

## 范围外事项

- 详情页字段缺失、恒零值与展示内容和提交数据不一致：由 #57 处理。
- 详情页组件中改了也无法保存的编辑态控件与死函数清理：一并交给 #57，避免同一文件改两遍。
- 「我的论文」列表的分页、搜索与排序：本次只做按提交时间倒序的基础列表，容量增长后再迭代。
- 上传页新增已提交论文列表：经评估否决，理由见澄清记录 2026-08-26 第 4 问。
- 论文编辑能力、管理员审核流程、后端权限规则调整。
- 新增后端接口：复用既有 `GET /api/papers/my-uploads`，不新建。
- 详情页内容的实时刷新或审核状态变更推送。

## 澄清记录

### 2026-08-26

- 问：详情页要以什么形式提供持久入口？→ 答：新增基于论文编号的独立路由地址，使浏览器前进/后退与
  刷新都能保持，地址可收藏可分享。不采用「仅在上传中心列出已提交论文」的方案，因为那样仍无法
  刷新保持或分享。
- 问：本 Feature 是否一并清理详情页组件中无法保存的编辑态控件？→ 答：不清理，交给 #57 一并处理。
  理由：#57 需要重写同一文件的字段展示，两件事分开做会改动同一文件两遍。
- 问：详情页升级为可寻址地址后，权限如何处理？→ 答：完全沿用后端既有 `GET /api/papers/{id}`
  权限判定，前端不放宽、不自行判定；无权时显示明确提示且不暴露内容。
- 问：首轮验收发现只有路由、没有界面入口，用户仍需手工拼接网址。已提交论文的列表入口放在哪里？
  → 答：放用户页。**否决上传页方案的理由**：上传页的
  「上传解析记录」与已提交论文生命周期性质相反——前者存 Redis、24 小时清理、受 100 条活动任务
  配额限制、语义是「待我处理」；后者存 MySQL、永久保留、无上限只增不减、语义是「已完结归档」。
  混列会导致三个具体问题：(1) 上传页的「0/100」配额徽章语义失真，因已提交论文不占配额；
  (2) 无界列表嵌入有界列表旁，随时间增长必然需要独立分页与筛选，届时它已是独立页面只是位置错误；
  (3) 待办工作区混入永久归档，用户每次上传都要先掠过历史记录。用户页作为个人资产归属地更合适。
  实施时修正了一处方案细节：原打算在提交成功的 Snackbar 中加「查看详情」按钮，但核实
  `UploadPage.handleTaskSubmitted` 后发现提交成功已直接 `navigate` 到详情页，Snackbar 随页面卸载
  消失，该按钮在真实路径上不可见。FR-008 因此改为「详情页提供前往我的论文列表的入口」——这才对应
  用户反馈的真实缺口：**离开详情页之后**回不去。
- 问：验收发现访问 `/upload/papers/999999`（相对路径误拼）显示全白页面。是否属本 Feature？
  → 答：属于。可寻址地址一旦对外，用户就可能拼出任意错误地址；白屏不满足「失败必须有明确提示」
  的既有约定。新增 FR-009 要求未匹配路由显示「页面不存在」并提供返回。


## 2026-10-29：检索与导航后续需求

关联 [Issue #178](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/178) 与[新Spec](../178-search-results-navigation/spec.md)。

原 FR-004 历史原文：

> 详情页的「返回」操作必须回到上传页，且返回后该论文详情地址仍然可用。

2026-10-29，用户在调查搜索来源错误返回后明确要求删除此强制约束，并认可按来源恢复检索。原上传流程的场景、SC-002及旧验证是历史记录，不得继续解释为所有来源都应返回上传页。新返回／刷新／前后退验收以#178为准；本轮只改需求文档，当前代码仍需按新规格实施。
