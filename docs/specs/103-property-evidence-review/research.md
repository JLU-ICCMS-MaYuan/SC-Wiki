# 决策与依据

- 故障属于证据转换遗漏、仅 record_key 映射、片段匹配静默 continue，以及缺少语义核对。依据 backend/api/rag.py、backend/ingest/scientific_drafts.py 与 Go 审核校验。
- 保留完整性要求，补上上传检查和人工语义裁决；删除约束不能解决无来源发布。
- 复用 RQ、Redis 与请求模型上下文，不增加基础设施；任务超时十分钟，模型单次读取九十秒，终态清理凭据。
- Go 保有审核事务，Python 提供只读核对准备，避免复制分类与批准逻辑。
- 源文本确定性复核与模型语义核对分别负责定位和支持程度。人工对疑点裁决，AI 不代表科学正确性保证。
- 模型调用复用现有 `backend.rag.llm.complete_json` 流式客户端；当前供应商的普通响应不可靠，直接假定返回 `.choices` 会失败。流式部分结果回调同时检查取消与总期限，不另建模型适配层。
- 上传核对结果落库时，必须 flush、重载后用数据库实际精度计算摘要。MySQL 的定点值与内存浮点值表示不同，直接散列写入前对象会导致内容未变也重复核对；统一十进制文本解决该问题。
- 管理员科学数据以正式详情为事实来源；审核快照只继续为既有分类回填服务。旧上传快照覆盖正式物性会把已经保存的多证据与编辑重新抹掉。
- 已完成但未应用的任务按用户、目标和内容版本在 Redis 短期缓存，预检查返回可复用的 job_id。只有任务结果且无数据库缓存时也能自动续提，不能丢掉任务身份。
- 页码是来源元数据，不靠模型补猜。新分段传播跨片段页码；旧论文片段缺页码时显示片段编号。原文唯一匹配可修复旧片段序号；文件不匹配、引句不存在、多个匹配或无来源文本分别解释。

## 用户反馈后的交互修正

用户明确要求证据选择由系统完成。原设计把手动原文候选暴露为默认选项，使已有 AI 原文的疑点也出现片段下拉框，混淆来源定位与科学裁决。取消该选择器及引句编辑，只读原文默认折叠；不展示内部文件、片段编号，缺页码诚实显示未提供页码。后台负责定位和关联，人工仅判断科学结论。

同时修复重新查找在无手动候选时复用旧疑点、没有创建任务的问题：显式重试跳过前端缓存短路，重新经三秒倒计时启动后台核对，不更改科学数据与权限约束。
