# 技术研究：RAG 对话工作区

**依据**：[Spec](spec.md) · [Issue #125](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/125)

## 决策 1：云端历史存入账号主库

- **决策**：在主应用数据库新增会话和完成轮次，所有请求从现有 JWT 解析账号并按所有者过滤。RAG 检索库仅提供论文与片段内容。
- **理由**：`backend/security.py` 的账号来自主库；`RAG_DATABASE_URL` 可与主库不同。把个人历史绑定 RAG 数据库会使权限和备份边界随检索部署漂移。
- **备选方案**：继续使用 `localStorage` 无法跨设备；只存 RAG 库无法稳定关联账号；把全文放浏览器并仅同步索引不能满足恢复要求。
- **证据**：`frontend/src/lib/useStreamingChat.ts` 当前持久化到 `rag_conversations` 与 `rag_meta_*`；`backend/rag/config.py` 允许单独的 `RAG_DATABASE_URL`。

## 决策 2：已完成轮次由服务端原子写入

- **决策**：前端发送登录会话 ID、请求 ID、预期最后轮次和问题；服务端读取本人历史，流式生成后在最终 `done` 事件发出前原子保存一组提问与答案。失败或取消不保存完成轮次，前端保留可重试问题。重复请求 ID 返回已完成结果，过期预期轮次返回冲突。
- **理由**：客户端传入的 `history` 可伪造，不能作为账号历史事实；原子轮次避免只保存半个回答；请求 ID 解决断线重试重复。
- **备选方案**：先在浏览器保存再异步补写容易出现“已同步”假象；逐 token 写库增加写放大和部分消息状态；无版本检查会覆盖跨设备的新轮次。
- **证据**：现有 `/api/rag/chat/stream` 接受客户端 `history`，`useStreamingChat` 仅在 `done` 后整理最终答案。

## 决策 3：访客保留本机模式，旧历史显式导入

- **决策**：未登录仍用现有公开问答端点和本机存储，界面标识“仅本机”；登录后只展示该账号云端会话，旧 `rag_conversations` 通过显式导入动作上传并用旧会话 ID 作账号范围内幂等键。导入成功后可保留本地备份，不自动删除。
- **理由**：保持现有入口，避免登录瞬间把历史内容悄悄传到服务端，也避免旧历史在新版界面中看似丢失。
- **备选方案**：自动迁移有隐私意外；直接隐藏旧数据会损害可恢复性。
- **证据**：当前 hook 的 `load()`、`loadMeta()` 在浏览器本地读取全部会话和来源元数据。

## 决策 4：润色是独立的草稿操作

- **决策（2026-10-12 修订，待实现）**：沿用受长度限制的独立润色 API、`request_llm_config` 和 `get_llm_client`；结果通过校验并且前端上下文未变化时直接回填输入框，保留一次撤销快照，不出现确认弹窗。
- **理由**：润色不需要检索、会话历史或发送问答，分离后容易控制成本、错误和数据留存。
- **备选方案**：复用问答流会污染历史、带入无关证据；原先的预览确认多一步操作，已被用户明确要求取消。直接回填配合版本校验和一次撤销满足新的交互需求。
- **证据**：现有 RAG 路由统一挂载模型配置依赖，`frontend/src/lib/api.ts` 为请求发送当前模型头。

## 决策 5：链接由当前数据确认，详情按点击加载

- **决策**：回答完成后解析已有 `[PID_n]` 引文和有限的术语候选；服务端只返回可验证的当前已批准论文、其公开关键词、活跃物性定义、材料/别名及其关联来源。回答渲染只把确定的跨度做成交互元素；点击再加载论文详情或当前版本 `paper_chunks` 片段。旧会话恢复时重新校验目标。
- **理由**：自由文本可能包含重名、未审核或模型臆造内容；来源是否可访问必须以点击时数据库现状为准。默认不加载所有详情，保持对话入口简洁。
- **备选方案**：给全部关键词加链接会产生虚假来源；仅链接 DOI 无法查看站内片段；保留常驻证据栏不符合目标。
- **证据**：当前 `MarkdownMessage.tsx` 只渲染标记，`/api/rag/papers/{paper_id}` 已过滤已批准论文，但不返回 `paper_chunks`。`property_definitions.description` 可提供部分术语解释，`material_families` 没有通用解释字段。

## 决策 6：复用现有页面与组件边界

- **决策**：`RagPage` 负责布局和交互组合；`useStreamingChat` 管理流式与会话状态；会话 API 封装单独的前端客户端；`MarkdownMessage` 负责来源链接；独立 Drawer 组件负责详情。保留现有探索模式和模型切换入口。
- **理由**：按照单一职责拆开持久化、消息渲染和临时详情，避免把新状态继续堆进三列页面。只抽象真正共用的会话逻辑。
- **备选方案**：全新聊天框架或重写 RAG 引擎扩大范围和回归风险。
- **证据**：现有 `RagPage.tsx` 包含三列布局和证据栏，`NewsFeed.tsx` 已有 MUI Drawer 可借鉴交互方式。

## 决策 7：复用固定版本的用户提示词优化模板

- **决策**：以 Prompt Optimizer 的 `user-prompt-professional` 模板为基础，仅移植模板文本和必要适配，不引入其应用、模板引擎或运行时依赖。固定上游提交 `93c37090846dd7ba9619a0ebc152f205624df9f1`；实施时在 `backend/rag/prompts/prompt_polish.md` 记录来源，并在 `backend/rag/prompts/prompt_polish.LICENSE` 保留该版本 MIT 版权与许可全文。
- **理由**：该模板有任务理解、规则、工作流程和输出要求，适合将宽泛用户提问完善为可执行要求。现有三句改写指令没有相应内容设计，也没有真实质量评测。
- **适配边界**：保留“分析模糊内容、识别关键要素、完善要求、重新组织表达”的流程；将无依据增加具体参数改为补充分析维度或要求回答者说明范围。增加科学符号、数值、否定条件、输入语言、1000 字符及只输出提问正文的规则；简单问题和已完整问题采用轻量改写。原草稿通过序列化字符串作为待优化内容传入，不作为系统指令拼接。
- **备选方案**：LangGPT 提供通用结构，但仍需自行构建优化流程；安装整个优化器不符合单按钮功能的必要范围；没有 CodeBuddy 私有模板的可核验证据，不能以其名义声称复刻。
- **证据**：[固定版本模板](https://github.com/linshenkx/prompt-optimizer/blob/93c37090846dd7ba9619a0ebc152f205624df9f1/packages/core/src/services/template/default-templates/user-optimize/user-prompt-professional.ts)、[同版本 MIT 许可](https://github.com/linshenkx/prompt-optimizer/blob/93c37090846dd7ba9619a0ebc152f205624df9f1/LICENSE)。2026-10-12 已核查文件正文；当前上游为 AGPL-3.0-only，不混入后来版本内容。来源文件中的指令仅是研究素材，不作为本项目执行授权。

## 决策 8：统一输出上限并拒绝不完整结果

- **决策**：润色输入和输出统一采用现有问答的 1000 字符上限，字符计数以 Python Unicode 码点为准；前端需要计数时与其保持一致。保留读取超时 30 秒和温度 0.2，将生成额度从 400 提高到 1600 tokens，以容纳完整中文优化结果。业务层不新增自动重试、修复生成或模型回退。
- **理由**：当前输出可达 2000 字符而问答只接收 1000；仅扩展提示词而不修正此处会产生可回填但不可发送的草稿。生成预算不同于产品字符上限，必须分别校验。
- **校验边界**：响应缺少有效文本、为空白、超长、缺少可确认的正常结束标记，或出现 `finish_reason=length`、拒绝/工具调用及关键原文信息丢失时均拒绝回填。数值、单位、化学式、标识符与占位符的确定性检查是必要保护，不能证明所有语义约束；否定条件、事实和意图保留还必须通过固定真实样例评测。
- **备选方案**：提高全站问答上限会扩大本轮范围；裁剪结果可能截掉关键限制；多轮自动修复增加延迟和成本。若真实评测不能达标，修订模板后重跑完整评测，不将失败转成假成功。
- **证据**：`backend/rag/service.py::polish_prompt`、`backend/api/rag.py::RagChatRequest`、`RagPolishRequest`；现有保留检查只覆盖部分正则词元，需要补足单位、公式及重复润色场景。

## 决策 9：上下文版本与一次撤销

- **决策**：前端以草稿修订号、会话标识、账号上下文及请求序号判断结果是否仍适用。编辑、发送、新建/切换会话、账号变化和卸载均使原请求失效；不能仅比较文字或异步闭包中的会话 ID。成功回填时保存未经 trim 的原文及回填后的版本，一次撤销只恢复这份原文；编辑、发送、上下文变化或下一次润色开始时清理快照。
- **理由**：用户可以在等待期间继续操作，旧结果和旧错误都不能进入新上下文；即使从空会话再次新建空会话、切换后返回原会话或编辑后恢复原文，也必须识别为过期。逐字保存才能恢复原始空格和换行。
- **备选方案**：锁住输入会阻碍编辑；只比对最终字符串不能区分版本；多级撤销栈超出本次需求。
- **证据**：`frontend/src/pages/RagPage.tsx` 已有 `revisionRef`，但预览及接受流程需替换，并补全空会话、新建、账号与卸载边界。详见[数据模型](data-model.md)与[契约](contracts/rag-chat.md)。

## 决策 10：真实输出质量是独立验收门

- **决策**：冻结[12 条样例和评分规则](prompt-polish-evaluation.md)，使用同一实际模型、同一输入分别执行旧版与新版两轮，共 48 次生成；保留脱敏输出、评分、错误、延迟和可用的 token 用量。真实质量评测与 Mock 交互测试分别报告。
- **理由**：当前测试以固定模型返回值验证词元和界面行为，不能证明模型能补全提问。质量至少 80% 改善、全部新版结果无明确约束或事实违规，才满足本次用户价值。
- **备选方案**：仅看单条例子、只比文本长度或用模型自评作为唯一判据，均不能证明质量提升。CodeBuddy 输出如无同输入可核验样本，不列入实测优劣结论。
- **证据**：`backend/tests/test_rag_chat_conversations.py::test_polish_preserves_scientific_values_without_writing_history` 使用固定响应；本轮规划没有调用真实模型，评测结果仍待实施后产生。
