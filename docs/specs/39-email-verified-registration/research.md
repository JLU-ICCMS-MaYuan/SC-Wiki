# 技术研究：邮箱验证注册

## 决策 1：认证只在 Go 实现

- **决策**：不挂载旧 Python `auth_routes`。
- **理由**：Nginx 已将 `/api/` 交给 Go，双实现会产生不同密码、审批和错误规则。
- **备选方案**：把认证转回 Python；拒绝，因为会扩大代理和会话兼容范围。
- **证据**：`goserver/main.go` 显式注册登录/注册，Python 路由未 include。

## 决策 2：Redis 保存短期挑战

- **决策**：Redis 保存验证码摘要、TTL、尝试次数和额度，MySQL只保存最终验证事实。
- **理由**：挑战天然短期，Redis 可原子过期和计数，避免继续使用明文数据库字段。
- **备选方案**：MySQL 保存验证码摘要；拒绝作为主方案，因为额度窗口和清理复杂度更高。

## 决策 3：发送失败关闭

- **决策**：SMTP 配置缺失、超时或发送失败均返回失败。
- **理由**：旧实现的假成功和日志验证码会造成无法完成的注册及凭证泄露。
- **备选方案**：开发环境打印验证码；仅允许显式测试邮件替身，不允许生产降级。

## 决策 4：验证响应直接登录

- **决策**：验证成功直接返回 token 和用户 DTO。
- **理由**：用户已提供注册密码，再次要求登录没有额外安全收益。
- **备选方案**：跳回登录页；不符合已确认体验。

## 决策 5：恢复现有功能并接入网易邮箱

- **决策**：继续使用 #39；Go 是唯一生产认证入口。采用网易 465 implicit TLS 和用户已有授权码，保留外部配置。
- **理由**：现状为显式停用验证，不能只填 SMTP 配置，也无需重复开发用户模型。
- **备选方案**：新建重复 Feature 或恢复 Python 认证，均扩大维护面。
- **证据**：`registerHandler` 直接标记已验证，现有 Overview 明确说明停用；#39 仍开放。旧 T001–T012 勾选不证明当前行为完成。

## 决策 6：可恢复的外部发送失败

- **决策**：保留未验证账号，通过正确密码登录恢复验证；发送成功后发布挑战，失败保持旧码，限制发送尝试并给出冷却时间。
- **理由**：数据库与邮件无法形成同一事务，避免假成功、覆盖凭据或邮件失败后无法继续注册。
- **备选方案**：邮件失败删除用户会增加并发删除风险；暂存所有注册资料需更改既有数据所有权，本次不采用。

## 决策 7：重发校验已有密码

重发携带本次注册或登录时已输入的密码，只保留在弹窗内存；未知邮箱使用等成本密码比较。这样 SMTP 真实失败信息只向持有正确凭据的用户返回，避免匿名重发泄漏账号状态。用户在推荐后要求继续，采用该方案；不引入额外短期凭据和存储。
