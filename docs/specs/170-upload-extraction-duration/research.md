# 技术研究

## 决策与证据
1. 在 `upload_contracts.apply_state_changes` 统一推进计时，`create_task` 初始化；理由是Worker、失败回调、取消、角色恢复及重试均经过此状态契约。Redis事务和 `persist_upload_state` 原样保存新增字段。拒绝使用 `updated_at`，它随访问/编辑变化。
2. 使用累计秒数与当前区间起点：角色确认暂停后回到队列，只有重新进入 extracting 才恢复。终态结算一次，重复更新不重复累计。拒绝简单结束减开始，不能排除人工等待。
3. 历史无计时记录保持缺失，只有明确重试创建新计时；不为已运行旧任务虚构起点，不查询日志或迁移历史数据。
4. 列表复用现有1秒刷新时钟，每3秒读取仍可能变化的任务状态；只读接口沿用权限。完成后停止轮询；并发读取只采用最后发起请求，防止旧响应覆盖终态。
5. 页面显示分秒（超过一小时仍累计分钟）；无运行起点且尚未开始显示“尚未开始”，错误字段显示“未记录”。计时由服务端拥有，客户端只计算当前区间显示值；不写入业务记录。

## 2026-11-09：token统计设计依据

用户已确认新增实际token记录与显示。本次只增加运行指标，不改变#170计时、#211终态、#224重试/恢复或科学提取算法。

1. 现有llm_calls.json仅在Worker退出时写入，且内存calls会在恢复时重建；不能作为跨暂停累计或中断完整性的权威。采用请求开始/结束即时写入现有任务状态，复用已有快照；保留原日志用途。
2. 用量统计放在实际SDK请求边界，位于JSON/严格科学结构验证之前，所以返回用量但结构无效的请求仍计消耗；缓存检查点不进入SDK边界，自然不重复计数。
3. 摘要走LangChain并返回usage_metadata，必须接入同一请求收集器；只改科学JSON入口会漏计这部分。
4. 使用ContextVar传递任务收集器，现有#224 copy_context将其传入请求线程。写入依赖update_state的既有执行代次检查，另核对run_id，隔离暂停后的旧执行与重试后的旧轮次。
5. 未结束、缺失或损坏回执在请求计数与有效计量数之间形成差额；不能用字符估算、完整0或只统计成功结果代替。上游缓存命中已经包含在回执中，不另加细项。
6. 任务私有请求表仅保存随机请求ID及计量状态，不保存提示词、密钥或模型响应。已有任务无统计记录保持缺失，明确重试后才创建新轮次，不做历史回填。

已查明自动谱backend/spectra/vision.py与原生PDF backend/ingest/native_pdf.py绕过统一JSON入口，T010/T014同时覆盖这两处实际SDK边界；Responses实际用量使用input_tokens/output_tokens。仅补全已确认的本轮自动解析消耗范围，不修改科学输出规则。
