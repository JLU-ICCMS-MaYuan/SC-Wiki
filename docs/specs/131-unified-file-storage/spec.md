# SC-Wiki 单机起步、逐步拆分三组服务

## 目标与部署演进

从第一次部署就划分“网站应用、数据存储、解析计算”三组服务，初期全部运行在一台云机器，后续按负载逐步迁出。三种部署形态使用同一套业务代码，通过部署配置选择服务位置。

| 阶段 | 机器 A | 机器 B | 机器 C |
|---|---|---|---|
| 初期 | 网站应用 + 数据存储 + 解析计算 | — | — |
| 数据增长后 | 网站应用 + 解析计算 | 数据存储 | — |
| 解析负载增长后 | 网站应用 | 数据存储 | 解析计算 |

同机时使用容器网络，跨机后使用同云私网。允许维护窗口迁移，不要求零停机。

本次完整规划三组服务的跨机能力，包括对象存储；实际部署仍从一台机器开始。本地原生开发保留现有启动方式。

## 三组服务的职责

| 服务组 | 包含内容 | 边界 |
|---|---|---|
| 网站应用 | Nginx/网页、Go API、Python API、登录、检索、审核、RAG 对话、资讯调度与 Worker | 接收用户请求、鉴权、提交解析任务、展示结果 |
| 数据存储 | MySQL、Redis、Qdrant、Neo4j、S3 兼容对象存储 | 保存业务数据、队列与草稿、向量、图谱和文件 |
| 解析计算 | 上传解析 Worker、证据核对任务、GROBID、PDF/OCR 解析依赖 | 消费任务、读取文件、执行解析与提取、保存产物和任务状态 |

对象存储初期同机自托管，归入数据组；后续可随数据组迁移。接入采用标准 S3 接口，不绑定某家云厂商。

**这替代此前“附件长期保留在应用侧本地目录”的方案。** PDF、结构附件、解析产物、审核证据和头像进入统一存储；应用与计算机器仅保留临时文件、可重建缓存和运行日志。

## 核心设计约束

**文件与任务**

- 存储引用使用稳定对象键，不把某台机器的绝对路径作为跨进程契约。
- API 保留现有鉴权和文件访问入口；首版由 API 代理上传、下载，不新增浏览器直连对象存储流程。
- Worker 按需下载到任务临时目录，上传持久产物成功后才发布完成状态。
- 保留 Redis/RQ 队列；任务重试不能重复创建正式记录、覆盖其他版本产物或误删被引用文件。
- 历史文件采用可校验、可续跑的一次性迁移；保留源文件直至验收完成。生产对象存储模式不静默回退读取旧本地目录。
- 本地开发通过本地文件存储实现保持无 Docker 使用方式，不要求日常开发启动对象存储。

**编排与连接**

- 三组使用独立 Compose 项目；提供单机组合启动入口，复用服务定义。
- 应用或解析组的停止、升级不操作数据服务和数据卷。
- MySQL、Redis、Qdrant、Neo4j、对象存储及 GROBID 地址均可配置；跨组启动检查使用真实连接，不依赖跨项目 `depends_on`。
- 补齐 Go Redis 认证及所有 Qdrant 调用入口的统一配置。数据服务仅向必要的私网来源开放。
- 区分进程存活、依赖就绪和任务执行成功；连接故障有超时、脱敏诊断和明确失败状态。
- 数据库 schema 迁移作为显式维护步骤，与应用版本配套；正常启动不自动修改远程 schema。

**迁移与恢复**

- 第一次拆分迁移数据组，第二次拆分只迁移解析运行环境与配置；业务文件已经在对象存储，无需再从网站机器搬到解析机器。
- 两次迁移都包含停止接收相关任务、排空运行任务、备份、校验、切换和恢复访问。
- 保留旧环境用于切换前回退；新环境恢复写入后，不允许直接切回旧快照而丢弃新增数据。
- 本次不引入 Kubernetes、数据库集群、自动扩缩容或跨云公网部署。

## 背景与目标

API、上传 Worker 和证据核对当前通过本机目录共享文件。将计算节点移到其他机器后，数据库仍可连接，但文件路径不再可达。本功能让业务文件不依赖应用或计算机器的位置，同时保持本地原生开发体验。

## 用户场景与验收

### US1：在统一存储中使用业务文件（P1）

用户照常上传论文、结构附件、人工证据和头像，查看解析结果与审核证据，无需知道文件存放在哪台机器。

**优先级理由**：这是三组服务能跨机器使用同一份业务文件的前提。

**独立验收**：使用真实对象存储运行上传、读取、替换和清理流程；拒绝直接访问应用持久目录后仍可用。

1. 假如用户上传合法文件，当上传成功并进入后续任务时，那么文件已完整保存且内容可核验。
2. 假如其他用户无权读取草稿或证据，当其请求文件时，那么沿用现有权限拒绝访问，不泄露存储位置或凭据。
3. 假如文件仍被正式论文或返修引用，当清理上传任务时，那么仍可从授权入口读取文件。

### US2：迁移已有文件且可恢复（P1）

管理员在维护窗口将历史文件与引用迁至统一存储，不丢失已有论文、草稿、证据和头像。

**优先级理由**：现有数据不能因启用新存储而不可读；生产切换须与 US1 一起完成。

**独立验收**：对包含正式记录、持久草稿、返修及临时任务的样本迁移，中断重跑后逐项校验。

1. 假如扫描发现文件缺失、越界或引用不支持，当管理员预检时，那么阻断应用切换并输出定位信息。
2. 假如对象复制完成但引用更新中断，当继续同一迁移时，那么按清单续跑，不重复覆盖冲突内容。
3. 假如目标尚未开放新写入，当需要回退时，那么能恢复旧引用和原文件访问。

### US3：保留本地开发与运维边界（P2）

开发者仍可无 Docker 启动本地服务，使用文件系统实现；生产对象存储故障则报告不可用，不读取意外的旧本地副本。

**优先级理由**：本地兼容和生产故障边界须随 US1 验证，但不改变优先交付的文件主链路。

**独立验收**：原生启动、文件操作与冻结恢复回归；对象存储停机时确认无本地兜底成功。

### 边界与异常场景

- 存储认证失败、内容缺失、摘要不一致或上传中断时，不把文件引用标记为有效。
- 人工证据和候选附件有从实体 ID/元数据派生的路径，迁移清单须完整枚举；未知持久文件阻断切换。
- 迁移切换前可从保留的源文件回退；新环境开放写入后不得直接回退旧快照。

## 需求

- **FR-001**：所有持久业务文件必须通过统一访问边界读写，包括原始附件、解析与审核产物、人工证据、头像；数据库内结构正文仍以数据库为事实来源。
- **FR-002**：跨进程引用必须是稳定文件标识及完整性信息，不包含节点绝对路径、存储凭据或可变临时位置。
- **FR-003**：保留现有 API、权限、文件格式及大小限制；先鉴权再读取，上传成功前完成内容校验与持久化。
- **FR-004**：文件写入失败、部分写入或内容冲突不得发布有效引用或伪报成功。
- **FR-005**：计算所需本地文件必须由持久引用按需取得；本地缓存丢失不得造成持久数据丢失。
- **FR-006**：删除必须遵循文件所有权、论文版本和引用关系；清理可重试，不能删除仍被引用的对象。
- **FR-007**：迁移必须先建立文件与引用清单，覆盖附件表、头像、持久草稿、返修、审核/证据快照和 Redis 临时任务中的已登记字段。
- **FR-008**：迁移必须支持预检、校验、续跑和切换前回退；保留源文件，不自动清除旧数据。
- **FR-009**：生产存储模式不静默读取旧目录；本地开发保留文件系统实现及现有原生命令行为。
- **FR-010**：错误、日志、备份和迁移报告不得泄露访问密钥、临时模型凭据；未知引用和不一致必须明确阻断。

### 关键实体

- **业务文件引用**：由现有论文、任务、证据、返修或用户记录持有，包含可核验的稳定文件身份；不授予额外访问权限。
- **迁移清单**：逐项追踪已有文件、显式引用及按实体身份派生的路径，与备份和切换阶段关联。
- **可重建临时文件**：计算节点从持久文件按需取得，不能成为唯一业务副本。

## 成功标准

- **SC-001**：US1 中每类文件的上传、读取、替换、清理及越权场景均在真实 S3 后端通过。
- **SC-002**：迁移清单中全部有效引用可解析，文件大小与 SHA-256 全部一致；存在未解释缺失时不得切换。
- **SC-003**：同一迁移中断后重复执行不产生内容冲突、重复业务记录或丢失源文件；切换前回退通过。
- **SC-004**：移除应用/Worker 历史目录和缓存后，已迁移业务文件仍可读取；对象存储故障不会伪报成功。
- **SC-005**：本地文件后端、原生启动和冻结恢复回归通过，正常本地工作不新增 Docker/S3 前置条件。

## 假设与依赖

对象存储初期自托管并与其他服务同机，之后归数据组。首版 API 代理上传下载，桶保持私有。本地与生产使用相同文件业务接口、不同存储实现。
