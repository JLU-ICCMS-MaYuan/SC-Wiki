# Feature 规格：只读详情页与校对表单一致

**GitHub Issue**：[#59](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/59)

**创建日期**：2026-08-27

**状态**：草稿

## 背景与目标

只读「论文详情」页与校对页「AI 临时表单」是两套独立实现的表单，字段集、字段语义与展示形态都不一致。用户的诉求很直接：**提交的东西和审核的东西必须保持一致**。

当前的不一致有三种表现，用户体验上都指向「系统在骗我」：

- 详情页出现用户从未填写过的字段（最小值/最大值），而真正有值的字段反而不显示；
- 详情页缺失校对页的整套分类字段（晶系、空间群、超导类型、维度、压强、Tc），用户无法复查自己确认过的分类；
- 同一段文本在两个页面用不同名字出现（校对页叫「分类理由」，详情页叫「研究理由」），用户以为系统凭空生成了内容。

本 Feature 以校对页材料状态卡片为唯一基准，重写详情页的字段集与展示形态，并纠正字段语义错配。

Bug 分类：**原设计缺陷**。详情页与校对页从一开始就是各自实现，没有共同的字段集基准；[#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57) 已让后端能把完整数据读出来，但前端仍按旧字段假设渲染。

## 用户场景与验收

### 用户故事 1：详情页展示的字段与提交时确认过的一致（优先级：P1）

**优先级理由**：这是 Issue 的核心诉求。用户在校对页逐项确认过分类，却在详情页看不到，等于无法复查自己的提交；同时详情页显示的 min/max 是用户从未填写的字段，比缺失更容易让人怀疑数据被篡改。

**独立验收**：打开一篇已提交论文的详情页，其材料状态展示的字段与校对页材料状态卡片逐项对应，既不缺项，也没有校对页不存在的输入项。

**验收场景**：

1. **假如** 某材料状态在提交时确认了晶系、空间群符号与国际群号，**当** 打开详情页，**那么** 这三项均可见。
2. **假如** 某材料状态确认了超导类型、材料维度、材料家族与元素种类数，**当** 打开详情页，**那么** 这四项均可见。
3. **假如** 某材料状态的压强是单臂区间（只有下限，原文 `above 200 GPa`），**当** 打开详情页，**那么** 显示原文表述与下限，不显示凭空补造的上限。
4. **假如** 某材料状态有 Tc 结果（含 Tc 数值、Tc 方法、λ、ωlog、μ*），**当** 打开详情页，**那么** 这些值按校对页的组织方式可见。
5. **假如** 某物性在库中只有原始值与解析值而没有数值范围，**当** 打开详情页，**那么** 显示名称、原始值/解析值与单位，**不显示**「最小值」「最大值」两个空字段。

### 用户故事 2：字段名称与内容语义对应（优先级：P1）

**优先级理由**：同名不同义比字段缺失更严重——用户会认为系统自动生成了他没写过的内容，从而不信任整个审核链路。

**独立验收**：详情页中每个带标签的字段，其标签与内容的实际来源一致；用户在校对页填写的「分类理由」在详情页也叫「分类理由」。

**验收场景**：

1. **假如** 用户在校对页只填写了「分类理由」，**当** 打开详情页，**那么** 该文本以「分类理由」为标签显示，不以「研究理由」为标签。
2. **假如** 用户从未填写过「研究理由」，**当** 打开详情页，**那么** 不出现一个标为「研究理由」却有内容的字段。
3. **假如** 研究方法是多项条目，**当** 打开详情页，**那么** 以可读列表（每行一项）展示，不出现 `["..."]` 形式的原始 JSON 文本。

### 用户故事 3：结构预览与校对页同源（优先级：P2）

**优先级理由**：结构预览的数据源已由 [#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57) 改为 `structure_models` 并随详情接口返回，本故事只需让前端按该来源渲染并保证空态可读。当前全库无结构模型记录，用户实际感知不到差异，故排在 P2。

**独立验收**：详情页的结构预览读取材料状态下的结构数据；无结构数据时显示明确空态而非报错或空白。

**验收场景**：

1. **假如** 某材料状态有结构数据，**当** 打开详情页，**那么** 该结构在所属材料状态内渲染 3D 预览。
2. **假如** 论文没有任何结构数据，**当** 打开详情页，**那么** 显示明确的空态说明，不显示破损的预览容器。

### 边界与异常场景

- 论文没有材料状态时，展示明确空态，不渲染空白卡片骨架。
- 材料状态的可选字段在库中为 NULL 时不显示该项，或显示为「未填写」，但不显示 `null`、`undefined` 等原始值。
- 同一材料状态有多条计算上下文时（含数值全为 NULL 的记录），全部展示，不由前端挑选「哪条才算有效」。
- 物性的原始值与解析值不一致时（如原文 `0` 而解析值 200），两者都可见，不由前端裁决谁正确。
- 详情页是只读的：不得出现无法保存的编辑态控件。
- 研究方法为空或不是列表时，不渲染空列表容器，也不抛错。

## 需求

### 功能需求

- **FR-001**：详情页的材料状态必须展示晶系、报告空间群符号与国际群号、超导类型、材料维度、材料家族与元素种类数。
- **FR-002**：详情页的材料状态必须展示压强的原文表述与可用的边界值；单臂区间不得补造缺失的一侧。
- **FR-003**：详情页必须在所属材料状态内展示 Tc 结果及其关联的计算上下文数值（λ、ωlog、μ*、Tc 数值与 Tc 方法）。
- **FR-004**：详情页的物性必须按名称、原始值、解析值与单位展示，不得展示校对页不存在的「最小值/最大值」输入项。
- **FR-005**：详情页展示的字段集不得包含校对页材料状态卡片中不存在的字段。
- **FR-006**：用户在校对页填写的分类理由，在详情页必须以「分类理由」呈现，不得以「研究理由」呈现。
- **FR-007**：详情页不得展示一个标为「研究理由」却承载分类理由内容的字段。
- **FR-008**：研究方法必须以可读列表展示，不得暴露 JSON 数组原文。
- **FR-009**：结构预览必须取自材料状态下的结构数据；无结构数据时显示明确空态。
- **FR-010**：详情页不得保留无法持久化的编辑态控件与其对应的增删改函数。
- **FR-011**：既有行为不得回归，包括详情页的权限提示分流、按合法来源返回与「我的论文」入口、以及 [#56](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/56) 确立的地址驱动行为；原固定返回上传列表的约束由 [#178 后续需求](../178-search-results-navigation/spec.md) 取代，本地实现与验证见[＃178验收记录](../178-search-results-navigation/validation.md)。

### 关键实体

- **材料状态**：详情页展示的组织单元，与校对页的材料状态卡片一一对应。其下挂载 Tc 结果、计算上下文、结构与普通物性。
- **Tc 结果**：临界温度结果，含结果类型、Tc 判定方法、数值与原文表述。
- **计算上下文**：承载 λ、μ*、ωlog 与计算方法，隶属材料状态。
- **普通物性**：Tc 之外的性质，字段集为名称、原始值、解析值、单位与条件说明。
- **分类理由**：用户在校对页确认分类时填写的说明文本，与论文层面的「研究理由」是不同语义。

## 成功标准

- **SC-001**：详情页展示的材料状态字段集与校对页材料状态卡片逐项一致，无缺项、无多余项。
- **SC-002**：paper 4 的 `name_raw='thermodynamic stability'`、解析值 200、单位 `meV/atom`、`pressure_raw='above 200 GPa'`、空间群 `Fm-3m`/225、Tc=274 K、λ=2.56、μ*=0.1 在详情页全部可见。
- **SC-003**：详情页不出现「最小值」「最大值」空字段，也不出现标为「研究理由」的分类理由文本。
- **SC-004**：研究方法以可读列表展示，页面文本中不含 `["` 或 `"]` 形式的 JSON 片段。
- **SC-005**：无结构数据的论文详情页显示空态说明且不报错；`PaperEditView` 中不再存在无法保存的编辑控件与死函数。
- **SC-006**：前端既有测试与新增测试全部通过，`tsc --noEmit` 无输出。

## 假设与依赖

- 依赖 [#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57)（已完成、已关闭）：详情接口已按材料状态嵌套返回 `tc_results`、`calculation_contexts`、`structures`，材料状态已含压强区间、空间群、温度、磁场、`state_kind`、`note`，物性名已取自规范定义。本 Feature 只做前端展示，不再改后端读取契约。
- 校对页 `UploadTaskEditor` 的材料状态卡片是字段集的唯一基准（已核实其含材料、材料家族、元素种类数、维度、类型标签、压强、晶系、空间群符号与群号、超导类型、Tc 及 λ/ωlog/μ*）。
- 研究方法在库中本就是英文术语列表，不存在中译英丢失（已核实草稿与库内两端一致）；用户感知的「提交中文、审核英文」源于展示形态差异（校对页每行一项 vs 详情页 JSON 原文）。
- 当前全库 `structure_models` 为 0 行，结构预览只能验证空态；有结构数据的渲染路径需待有真实数据后核验。
- `papers.rationale` 列当前存储的是 `classification_reason` 的内容（后端 `rationale=draft.get("classification_reason") or paper_data.get("rationale")`）。本 Feature 按「该列承载分类理由」如实呈现，不改写入侧。

## 范围外事项

- 后端读取契约与数据模型：已由 [#57](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/57) 完成。
- 详情页入口与路由可达性：已由 [#56](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/56) 完成。
- 以 `UploadTaskEditor` 的 `readOnly` 模式替代 `PaperEditView`：经评估不采用，理由见澄清记录。
- 写入侧的 `rationale` 与 `classification_reason` 字段分离（是否为 `rationale` 增设独立列、是否在校对页增加「研究理由」输入）：属数据模型与采集流程变更，需独立需求。
- 物性原始值与解析值不一致的历史数据修正（paper 4 `value_raw='0'` 而解析值 200）：属写入侧问题，本 Feature 只如实呈现两者。
- 管理员审核页的表单一致性：本 Feature 只处理用户侧只读详情页。

## 澄清记录

### 2026-08-27

- 问：#59 修复范围第 5 项提出「以 `UploadTaskEditor` 的 `readOnly` 模式承载详情页，替代 `PaperEditView`」。核查发现 `readOnly` 模式已成熟、draft 字段与 #57 新增的详情响应高度重合，但存在三处形态差异（详情响应的 `calculation_contexts`/`structures` 是数组而 draft 是单数 `calculation_context`/`structure`；draft 物性含 `pressure_gpa`/`temperature_k` 而这些概念已归属材料状态）。选哪条路线？→ 答：改造 `PaperEditView`，对齐字段集与排版。理由：复用 readOnly 需要「已提交论文 → draft」适配层，而数组→单数必须人为定丢弃或合并规则（paper 4 即有 2 条计算上下文，其中 1 条全为 NULL），存在丢数据风险；改造 `PaperEditView` 改动可控、无需适配层，且能按数组完整展示计算上下文与结构。代价是仍为两套代码、未来仍可能漂移，由 SC-001 的字段集一致性测试约束。
- 问：`PaperEditView` 的死代码清理是否在本 Feature 完成？→ 答：是。#57 已将其移交本 Feature，且本 Feature 既然重写该组件的字段集与排版，一并清理不构成重复劳动。据此设 FR-010 与 SC-005。


## 2026-10-29：检索与导航后续需求

关联 [Issue #178](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/178) 与[新Spec](../178-search-results-navigation/spec.md)。

原 FR-011 中的“返回上传列表”作为历史验收要求保留记录，2026-10-29用户已明确取消固定上传返回。当前有效后续需求改为按合法来源返回，搜索来源恢复检索条件／展示方式／页码；权限分流、只读字段、可寻址能力和其他表单合同不因此改变。旧Quickstart中的返回上传入口为历史验收，本次功能实现前不得声称已变更。
