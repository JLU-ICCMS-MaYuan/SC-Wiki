# 解析后表单到底怎样核对

这份说明针对当前实现，修改建议单独标记。最新逐项计数在[字段数据](assets/field-audit.json)，覆盖447个核对单元与518个可编辑入口；[逐项清单](field-catalog.md)及[输入入口CSV](assets/editable-fields.csv)可定位每一项。

## 先区分三个动作

| 动作 | 现在具体做什么 | 是否请求大模型 |
| --- | --- | --- |
| 刷新核对状态preflight | 构造当前快照、读取历史、检查旧证据/规则、组装状态；还读PDF文本层/页码与人工记录基线 | 否，本轮实测0次 |
| 保存人工记录或点击完成 | 保存草稿→preflight→保存说明或决定；可能等待已有请求，但自身不启动模型 | 否 |
| 首次页面自动核对／让系统重新查找／管理员全量核对 | 先preflight，再按缓存/状态/请求范围创建或复用后台任务，任务可能调用模型 | 可能；缓存命中可能0，实际请求数依窗口/重试变化 |

“不是LLM”不等于“不做核对”。程序也会反复验证旧结论、扫描引句。页面打开时另有自动任务，不能把它和点击完成串成同一次模型调用。

## 按用途归成8类，而不是8个独立引擎

| 类别 | 执行者与具体内容 | 例子 | 保存时是否需要 |
| --- | --- | --- | --- |
| 1. 格式与领域约束 | 程序：类型、空值、枚举、范围、单位/数值合同 | 文本N(EF)不用的数值槽可空；不能把布尔当数值 | 改值要做；未改值不应重复全表做 |
| 2. 当前版本与依赖 | 程序：值、材料/相、软件/阶段、来源/规则版本是否变了 | Tc变了不使同组网格失效；来源换了要判断 | 保留轻量、局部并发/版本检查 |
| 3. 原文真实性与位置 | 程序：引句是否存在、是否唯一、文件/PDF页码/来源是否可读；不是判断论文本身科学正确 | 标题首页定位，SSCHA声明段落定位 | 首次或相关来源变了要做；同版本重复全文扫描待删减 |
| 4. 确定性推导 | 程序：化学式元素种类数、空间群号/晶系、明确单位转换 | P6/mmm → 191 → 六方晶系 | 相关输入改变才重算，无需LLM |
| 5. 模型科学与语义判断 | LLM：数值是否对应原表、归纳/分类、局部例外、阶段与流程关系 | 超导类型、主要发现、Tc原表归属 | 保存动作不触发；首次/显式重核等单列审查 |
| 6. 已确认条件/适用范围规则 | 程序校验模型给出的结构化依据：值、单位、软件、阶段、材料/物相、覆盖和例外；结果归属另检查 | QE参数不借VASP；采样/插值分开；Tc归属不能反向使旧条件失效 | 相关输入/来源/规则变时；当前版本凭证有效就复用 |
| 7. 历史恢复 | 程序：当前版本无合适结论时，看旧claim与原文能否在已知兼容边界重验 | #144处理v1→v2内部表示变化 | 应只在确需恢复时发生，不应每次遍历整篇 |
| 8. 人工说明与批准 | 人写理由/补来源，程序核对权限、版本绑定、记录是否完整 | 人工修改记录、管理员说明、最终批准 | 保存实际变更/新决定；不伪造人工身份 |

第2、7、8类主要是状态与审计管理，不是又独立审读了一次论文。第6类中的“共用关联”和“规则凭证”当前还有不同代码入口，次数分别列，不把它们说成新的科学方法。

## 为什么读取历史、为什么再验旧证据

有三个原始用途：显示人工/AI修改过程；当当前版本缺少结果时恢复旧记录；保证旧通过不能覆盖新冲突。这些用途本身有必要。

过度工作发生在调用范围和频率：ordered_check_rows按整篇target读取所有历史大JSON；load_results挑当前版本并对条件历史调用effective_result/recover；即使只保存一个条件，save_draft仍调用整篇load_results。又在public_snapshot→checked_result中对刚恢复的凭证和来源再检查一遍。

旧证据重验原本是防止“旧hash换新hash就强行通过”，尤其是#144的已知版本恢复。当前实现没有把“已经在当前版本验证过”的结果与“本次需要再次恢复”充分分开，所以每次读取又做一轮。建议是保留历史、正确失效和必要恢复，移除同版本的重复全量工作；不是删历史或无条件接受旧证据。

## 两条保存链，修改和未修改目前都会走

### 点击完成

1. 刷新/等待本地待保存理由队列。
2. 调用saveCurrent→UploadTaskEditor.saveDraft(false,false)。函数没有“未修改直接返回”短路，仍校验全草稿并PUT整篇草稿。
3. restore→POST preflight。该次实测：构造3次上传快照、加载2次历史结果、进行2轮PDF当前来源校正、1轮人工修改完整性、1次公开状态组装。
4. 对activeGroup每个项目顺序POST proposals。后台再次构造整篇快照，rows_for读取整篇历史并加锁；条件字段还执行整篇load_results，之后才写本项决定。
5. 完成后关闭侧栏；期间manual/history等效果可能另发读取请求，不能把上面主路径请求数冒充整次点击的恒定次数。

### 保存人工修改记录

1. prepareManual先saveCurrent：即使值没变也保存整篇。
2. restore再preflight。
3. PUT manual字段说明。_manual_snapshots又调用snapshot_for，读取整篇结果/PDF；它取得cached却不使用，再从AI初始草稿构造一份baseline来判断修改。
4. 附件每个再POST files，入口也会构造快照/基线；此处次数受附件数影响。

源码：frontend/src/components/EvidenceWorkflow.tsx的accept、prepareManual、restore；UploadTaskEditor.tsx的saveDraft；ManualEvidenceSection.tsx的save；backend/api/evidence.py的preflight、_manual_snapshots、proposal_operation；backend/ingest/evidence_proposals.py的save_draft。

## 一次preflight的真实计数

实测提交/快照/时间见field-audit.json。2026-10-21，未插桩的一次处理11.661秒，输出27.79 MiB；另一次包裹函数计数，版本一致。此前12.285秒是另一次测量，不能当固定延迟或性能改进。

| 观察项 | 次数 | 含义 |
| --- | ---: | --- |
| 构造上传快照 | 3 | 当前2次+人工比较基线1次，不能称为3次LLM核对 |
| 加载历史核对结果 | 2 | 每次按整篇读取；1699历史行约51.42 MiB |
| 历史恢复入口 | 544 | 包含失败/提前返回，不等于544次成功恢复 |
| 条件依据验证 | 651 | validate_assessment实际调用；条件/历史不同次数不同 |
| 原文片段定位 | 4618 | 多条证据/多种入口，嵌套于上述检查，不可相加为审核总数 |
| 当前状态组装检查 | 423 | 447单元中已有结果的423项进入checked_result；其他项直接未核对 |
| 关联依据检查 | 290 | checked_review调用，不等于290个不同字段 |
| 大模型请求 | 0 | 只读preflight代码轨迹，未启动任务 |

例子：标题和作者各额外2次PDF首页核验，标题/作者/主要发现各1次当前状态检查、1次片段定位；超导类型1次状态检查、2次片段定位。250 GPa SSCHA软件4次历史恢复入口、5次条件依据验证、36次片段定位、2次关联依据检查、1次状态检查。200 GPa同名字段是4/3/21/2/1；同名字段不应假设次数相同。

## 次数口径与覆盖限制

- 这是解析后当前草稿的一次preflight；不是首次PDF提取总次数、历次AI调用总次数，也不是整个“完成”链的总数。
- 修改后次数依所改字段、依赖、历史、窗口和缓存变化。当前未逐项修改447项，因此该栏明确“未实测”，不能填与未修改相同的数字。
- 每个字段列status_check等入口数；rule_entry、result_scope_entry有提前返回，不能据此说所有字段都做了一次SSCHA判定。
- 没有落在record上下文内的定位调用保留在unattributed_counts，不能随意平均分给字段；PDF/派生遍历为批处理，内部逐键分支未伪造次数。
- 普通物性整条核对与预测Tc拆成子项是当前真实差异。当前来源中的空字段、派生字段也保留，不能仅统计红框。
- 结构文件内每个原子、内部追溯JSON每个元数据不是表单输入框；清单以服务端editable_fields及审核单元为边界。固定value_kind/方法身份等在主表单可控但非proposals可编辑的键另见字段族表，不能声称518即全站所有HTML控件。
- 新建任务会把多个记录分批、按来源窗口检查；当前每窗最多120000字符，含条件的记录批最多12项、其他最多20项。同一字段通常参与每来源窗一次，纠正/传输重试可能增加请求；这是代码公式，未执行本轮LLM测量，不能写成固定1次或2次。

## 按字段讨论的起点（建议，尚未全部采纳）

| 字段族 | 未修改且凭证有效 | 修改后建议 | 需要用户决定 |
| --- | --- | --- | --- |
| 标题、作者、期刊、DOI等 | 不写科学值、不全量刷新，复用当前结果 | 校验格式及当前字段来源；保留人工更正 | 名称修正是否只留人工理由，无需LLM |
| 超导类型、理论分类 | 同上 | 枚举合法性；分类科学含义按原文/人工理由判断 | 改分类时是否必须再次请求LLM |
| 主要发现、摘要、总结等 | 同上 | 保存文本与理由，不因“这是归纳”自动启动全文任务 | 哪些归纳字段需要用户显式重核 |
| 材料名、物相、压力、近似 | 同上 | 当前值格式与真实依赖失效；派生项按规则重算 | 哪些上下文影响哪些子项 |
| Tc、μ*、λ、ωlog | 同上 | 数字/配对/原表流程归属，只作用相应结果 | 数值改动是人工更正还是待AI验证 |
| 软件、网格、截断能等 | 同上 | 软件/阶段/用途/范围真实改变才重核 | 继续沿用#139/#144已确认科学边界 |
| N(EF)等普通物性 | 同上 | 名称、值、单位分别判断变更，但旧实现共享单元 | 名称修改是否应触发数值科学核对 |
| 结构资料 | 同上 | 文件语法/结构身份及真实来源检查，独立于普通文本 | 用户提交结构与论文报告如何分工 |

这些是待讨论的删减候选，不把全部建议写成已实现规则。逐项审查从标题开始：未修改直接复用；只改错字保留人工理由，是否不调用LLM？


## 红框不是修改历史

用户补充询问的所有当前标红入口、原因与例外见[red-marking.md](red-marking.md)。来源待处理与输入错误是独立逻辑；未修改也可红，修改过但有效处理后可不红。不能把保存错误条、人工说明缺口或模型运行状态直接等同字段红框。
