# 实施计划：多文件正文自动识别与统一解析来源

**Issue**：[#135](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/135)；**Spec**：[spec.md](spec.md)

## 摘要

保留现有上传 API 的声明角色作为历史输入；提取文本后由纯规则角色评估器给出有效角色。唯一高置信主文自动生效，其他情况在分段 LLM 前暂停。统一来源清单供全部生成与核对组件读取。

## 技术上下文与质量门

- Python FastAPI/RQ/Redis 保存任务与文本，React 上传列表可编辑角色；MySQL 只保存正式论文及已核对草稿。
- #26 清单锁定规则由本 Feature 的受限角色决策替代；文件 bytes、file_id 和 SHA-256 不变。
- #114 解析器选择保持原样；评估器消费解析后的首页与章节文本，不依赖外部 LLM。
- 角色决策必须在引文解析和分段 LLM 前完成；任何未确认主文不得进入模型输入。

## 数据流

1. 接收声明清单并上传文件。逐文件提取文本、保存哈希和缓存，不再在角色判断前运行主文引文解析。
2. `document_roles` 评估各文本的正负信号：文章式标题/作者/摘要/DOI/引言，SI 名称/标题/S 编号图表等。只有唯一主文且其余文本可区分时自动设置有效角色；不使用首文件兜底。
3. 歧义时写入待确认状态和逐文件理由，前端展示候选并调用版本化角色确认接口。确认后从已提取文本继续分段与汇总，避免重新上传或重复提取。
4. 将有效文件清单交给统一来源读取器；引文、研究驱动力、关键词、理论子类型、材料家族与核对共享 `file_id/role/source_hash`。任务来源变更使旧核对结果过期。
5. 只针对未提交旧草稿由 #120 负责版本保护重算，不改已提交 Paper。

## 需求与验证映射

| 需求 | 实现职责 | 验证 |
| --- | --- | --- |
| FR-001～002 | 纯角色评估器与 Worker 插入点 | SI 先上传、正文先上传、手动错选 |
| FR-003 | 任务状态、确认接口、上传 UI | 歧义暂停、鉴权、版本、恢复 |
| FR-004～005 | 统一来源读取与缓存失效 | 所有字段同源、单文件兼容、幂等 |

## 必要复杂度

待确认状态和角色版本是必要的：#26 清单在上传后锁定，不能靠 UI 改值使 Worker 已消费的主文身份自动改变。必须把文件原声明和最终有效角色分开，并在恢复时保护并发。
