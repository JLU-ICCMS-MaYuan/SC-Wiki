# Feature 规格：修复论文详情页整页白屏（JSON 文本列字段被当数组消费）

**GitHub Issue**：[#64](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/64)

**创建日期**：2026-08-31

**状态**：已落地

## 背景与目标

科学字段右侧栏功能设计、原话及历史已迁移至 [#221](../221-scientific-field-sidebar/spec.md)，本处不再独立维护。

`PaperDetailPage` 已按 Issue #56、#57 的设计提供了 403/404/400/其他异常四路分流提示，但一条都没显示。原因是异常并非出在数据获取阶段，而是出在下游展示组件 `PaperEditView` 的渲染期：`keywords_tags` 从后端返回的是 JSON 字符串，代码却对它调用 `.map()`。React 对未捕获的渲染异常会卸载整棵组件树，而本项目没有 ErrorBoundary，于是一个叶子组件的类型错误换来整站空白。

本 Feature 修复该崩溃，并把回归测试的 fixture 校正到后端真实返回形态。

**业务价值**：
- 可用性恢复：正常提交流程产出的论文，其详情页当前 100% 不可访问
- 契约一致：让前端消费方式与后端实际返回的字段形态对齐，而不是与理想形态对齐
- 测试可信度：fixture 偏离契约会让全绿的测试掩盖真实故障，本次一并纠正

## 用户场景与验收

### 用户故事 1：上传者查看自己刚提交的论文（优先级：P1）

普通用户提交论文后，从「我的论文」列表或直接输入地址进入 `/papers/:id`，希望看到该论文的只读详情。

**优先级理由**：这是 Issue #56 已交付能力的完全回退，当前故障率 100%（只要 AI 抽取产出了关键词）。

**独立验收**：打开经正常上传流程提交的论文详情页，页面完整渲染，不白屏。

**验收场景**：

1. **假如** 一篇论文的 `keywords_tags` 是 JSON 字符串 `'["超导", "汞", "液氦"]'`，**当** 上传者打开其详情页，**那么**：
   - 页面正常渲染，顶栏与侧边导航可见
   - 「论文详情」标题与「只读模式」标识可见
   - 关键词区展示「超导」「汞」「液氦」三个独立标签
   - 控制台无未捕获异常

2. **假如** 同一篇论文的 `methodology` 是 JSON 字符串，**当** 打开详情页，**那么** 研究方法按 `• ` 前缀逐项展示，与 Issue #59 已确立的可读列表形态一致。

3. **假如** 同一篇论文的 `authors` 是 JSON 字符串 `'["H. Kamerlingh Onnes"]'`，**当** 打开详情页，**那么**：
   - 作者区展示 `H. Kamerlingh Onnes`
   - 页面文本不含 `["` 或 `"]` 片段

### 边界与异常场景

- **数组形态**：字段已是数组时行为不变（管理员编辑路径、既有测试载荷均为此形态）
- **null 与空串**：字段为 `null`、`undefined`、空字符串时不渲染对应区块，不抛错
- **非法 JSON**：字段是无法解析的裸字符串时，退化为单元素列表展示原文，不抛错
- **非数组 JSON**：字段解析出对象或数字（如 `'{"a":1}'`、`'42'`）时视为空列表，不抛错
- **空数组字符串**：`'[]'` 视为空列表，不渲染区块
- **元素含空值**：`'["超导", "", null]'` 过滤掉空项，只展示有效标签

## 需求

### 功能需求

- **FR-001**：详情页对 `keywords_tags` 必须同时接受数组与 JSON 字符串两种形态，并渲染为独立标签。

- **FR-002**：详情页对 `methodology` 必须同时接受数组与 JSON 字符串两种形态，并按可读列表逐项展示（沿用 Issue #59 的 `• ` 形态）。

- **FR-003**：详情页对 `authors` 必须同时接受数组与 JSON 字符串两种形态，并以可读形态展示人名，页面不得出现 JSON 数组原文（`["` / `"]`）。

  此前实现为 `JSON.stringify(data.authors || [])` 后直接渲染，即使不崩溃也会把 `["H. Kamerlingh Onnes"]` 原样印到页面上。Issue #59 修掉了 `methodology` 的同类问题但漏了 `authors`。

- **FR-004**：归一化逻辑必须在组件内收敛为单一实现，三个字段共用，不得为每个字段各写一份解析分支（DRY）。

- **FR-005**：归一化逻辑对 `null`、`undefined`、空串、非法 JSON、非数组 JSON 均不得抛出异常。

- **FR-006**：回归测试的论文 fixture 必须采用后端真实返回形态（JSON 字符串），而非人为构造的数组形态。

### 不做的需求

- **NFR-001**：不修改后端字段类型或序列化方式。把 `*string` 改成结构化数组需要同时改动 Go 模型、`paperToDict`、Python 写入侧与所有既有消费方（`SearchPage`、`share`），影响面远超一个白屏修复，属于独立的契约治理议题。本 Feature 只在消费侧容错。
- **NFR-002**：不新增 ErrorBoundary。见「范围外事项」。

### 关键实体

**论文（Paper）的 JSON 文本列**：
- `keywords_tags`、`methodology`、`authors` 三列在 MySQL 中均为 `text`/`json`
- Python 侧以 `json.dumps(..., ensure_ascii=False)` 写入（`backend/api/rag.py:1043`）
- Go 模型声明为 `*string`（`goserver/models/models.go:97`、`:113`、`:114`），`paperToDict` 原样透传
- 因此 API 返回值形态取决于写入方，消费侧必须两种都兼容

## 成功标准

- **SC-001**：`keywords_tags` 为 JSON 字符串的论文，详情页完整渲染且关键词逐项可见。
  **已验证**：新增 Vitest 用例断言「论文详情」标题与三个关键词标签同时可见。

- **SC-002**：`methodology` 为 JSON 字符串时逐项可读展示。
  **已验证**：新增用例断言 `• 电阻测量`、`• 低温实验` 可见。

- **SC-003**：`authors` 为 JSON 字符串时展示人名，且全页文本不含 `["` 与 `"]`。
  **已验证**：新增用例同时断言人名可见与 JSON 片段不存在。

- **SC-004**：既有 26 个详情页用例（含 Issue #56/#57/#59 的验收判据）全部保持通过，证明数组形态行为未回退。
  **已验证**：`paper-detail-route.test.tsx` 16 例 + `paper-detail-form-parity.test.tsx` 10 例全绿。

- **SC-005**：真实环境下 `GET /api/papers/9` 返回 200，`/papers/9` 页面返回 200 且渲染出详情。
  **已验证**：用 id=2 用户的合法 token 实测 API 200，重建前端容器后页面可访问。

- **SC-006**：TypeScript 编译无错误。
  **已验证**：`tsc --noEmit` 通过。

## 假设与依赖

- 后端 `GET /api/papers/{id}` 的字段形态维持现状（`*string` 透传）
- 详情页可见性判定仍完全由后端 `canViewPaper` 裁决，本次不触碰权限逻辑
- Vitest + React Testing Library 测试体系可用

## 范围外事项

- **不新增 ErrorBoundary**：本轮只修根因。白屏放大机制（无 ErrorBoundary 导致叶子异常拖垮整树）是全站性的健壮性缺口，影响所有页面而非仅详情页，应作为独立 Issue 处理，不混入本次 bug 修复。已在澄清记录中留档。
- **不统一其他页面的解析方式**：`SearchPage.tsx:707` 与 `share.tsx:632` 各自用 `try/JSON.parse/catch` 内联处理 `methodology`，形态上重复但当前不崩溃。抽取公共工具属于跨页面重构，超出本次修复范围。
- **不改后端字段类型**：见 NFR-001。
- **不追溯已提交论文数据**：不做数据迁移，库中现有 JSON 字符串保持原样，由消费侧容错。

## 澄清记录

### 2026-08-31

- 问：白屏是权限问题还是路由问题？ → 答：都不是。API 返回 200、路由匹配正常，是 `PaperEditView` 渲染期抛 `TypeError` 导致 React 卸载整树。
- 问：为什么 `PaperDetailPage` 的 403/404 提示没出现？ → 答：异常发生在分流之后的展示组件里，走不到那些分支。
- 问：既有 16 个详情页测试为何全绿？ → 答：`makePaper` fixture 用数组形态（`authors: ['Hanyu Liu']`），与后端真实返回的字符串形态不一致。属 fixture 偏离契约的测试盲区。
- 问：修后端还是修前端？ → 答：修前端消费侧。改后端类型需连带改 Go 模型、序列化、Python 写入与全部既有消费方，影响面远超白屏修复本身。
- 问：是否顺手加 ErrorBoundary？ → 答：本轮不加。根因已修，ErrorBoundary 属全站健壮性改进，单独立项以免混淆本次修复的验收边界。
- 问：`authors` 是否属于本次范围？ → 答：属于。它是同一根因下的同批字段，且原实现会把 JSON 原文印到页面上，与 Issue #59 的既定要求冲突。
