# Feature 规格：多模态 PDF 解析与证据驱动上传 Agent

**GitHub Issue**：[ #114](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/114)

**创建日期**：2026-09-23

**状态**：已确认，实施中

## 背景与目标

当前上传链路主要依赖 PyMuPDF 文本层。扫描页、复杂表格、公式、图像和曲线中的信息可能没有进入模型，且现有 `paper_chunks` 只能表达文本片段，不能长期保存区域级定位。用户需要一个能发现更多论文事实、保留可复核证据、在解析失败时明确失败或转人工的上传解析链路。解析方案通过任务配置选择；系统不把普通文本结果伪装成高级解析结果，也不在解析器失败时静默切换方案。

本 Feature 将解析器、PDF 原生多模态 LLM 和超导领域抽取组合为受控工作流。解析器只产生统一 Document IR，LLM 只产生带来源的 Claim，程序负责证据定位、覆盖审计、契约校验和正式写入。正式科学数据仍须经过用户校对、来源核对和审核批准。

## 用户场景与验收

### 用户故事 1：解析复杂论文（P1）

作为上传者，我希望数字 PDF、扫描 PDF、双栏论文、复杂表格、公式、图表、补充材料和中英文论文都能进入统一结构，以便后续抽取不依赖单一文本层。

**独立验收**：使用固定样例集按指定解析方案运行，所有成功样例都能返回带页码、块类型和内容哈希的 Document IR；指定方案不可用时明确失败或转人工，不能静默切换为另一种方案。

**验收场景**：

1. **假如**任务选择结构化文本方案，**当** PDF 有可靠文本层，**那么**系统使用 Docling，并保留页码、阅读顺序和区域坐标。
2. **假如**任务选择复杂版面、OCR 或视觉方案，**当**对应能力可用，**那么**系统使用 MinerU、视觉适配器或 PDF 原生多模态 LLM，并标记解析器、模式和版本。
3. **假如**任务指定的 Docling、MinerU、视觉模型、PDF 原生多模态 LLM 或 GPU 能力不可用，**当**任务继续，**那么**系统记录明确错误并进入可重试或人工处理状态；用户或任务策略可以重新选择其他解析方案。

### 用户故事 2：生成有证据的科学 Claim（P1）

作为上传者和审核员，我希望每个 Tc、压力、方法和条件候选都能回到具体文件、页码、区域和原文，避免模型生成看似合理但无法核对的数值。

**独立验收**：Claim 的每个 Evidence 都能由服务端在同一份 Document IR 中定位；无法定位的 Claim 不能进入正式科学字段。

**验收场景**：

1. **假如**模型返回材料、Tc、压力和引句，**当**程序校验 Claim，**那么**系统验证文件身份、页码、块 ID、区域和引句的一致性。
2. **假如**引句只能在 OCR 文本中找到，**当**系统保存证据，**那么**来源标记为 OCR/视觉来源，不能伪装为原始文本层精确引句。
3. **假如**模型没有可靠证据，**当**草稿生成，**那么**字段保持空值或待人工状态，不直接写入正式科学记录。

### 用户故事 3：覆盖审计与安全停止（P1）

作为上传者，我希望系统能发现漏读的表格行、不同压力和跨页条件，并在解析器或模型失败时明确停止、重试或转人工。

**独立验收**：覆盖审计能报告已处理页、表格行、疑似结果段落、未确认项和解析方案限制；任务不会永久停在运行态。

**验收场景**：

1. **假如**表格包含多行 Tc，**当**抽取完成，**那么**审计检查表格行数与 Claim 覆盖，并列出未采用行的原因。
2. **假如**上下文、预算或工具次数耗尽，**当**流程停止，**那么**任务进入“需要人工”或可重试状态，不伪造完成。
3. **假如**RQ 入口或模型调用在业务函数前失败，**当**失败回调执行，**那么**既有上传任务状态进入可见、可重试的失败状态。

### 用户故事 4：查看区域证据（P2）

作为上传者或审核员，我希望在校对页面按页码、区域和引句查看证据，并在区域渲染失败时仍能看到文本证据。

**独立验收**：真实上传、刷新、返回和审核流程中，字段可打开来源；页面图像按需渲染，不把截图作为唯一事实来源。

**验收场景**：

1. **假如**Evidence 有 bbox，**当**用户打开证据，**那么**页面显示文件、PDF 页码、区域高亮和原文引句。
2. **假如**原 PDF 或区域渲染失败，**当**用户查看证据，**那么**系统显示页码和原文，并明确说明图像不可用。
3. **假如**证据来自旧缓存且没有区域，**当**用户打开记录，**那么**沿用页码和引句显示，不破坏历史读取。

### 用户故事 5：渐进上线（P2）

作为维护者，我希望先比较新旧解析链路，再逐步启用新链路，避免一次升级影响所有上传任务。

**独立验收**：Shadow、灰度、默认三个阶段均可由配置控制；任务可以选择已支持的解析方案，新链路失败可以显式回退旧链路，用户不需要长期绑定某个解析器。

**验收场景**：

1. **假如**处于 Shadow，**当**任务上传，**那么**旧链路生成用户草稿，新链路只保存可比较结果。
2. **假如**处于灰度且新链路失败，**当**任务继续，**那么**任务使用旧链路回退并保留失败原因。
3. **假如**质量门未通过，**当**维护者尝试切换默认，**那么**配置拒绝切换并保留旧链路。

## 边界与异常场景

- 多文件任务的每个 PDF 保留独立 `file_id`、哈希和来源角色；不能把补充材料的事实静默归到正文。
- PDF 实际页码与印刷页码分开保存；无法识别印刷页码时为空。
- bbox 必须位于页面边界内；非法几何数据被拒绝并保留文本证据。
- 外部联网只用于出版元数据、研究背景和术语解释；不得补充 Tc、压力、材料、结构、方法、附件或正文事实。
- 不保存模型内部思维链；只保存结构化输出、工具调用摘要、规则版本和错误原因。
- 不因没有 GPU 阻断服务启动；视觉路径不可用时必须可观察地失败、重试或转人工，不能伪装成高级解析结果。
- 不批量重解析历史论文；旧缓存、旧 `paper_chunks` 和旧 Evidence 继续可读。

## 需求

### 功能需求

- **FR-001**：系统必须提供统一 `DocumentParser` 适配器接口，解析器只返回 Document IR，不直接写入正式科学数据。
- **FR-002**：系统必须提供 Docling 默认适配器、MinerU 可选适配器、PyMuPDF 文本适配器和 PDF 原生多模态 LLM 受控适配器；解析方案由任务策略选择，解析器失败不得静默自动切换。
- **FR-003**：Document IR 必须保存文档/文件身份、页码、可选印刷页码、块类型、阅读顺序、文本、bbox/多边形、内容哈希、置信度、解析器和版本。
- **FR-004**：系统必须把表格、图像、公式、标题、段落和 OCR 内容表达为可引用的稳定块或区域。
- **FR-005**：系统必须将 Tc、压力、方法、条件和材料状态候选表达为 Claim，并为每条 Claim 保存来源类型和 Evidence 列表。
- **FR-006**：程序必须验证 Claim 的文件、版本、页码、块 ID、几何范围和引句，验证失败的 Claim 不得直接进入正式科学数据。
- **FR-007**：系统必须执行覆盖审计，至少检查已处理页、表格行、疑似结果段落、不同压力/材料/方法组合和输出截断信号。
- **FR-008**：Agent 工具必须限定为文档读取、区域读取、表格/图像检查、文档内搜索、Claim 验证和覆盖检查；每任务最多 12 次行动，单工具最多重试 2 次。
- **FR-009**：系统必须区分直接引文、论文推断、通用知识、OCR/视觉来源和外部元数据，不能把它们伪装成同一种论文原文证据。
- **FR-010**：系统必须在解析器、模型、GPU、队列或预算不可用时记录稳定错误和所选解析方案，并提供重新选择方案、重试或人工处理路径。
- **FR-011**：系统必须支持 Shadow、灰度、默认三阶段；任务策略可以选择已支持的解析方案，灰度失败可按任务显式回退旧链路，用户不需要长期绑定某个解析器。
- **FR-012**：系统必须新增正式文档定位数据和定位关联表，支持新当前论文 revision 的定位复制、审核读取和按既有删除边界清理；旧 revision 不作为可长期打开的完整文档保存，截图按需生成。
- **FR-013**：外部联网工具只能用于出版元数据、研究背景和术语解释；其结果不得作为科学 Claim 的事实来源。
- **FR-014**：上传、提交、审核、发布和 RAG 必须继续使用现有权限、事务、来源核对和人工批准边界。

### 关键实体

- **DocumentSource**：上传文件、角色、哈希、媒体类型和版本。
- **DocumentIR**：一份文件的页面、块、表格、图像、公式、解析元数据和覆盖摘要。
- **DocumentBlock**：具有稳定 ID、类型、页码、坐标、文本和内容哈希的可引用单元。
- **Claim**：面向表单字段的结构化科学候选，包含值、归因、状态和 Evidence。
- **EvidenceLocator**：将 Claim 连接到文件、页、块、区域和引句的稳定定位。
- **PaperEvidenceLocator**：把现有 `paper_evidences` 与当前 revision 的 `paper_document_blocks` 连接起来的正式定位关联。
- **CoverageReport**：页面、表格行、疑似结果和未解决项的覆盖审计结果。
- **ParserRun**：一次解析所用的解析方案、解析器、版本、模式、能力、限制/错误和规则版本。

## 成功标准

- **SC-001**：固定 50 篇人工标注论文上，关键科学记录 F1 不低于旧链路；复杂表格、扫描页和多压力样例的记录召回率高于旧链路。
- **SC-002**：固定评测集上的 Evidence 页码/区域定位成功率达到 95% 以上。
- **SC-003**：无有效 Evidence 且无明确人工裁决的字段自动写入正式科学数据的数量为 0。
- **SC-004**：指定解析方案、模型、GPU 或队列不可用时，任务 100% 进入明确失败、可重试或人工处理状态，不永久卡在运行态；重新选择解析方案必须显式记录。
- **SC-005**：Agent 单任务行动数不超过 12，单工具重试不超过 2 次，且不存在无范围公网搜索调用。
- **SC-006**：区域证据在上传校对和审核流程中可查看；渲染失败时文本证据仍可用。
- **SC-007**：旧缓存、已提交论文 revision、权限矩阵、提交事务和审核历史回归测试通过。
- **SC-008**：Shadow、灰度、默认切换均可配置，默认切换前必须通过质量门并保留旧链路回退。

## 假设与依赖

- 当前主分支继续为 `mayuan`；Issue #114 是唯一协作状态来源。
- Docling 和 MinerU 纳入基础依赖，但运行时不要求 GPU；复杂视觉能力依赖可用模型和资源，解析方案由任务策略选择。
- #67 的联网实现只作为非阻塞关联；联网不可用时仅使用上传文件。
- 现有 `paper_chunks`、`paper_evidences`、科学数据契约和审核事务继续作为兼容边界。
- 至少 50 篇论文的人工标注集由项目维护者提供或从合法可用论文中建立。

## 范围外事项

- 首期云端 OCR 服务和第三方托管 PDF 解析。
- 多 Agent 群体、无边界自主浏览和模型内部思维链保存。
- 让用户长期绑定某一个解析器；任务级解析方案选择和维护者灰度配置不在此范围外。
- 外部论文/附件补全科学事实。
- 历史论文批量重新解析、自动批准和自动发布。

## 澄清记录

### 2026-09-23

- 问：Feature 是否作为 #24 子 Issue？→ 答：独立 `type:feature` Issue，不挂父 Issue。
- 问：解析运行方式？→ 答：本地优先、可插拔解析方案；Docling 默认，MinerU、PyMuPDF 文本方案和视觉方案按任务策略选择，解析器失败不静默切换。
- 问：是否纳入 PDF 原生多模态 LLM？→ 答：纳入受控 IR 解析适配器，只返回合法 Document IR；Claim 候选由独立提取步骤生成，不能绕过证据校验和覆盖审计。
- 问：解析状态是否扩展现有五阶段？→ 答：不扩展；`ir_ready`、`claims_ready`、`coverage_checked`、`degraded`、`needs_review` 都是 `reading` 的内部子状态。
- 问：论文升版如何处理定位数据？→ 答：定位数据和科学数据归入新的当前 revision；旧 revision 不保留可长期打开的完整文档，只保留现有修改历史。
- 问：不同文件如何进入解析链路？→ 答：只有 PDF 进入 PDF 解析方案；TXT/MD 保留直接读取，CIF/POSCAR 保留 ASE 结构候选和用户确认流程。
- 问：定位数据如何关联现有 Evidence？→ 答：新增定位关联表，连接现有 `paper_evidences` 与 `paper_document_blocks`，不替换现有科学 Evidence 关系。
- 问：区域证据如何保存？→ 答：正式保存定位数据，截图按需渲染。
- 问：上线方式？→ 答：Shadow → 灰度 → 默认，旧链路保留回退。
- 问：质量门？→ 答：正确性优先，至少 50 篇人工标注论文。
- 问：联网边界？→ 答：仅出版元数据、研究背景和术语解释，不补科学事实。
- 问：依赖和 GPU？→ 答：Docling/MinerU 纳入基础依赖，但无 GPU 时服务仍可启动；指定视觉方案不可用时记录失败并允许重新选择方案，不伪装为降级成功。
