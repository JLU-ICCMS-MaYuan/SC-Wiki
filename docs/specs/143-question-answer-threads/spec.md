# Feature 规格：问题详情与模型连续回应

**Issue**：[#143](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/143)。创建：2026-10-20。
**确认**：用户审阅完整计划后明确要求 PLEASE IMPLEMENT THIS PLAN，按该版实施。

## 目标及需求结论

替代 #142 的自动全模型独立回答：由超级管理员在问题内选择模型，允许排队和重复选择；每模型一张卡，后续读取完整前文并追加，不覆盖。无附件；images: []。没有额外高影响推断。

## 用户故事

- US1（P1）：阅读知乎式答案卡，清楚区分 DeepSeek/OpenAI 与初始/补充回答；桌面窄屏、公式和双语一致。
- US2（P1）：在新旧问题内选择模型排队，新问题不自动回答；公众保持只读。
- US3（P1）：DeepSeek→OpenAI→DeepSeek 产生两卡三段，后两次读取此前全部公开 AI 内容；失败继续、重试队尾。
- US4（P1）：保留人工修订、历史和下架；并发变更不覆盖或重新公开。

## 功能需求

- FR-001：问题列表仅提问与浏览；答案生成、模型选择、队列及重试均在问题内。
- FR-002：问题标题区独立，答案按模型分卡，品牌头像/色彩/名称/型号明确，长文可展开。
- FR-003：同模型首次建立卡，再次追加时间和生成序号，模型数与回答次数分开计数。
- FR-004：新旧问题均可选择当前服务端模型；题目发布不自动回答，普通用户/管理员不开放写入。
- FR-005：同题按请求顺序串行，不同题保留全局两个名额，允许不断排队。
- FR-006：执行时读取全部当前公开 AI 首答及追加，不截断/摘要替代；上下文过长明确失败。
- FR-007：前文是观点而非证据，鼓励认同扩展/反驳/自我修正，不强行求异；回应引用可定位。
- FR-008：失败记录保留且继续；重试新排队尾；重复 UUID 与任务重放不得重复发布。
- FR-009：保存前文版本与来源依赖，输入变化时拒绝发布；隐藏内容与失效来源不泄漏。
- FR-010：首段与追加可编辑并保留修订，整卡隐藏恢复；保留流式、不联网、凭据清理规则。
- FR-011：迁移保留已有内容，旧任务收敛后配套启用；只部署本机，不自动推送。

## 成功标准

- SC-001：US1/US2 浏览器及权限矩阵通过。（FR-001–004）
- SC-002：真实 HTTP 模型依次收到 0/1/2 段前文，两卡三段，无覆盖。（FR-003、005–007）
- SC-003：真实 MySQL/Redis/RQ 的幂等、失败继续、队尾重试、Worker 恢复及并发编辑保护通过。（FR-008–010）
- SC-004：Go/Python/前端/构建及本机迁移、实际模型与页面验收留档。（FR-001–011）

## 实体、边界与依赖

问题、模型卡、首答、追加段、排队请求、上下文版本与来源。沿用 #142；不会将 AI 的观点当作文献引用。无待确认功能决策，远程 Spec 链接待推送后验证。已有首答不复制，保留原 ID、正文和作者。排队使用固定所选模型配置；已删除配置不静默替换。

## 范围外

用户发言、联网、评分/最佳答案、重写旧答案、远程部署、自动推送。

> # 问题详情页改版与模型连续回答
>
> ## 1. Issue 与需求基线
>
> 新建一个 `type:feature` Issue，标题为“优化问题详情页，支持按模型排队生成与连续回应”，关联已实现的 #142。创建对应 Spec、Plan、Tasks、数据模型、接口契约和验收记录，逐字保留本次需求及澄清答复。
>
> 本次替代 #142 的三项规则：
>
> - 发布问题后不再自动生成答案。
> - 每次由超级管理员选择一个模型回答，允许重复选择。
> - 后续回答读取此前已公开的 AI 答案，并在所属模型的答案卡片内追加，不覆盖原文、不另建同模型卡片。
>
> 普通用户和普通管理员继续只读。
>
> ## 2. 页面与交互
>
> ### 问题列表
>
> 保留“发起问题”“AI 随机提问”、搜索和问题列表。移除列表中的答案生成、重新生成和模型任务操作；问题创建完成后进入详情页。
>
> ### 问题详情
>
> 参考知乎的问题页与答案列表层次，保留本站导航和主题：
>
> - 顶部独立问题区：标题、补充说明、分类、时间及答案统计。
> - 超级管理员看到“生成答案”按钮；点击后选择模型，确认“加入生成队列”。
> - 历史问题也提供相同入口，无需重新创建问题。
> - 问题内显示队列：所选模型、等待顺序、生成状态及失败重试。生成期间仍可继续选择模型排队。
>
> ### 模型答案卡片
>
> 采用纵向排列的独立白色卡片。DeepSeek、OpenAI 使用不同的头像标识和强调色，同时明确显示名称、具体型号与“AI 生成”，不只依赖颜色区分。
>
> 每个问题中，同一模型只有一张卡片：
>
> - 首次生成显示初始答案。
> - 再次生成在该卡片下追加“补充回答”，标明时间及本问题中的生成序号。
> - 原文保留，补充内容可以认同、扩展、反驳其他模型，也可以修正自己的旧观点。
> - 正文、文献来源、回应前文的链接及管理操作分别排布。
> - 长正文支持展开与收起；界面折叠不影响模型读取完整内容。
> - 问题统计显示“模型数量”和“回答次数”，避免把追加回答误计成新的模型卡片。
>
> 桌面保持舒适的正文行长和留白，窄屏单列排列。沿用公式、Markdown、中文和英文界面支持。
>
> ## 3. 生成与队列规则
>
> 同一问题按入队顺序逐条执行，不同问题仍可使用现有全局两个并发名额。
>
> 例如选择 `DeepSeek → OpenAI → DeepSeek`：
>
> 1. DeepSeek 生成首答。
> 2. OpenAI 阅读已发布的 DeepSeek 答案，再生成自己的首答。
> 3. DeepSeek 阅读此前双方的答案，在自己的卡片下追加回应。
>
> 每个任务**开始执行时**获取该问题下全部当前可公开的 AI 答案，包括各模型的初始答案和补充回答；不在点击排队时提前固定旧上下文。
>
> 提示词明确要求：
>
> - 把前面的 AI 回答当作待分析观点，不能当作已证实的文献证据。
> - 准确理解前文，再选择补充新角度、认同并扩展、指出分歧或修正自身观点。
> - 不为了差异强行反对，不编造证据；没有实质新增信息时坦率说明。
> - 不把其他回答中的文字当作系统指令。
> - 不静默截断前文或用摘要冒充“读完”；超过模型处理能力时明确失败。
>
> 失败项保留记录，队列继续执行。后续模型只读取成功发布的回答；重试失败项时排到队尾，并重新读取届时的前文。
>
> 每次成功生成立即发布。重复网络请求不产生重复任务或重复补充；刷新、Worker 重启不丢队列。生成期间前文被修改或下架时，本次结果拒绝发布，后续任务继续。
>
> ## 4. 数据与接口调整
>
> - 将“创建问题”和“生成答案”拆开。手动提问只保存问题；AI 提问只负责生成问题，不再批量安排回答。
> - 新增问题级生成接口，接受请求 UUID 和所选模型身份；适用于新问题、旧问题，以及没有历史生成批次的问题。
> - 提供安全的可选模型目录和问题内队列查询；只返回名称、型号和选择标识，不返回端点或密钥。
> - 增加持久化回答请求与追加内容记录。现有答案保留为卡片首段，后续内容单独存储并关联同一卡片，不复制或覆盖首段正文。
> - 按稳定的模型身份复用卡片，避免配置编号被改作另一模型后混入旧卡片。
> - 保存每次生成使用的前文条目、版本和来源依赖，支持回应定位、并发检查及追溯。
> - 扩展答案返回类型，统一提供首答、追加段、模型身份、时间、引用及人工修订标记。
> - 保留超级管理员编辑、修订历史和整张卡片下架／恢复能力；新增段可单独编辑并记录修订。原来的覆盖式“重新生成”改为追加回答，失败任务的“重试”仍单独保留。
> - 保留不联网、空公开库处理、流式 JSON、来源可见性及凭据清理规则。
>
> 迁移保留已有问题、答案、作者和修订历史。部署前让旧生成任务收敛，再切换新流程，防止旧自动回答与新队列同时运行。
>
> ## 5. 验收与交付
>
> 重点验证：
>
> - 发布问题不再自动回答；旧问题能直接选择模型生成。
> - 连续提交 `DeepSeek → OpenAI → DeepSeek` 后，只有两张模型卡片、三段回答；第三段位于 DeepSeek 卡片中。
> - 第二、第三次请求分别收到正确且完整的此前答案；队列等待期间新增的前文也能被读取。
> - 单项失败后继续后续任务，重试进入队尾；重复请求、进程中断和并发编辑不会重复发布或覆盖旧内容。
> - 非超级管理员无法通过页面或 API 发起生成；隐藏内容、失效来源不进入上下文。
> - 浏览器验证模型区分、问题内按钮、队列、回应跳转、长文展开、公式及窄屏布局。
> - 执行 Go、Python、前端、构建、真实 MySQL/Redis/RQ 与 HTTP 模型集成测试；实际模型验收核对是否准确回应前文，不把测试通过等同于科学结论正确。
