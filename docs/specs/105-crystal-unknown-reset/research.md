# 设计依据与取舍

## R1：用户事件触发而非加载清洗

决策：只在明确选择未知时清空。
理由：用户已确认不自动清理历史，合法群号仍可推导晶系。
拒绝方案：在归一化中遇到 unknown 就删群号，会破坏 AI 草稿与旧记录兼容。
证据：`backend/ingest/upload_jobs.py` 根据群号推导晶系；原 Select 只更新 crystal_system。

## R2：三字段原子更新与重复选择

决策：共享组件一次更新当前状态。Select 处理值变化，未知菜单项处理值相同的再次激活。
理由：三次独立更新可能基于旧状态互相覆盖；只用 onChange 无法处理重复选择。
备选：给两入口分别加保存前转换，不能即时清空且重复维护规则，因此不采用。

## R3：报告值与结构值分离

决策：只改 reported_space_group_*，不改 structure 或结构候选。
理由：报告空间群与附件解析结果是不同事实；清空前者没有删除后者的授权。

## R4：最小验证边界

决策：真实共享控件测试 + 双入口隔离浏览器 + 生产归一化/持久化重读。
理由：只断言对象值无法证明 MUI 重复选择或本地输入缓存正确；只 Mock 保存无法证明 null 落库。
不开模型、不接触业务数据，保持已有人工核对的版本规则。
