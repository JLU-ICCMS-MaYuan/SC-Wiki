# Feature 规格：修复探索页与社区页多行文本丢失用户录入的换行

**GitHub Issue**：[#68](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/68)

**创建日期**：2026-08-31

**状态**：已落地

## 背景与目标

用户在校对页按「一个要点一行」录入「核心发现」，进入探索页详情后所有要点被合并成一段
连续文本 —— 分条编号还在，但换行没了，结构不可读。

数据完好，纯渲染问题。以 Hg 论文（`papers` id=9）实测：库中 `key_finding` 经 `cat -A`
确认含 `\n`，API 返回的是真实换行（非 `\n` 字面）。缺陷在于展示侧未设 `whiteSpace`，
HTML 默认折叠连续空白符，把换行当空格处理。

`key_finding` 与 `summary` 都由用户在多行文本框按行录入，换行是**内容结构**而非排版
噪声。详情页 `PaperEditView` 对 `abstract`、`summary`、`key_finding`、`rationale` 四个
字段一直设了 `pre-wrap`；两个检索页都没有 —— 同一份数据三个页面有两种呈现方式。

**业务价值**：
- 可读性：分条要点是用户主动组织的结构，折叠后读者需要靠编号在长段落里找边界
- 一致性：同一字段在详情页正常、检索页异常，用户会怀疑数据本身出了问题
- 防回归：补测试锁定该样式，避免下次新增页面或重构时再次丢失

## 用户场景与验收

### 用户故事 1：研究者阅读论文的核心发现（优先级：P1）

研究者从探索页或社区页打开论文详情，希望按上传者组织的分条结构阅读核心发现与论文总结。

**优先级理由**：这是用户主动录入的内容结构被系统丢弃，属正确性问题；且用户已复测反馈
一次，说明实际影响可感知。

**独立验收**：Hg 论文的核心发现在探索页按原有换行分行显示。

**验收场景**：

1. **假如** 一篇论文的 `key_finding` 在库中含换行（用户按「一个要点一行」录入），
   **当** 研究者在探索页打开该论文详情，**那么**：
   - 核心发现按原有换行分行显示，每个编号要点独占一行
   - DOM 文本中保留 `\n` 字符，未被替换为空格
   - 该节点的 computed `white-space` 为 `pre-wrap`

2. **假如** 同一篇论文的 `summary` 含换行，**当** 打开探索页详情，**那么** 论文总结同样
   保留分行结构。

3. **那么** 核心发现
   与论文总结的分行结构与探索页一致。 科学字段右侧栏功能设计、原话及历史已迁移至 [#221](../221-scientific-field-sidebar/spec.md)，本处不再独立维护。

### 边界与异常场景

- **字段为空或 null**：不渲染该区块或显示 `-`，行为不变
- **字段为单行文本**：`pre-wrap` 不改变单行文本的呈现
- **字段前后有多余空白**：`pre-wrap` 会如实保留，与库中内容一致（不做 trim，避免擅自
  改写用户录入的内容）
- **社区页的 JSON 解析分支**：`key_finding` 经 `JSON.parse` 兜底处理后仍须保留换行

## 需求

### 功能需求

- **FR-001**：`summary`（论文总结）与 `key_finding`（核心发现）在探索页与社区页均须以
  `whiteSpace: 'pre-wrap'` 渲染。共四处：

  | 字段 | 探索页 `SearchPage.tsx` | 社区页 `share.tsx` |
  | --- | --- | --- |
  | `summary` | ✅ | ✅ |
  | `key_finding` | ✅ | ✅ |

- **FR-002**：渲染行为须与详情页 `PaperEditView` 一致 —— 同一字段在三个页面呈现相同。

- **FR-003**：不得在前端对字段内容做 trim、换行替换或其他改写。换行是用户录入的内容，
  展示侧只负责不折叠它。

- **FR-004**：须有自动化测试断言该样式，且测试必须能真实捕获缺陷（移除样式后失败），
  而非恒真通过。

### 不做的需求

- **NFR-001**：不改后端。数据完好，API 返回的就是真实换行。
- **NFR-002**：不改动 `PaperEditView`。它四个字段一直是对的，无需修改。
- **NFR-003**：不改校对页的录入控件。用户录入侧工作正常，问题只在展示侧。

### 关键实体

**多行文本字段**：
- `summary`、`key_finding` 由用户在校对页多行文本框按行录入
- MySQL 中为 `text` 列，换行以真实 `\n` 存储
- Go 侧 `*string` 透传，API 返回真实换行
- 展示侧须以 `pre-wrap` 呈现

## 成功标准

- **SC-001**：探索页的核心发现节点 computed `white-space` 为 `pre-wrap`，DOM 文本含 `\n`。
  **已验证**：Vitest 用例断言 `getComputedStyle(node).whiteSpace === 'pre-wrap'` 与
  `node.textContent` 含 `\n`。

- **SC-002**：探索页的论文总结同样满足上述条件。
  **已验证**：同文件独立用例。

- **SC-003**：社区页两个字段均已加 `pre-wrap`。
  **已验证**：产物核对 —— `share-*.js` bundle 中 `pre-wrap` 出现 2 次
  （summary + key_finding）。

- **SC-004**：测试能真实捕获缺陷。
  **已验证**：临时移除 `pre-wrap` 后 2 个用例立即失败，恢复后通过。

- **SC-005**：TypeScript 编译无错误，既有测试不回退。
  **已验证**：`tsc --noEmit` 通过；全量 107 例中 106 通过（唯一失败为 Issue #63 在建
  代码的 `news-feed.test.tsx`，与本次无关）。

- **SC-006**：真实环境下库中与 API 的换行均已确认存在，排除数据侧丢失。
  **已验证**：`cat -A` 见 `\n`；API 返回 `chr(10) in key_finding` 为 True，`'\\n' in ...`
  为 False（即真实换行而非字面量）。

## 假设与依赖

- 后端继续以 `text` 列原样存储并透传这两个字段
- 前端改动需重建 dev 前端容器才会进入 bundle

## 范围外事项

- **不改后端**：见 NFR-001。
- **不动 PaperEditView**：见 NFR-002。
- **不处理 abstract 与 rationale 在检索页的呈现**：这两个字段当前不在探索页与社区页
  渲染，无从丢失换行；若日后新增展示，须一并设 `pre-wrap`。
- **不改表格内的备注列**：两页面物性表的 `row.note` 为单行短文本，不需要 `pre-wrap`。
- **不做 Markdown 渲染**：用户录入的是纯文本分条，保留换行即可满足可读性。引入
  Markdown 解析会改变内容语义（如 `1.` 被渲染为有序列表、特殊字符被吃掉），属独立议题。

- 问：要不要顺便做 Markdown 渲染？ → 答：不做。保留换行已满足需求，Markdown 会改变内容
  语义，属独立议题。
