# 验证路径：默认启用人工问题窗口并以最小改动接入新文献解析

本页描述后续验证方式，不代表已经运行。

## 前置条件

- 明确用户授权及适用测试环境，保留共享工作树和已有用户草稿。
- 使用[spec.md](spec.md)的FR/SC和[plan.md](plan.md)映射；真实来源、模型配置引用与实际执行分开记录。
- Issue远程链接未核实前保持检查表未完成，不自动推送。

## 操作与预期

1. 按SC-001验证：默认配置下新任务在红框出现真实问题，选择后经正式保存和调度恢复；无问题任务不会新增模型核对或无关科学写入。
2. 按SC-002验证：开关关闭的新任务保持既有保护；已有问题仍可读可答，关闭、刷新、重启和重新开启不丢队列及已保存的人工决定。
3. 按SC-003验证：三项契约、四宿主相关交互、构建及必要后端回归通过；固定隔离大草稿无关渲染/扫描/请求不回退，旧失败独立基线证明。
4. 按SC-004验证：直接使用新文献留证真实来源、模型、源码、问题/回答/复用/补做及保存重读范围；未发生科学冲突时不伪造真实人工案例。

## 必需检查入口

```sh
npm run test:field-contract --prefix "frontend"
npm run test:form-contract --prefix "frontend"
npm run test:form-contract:mutation --prefix "frontend"
npm run build --prefix "frontend"
```

以上是后续实现的必要验证入口，本次纯文档未运行这些业务检查；已知故障先证明回归可失败，旧失败以独立基线单列。真实PDF验证要记录源码、文件哈希、实际模型、原失败、复用和新提取范围、正式后处理与保存重读，不以旧AI响应冒充新提取。

真实新文献由用户实际提供，目标环境另按任务授权核实；产品使用无需相同文献开关对照。后端定向测试路径见tasks.md；脚本或API尚未落地时不可将其写成可运行验收命令。
