# 实施计划：已拒绝论文返修

**GitHub Issue**：[#108](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/108)
**Spec**：[spec.md](spec.md)

## 技术上下文与职责

Python FastAPI / SQLAlchemy / MySQL 承载独立返修草稿与原子重新提交；Go 为详情返回 can_revise；React / TypeScript / MUI 复用 UploadTaskEditor 与 MaterialStatesEditor。pytest、Go tests、Vitest 验证权限、持久化及页面。迁移仅在隔离测试库执行，生产升级单独记录。

## 方案

- 新增 PaperRevisionDraft：每篇论文一份草稿，独立随机 revision_id 标识一次返修，draft_version 防多窗口覆盖，base_revision + base_fingerprint 检测管理员同版本编辑或审核变化。已提交后清空草稿内容，下一次拒绝可重新初始化。历史 operation_id 保存永久幂等回执。
- POST revision-draft 开始或恢复，GET 只读取，PUT 带返修标识和草稿版本保存；POST revision-draft/submit 复用既有校验、科学数据整体替换和版本级联，书目和科学数据同事务保存。
- 服务端从当前正式数据恢复全部模块、记录和结构，不把来源服务器路径或管理员备注放入草稿。返回不能恢复的分类提示。科学结构候选由既有解析服务生成，来源身份由服务端记录。
- 来源核对新增 revision 目标，以返修标识隔离多轮核对。复用上传草稿的断言构造，来源文本读正式 PaperChunk。模型完成时重新校验归属、草稿版本与正式基线，防止迟到任务污染新一轮。
- 提交清理旧的当前科学实体、升版后按草稿重建；保留文件、文本片段与来源锚点；保留审核历史，追加 modified 事件。新待审分类选择写入现有审核快照契约，管理员审核可恢复；快照持久信息可从提交历史中的分类选择重建，避免依赖文件写入成功。
- 前端增加 /papers/:id/revise；详情和我的论文只根据服务端 can_revise 展示入口。UploadTaskEditor 增加返修配置，复用表单、来源核对和错误定位，暂存与送审按钮分离。旧 PATCH 不允许普通上传者直接覆盖 rejected 正式数据。

- 未修改结构保留原格式、元数据及证据关联，重绑结构引用并重算摘要；旧记录定义事件随论文修改历史存档，作者角色标记随返修提交历史保留。参见 Research R6。

## 顺序与必要复杂度

文档门 → 持久化及权限测试 → 草稿服务 → 核对及提交 → 前端 → 集成验收与文档。
独立草稿是保存不改变正式数据的必要条件；行锁与摘要分别防事务交错、旧内容覆盖；原上传任务、管理员两段保存都不能替代此流程。
