# 两机到三机的计算组迁移

**来源**：[Spec](../spec.md) FR-008、FR-010、FR-011。

## 前置条件

A 为网站+计算，B 为已通过 #132 验收的数据组；C 已具备同云私网与固定版本容器运行环境。所有业务文件已在 #131 的统一存储中。C 不挂载 A 的业务目录，也不复制数据库或业务附件。

## 流程

1. 网站进入维护窗口，停止新的上传/核对/重新解析入口和相关队列生产者。首版通过维护入口与停止生产者操作完成，不新增完整只读产品模式。
2. 等待上传、核对、shadow 和延迟清理等需迁移队列的状态可解释；所有运行执行必须终止为成功/失败/取消，不能把失联任务当已排空。延迟清理任务以可校验队列状态留在 B，迁移后由同版本调度者接续，不复制/重放两套调度。
3. 停止 A 的计算组，保留其固定配置用于回退。C 配置数据端点、私密运行凭据、GROBID 和独立临时/模型缓存，使用相同 release 启动 compute；每个队列的延迟调度者仅保持一套有效实例。
4. A 将需要的 GROBID 地址改为 C 私网地址；前端 API 和 B 数据地址不变。运行就绪检查、恢复检查及最小真实任务，验证应用本地目录不可访问仍成功。
5. 开放用户入口，记录切换时间。确认日志任务身份指向 C，产物归 B 的对象存储，A 仍可完成证据查看和审核。

## 回退与失败

开放新任务前可停止 C 并恢复 A 的 compute 与 GROBID 地址。开放新任务后必须先停收并排空/收敛 C 当前执行，再回到 A，不能同时启动旧执行或重置执行代次。B 的业务数据不回退；本次只迁移计算位置。

若 C 缺模型、内存不足、指定 OCR 不可用或网络不通，保留维护状态并回到旧计算节点；不得自动换解析方案把部署问题伪装成任务成功。GPU 不作为首版必要条件，选择现有可 CPU 运行且已验证的样例。

## 业务兼容

任务列表、校对、审核接口和授权文件访问保持原入口。网站按需证据渲染可保留在 A；高负载上传/提取/核对运行在 C。资讯 Worker 仍归 A，不随上传队列搬迁。
