# 设计依据

## 现状证据

- `EvidenceFieldMarkers` 仅遍历 `evidenceProblem` 项，解决后标签入口消失；`EvidenceWorkflow.dialog` 将接受记录渲染为顶部绿色按钮。本功能将两个判断分离。
- `scientific_evidence.field_records` 跳过空值，现有科学字段没有标题/作者等书目。新浏览目录不能再等同于需要批准的断言集合。
- `checked_proposal` 原先丢弃没有引句的建议。新增明确依据类型允许通用知识建议，仍严格校验所有声称的引句。
- `run_evidence_job` 复用非空缓存；管理员全量审核必须有独立目的及缓存规则，并复核已有建议本身。
- 批准已写永久来源 JSON 并删除临时核对；新增信息应随既有事务归档，不能只存前端或依赖 Redis。

## 决策

- 复用现有侧栏、结果表和提交流程，避免建立第二套事实存储。字段可浏览不意味着字段必须有证据。
- 依据类别与人工确认分开保存。否则人工确认会把通用推测改成没有生成背景的普通人工来源。
- 上传生成置于提取之后，先得到规范字段和稳定身份；推断与推测在类型和来源校验后自动写入主表单，生成失败不丢弃成功提取结果。
- 管理员审核重查全部现有结果；普通字段查看零模型请求。后续重试可限定失败项。
- 旧 #85 的页面不铺开逐字段建议要求由新需求扩展为按需侧栏，英文科学值及原始来源语言约束继续适用。

## 实施核对后的补充

- #53 的按论文研究方法自动补写超导类型与 Tc 方法规则，仍须满足本 Feature 的逐字段来源类别、简短理由及管理员裁决约束；确定性单位换算和元素数量计算继续保留。
- 旧状态级计算/实验条件已迁移至物性记录，侧栏对此类汇总只读，替换建议使用实际物性记录入口，避免产生无法保存的旧表示。
- 已保存候选跨来源批次引用时，用完整来源目录验证旧引用；模型新引用仍只在实际输入批次中定位。
- 后台保存锁定当前结果，优先保留数据库最新人工决定。支持资格被新复核撤回时，使尚未提交的旧接受草稿退出接受状态，输入保留；准备提交时再校验一次。
- 旧值、旧候选、人工理由与引用通过独立只读 history 归档，不参与当前版本门禁。上传转论文使用文件 ID 映射重新绑定当前引用，同文同页不猜文件。

## 2026-10-10 自动填写与侧栏更正

- 用户明确更正此前“推断和推测只保存待采用建议”的解释：有效推断与通用知识推测直接进入主表单，侧栏只展示简短且可核验的 AI 理由；直接记载不需要额外替换建议。
- 初次提取继续优先写入直接记载和忠实概括。后续核对模型用当前字段、论文来源和字段结构提出推断或推测；服务端校验类别、类型和引句，再将符合覆盖规则的值写入草稿并重建字段快照，避免旧内容哈希为新值背书。默认只填空值或 `unknown`，不覆盖非空原文值。
- 自动填写的来源类别、理由和版本与字段绑定。论文推断需可定位引句；通用知识推测可无引句，但不能被判为论文支持。上传可以送审，管理员批准仍需独立逐项理由。用户改动主表单后，旧 AI 理由只作为历史。
- 旧侧栏同时显示“没有可靠的 AI 替换建议”和当前值的 `material/relation/page/quote` 编辑器，根因是 `editable_fields` 被无条件渲染。移除该编辑器，保留主表单作为唯一值编辑入口；历史接受草稿按现有版本门禁处理，不暗中把不可见候选应用到当前值。
- **决策 / 理由**：自动保存不因理由未填中断；显式提交或管理员批准才执行完整性门禁，否则用户无法保存进行中的编辑。上传证据与缺证均要求简短判断理由；缺证另需原因。以规范化值和稳定字段身份判定修改，避免每次键入都产生新审核事件。
- **决策 / 理由**：人工证据使用专用持久记录和私有文件目录，不借用 `PaperFile` 或 `paper_quote`。文字、截图、文本文件都标记真实提交者、来源说明、摘要和版本，能供审核员与 AI 使用，却不伪装为论文作者原文。
- **决策 / 理由**：图片 AI 审阅必须有真实图像输入或经校验提取结果；先用服务端随机六位数字图片校验当前模型确实能读图，再发送人工截图。仅当校验通过且审核请求成功时标记“AI 已读取”；校验失败、模型拒绝图片或请求失败均标“AI 未读取”，交给人工审核。接口成功并不保证模型看见了图片：本次配置的模型接受了合成图片请求，却没能识别独立随机数字图片，因此不能据此标已读。把人工截图简单拼成论文文本会丢失来源身份并可能误判，故不采用。
- **备选方案**：仅把图片路径和人工理由塞入现有核对结果 JSON，初期少一张表，但临时任务清理、审核转接、权限下载和孤儿文件回收无法获得清楚的所有权边界，故不采用。
- **兼容边界**：旧记录无人工修改说明时保留历史原样，不批量生成假理由；新规则只对本次实际修改与后续显式提交生效。审核员已有裁决理由与上传者的修改理由职责不同，均须留痕。
- **现有门禁差异**：当前上传遇到没有论文有效出处且未采用建议时保留草稿；新增人工修改说明允许此类修改进入待审，但结果仍标“人工待审来源”，管理员不能仅凭上传者的理由批准。必须在提交 API 与批准 API 两侧分别验证，不能只放宽前端按钮。

## 2026-10-10 旧 PDF 区域定位补充

## 2026-10-10 首页来源与 300 DPI 局部图

- **现状证据**：H3S 首页标题存在于 PDF 和解析 Markdown 的 heading，原核对只检查 chunk 正文，引句因此落到末页“How to cite”。旧区域渲染整页 `scale=1.5`，约 108 DPI；H3S 首页整页 300 DPI 为 2481×3260 像素、约 1.35 MB，标题局部约 1758×511 像素，局部渲染既清楚又节省传输。旧草稿的部分引句缺页码或页码与原 PDF 不符。
- **决策**：主 PDF 首页标题与署名经当前文件 SHA-256 和实际文字核验后优先作为当前依据；普通引句唯一匹配修正页码，重复或失去定位的 PDF 引句退出无依据的 `supported`。定位与语义支持仍分别判断。
- **决策**：使用现有 PyMuPDF `search_for`、文本行 bbox 和 `get_pixmap(dpi=300, clip=...)`；局部图只含引句及同栏上下各三行，跨页/跨栏分开，图表加入可信邻近说明。缩放只改变视窗，不改变图片来源或偷偷降低 DPI；扫描件原图本身不足 300 DPI 时提示真实限制。
- **历史边界**：用户明确要求从当前待审目标及其旧核对快照中删除被首页证据替换的末页标题来源。按目标备份与事务修复，保持其他审核内容；已批准论文不参与批量修正。

## 2026-10-11 保存与结构家族布局问题调查

- **已验证代码事实**：`ManualEvidenceSection.save()` 只向人工说明接口发送 `expected_version`、理由、缺证原因及文字条目，成功后只 `setSaved`；组件没有保存成功回调。`EvidenceWorkflow` 仅传入 target、record、version，因此这个按钮成功也不会关闭侧栏。它与外层 `accept()` 的保存当前值、刷新版本、会话检查及关闭流程相互独立。
- **已验证代码事实**：缺少 endpoint 或 version 时 `save()` 直接返回，按钮没有对应的不可用原因。`backend/api/evidence.py` 在说明版本不符时返回 409；`UploadTaskEditor` 有 5 秒自动保存，但人工说明按钮未串联该保存流程。由此存在时序风险，尚未取得用户这次点击的请求响应，不能认定其确实发生 409 或数据未落库。
- **已验证代码事实**：结构家族用 `Autocomplete multiple freeSolo`，值在 `onChange` 写入状态，文本输入与已选择项不等价。实施时应复现“只键入名称后直接点击侧栏”的路径，确认未提交文本是否参与保存，不能靠截图推断已经写入。

- **设计决策**：在既有工作流中串联“保存当前值 → 刷新字段版本 → 保存说明 → 反馈并关闭”，复用当前字段身份与会话保护，不建立新持久层，不删除 409 保护。部分失败如实反馈；相邻字段值变化不得自动继承旧版本说明。

- **交付边界**：本次仅更新 Issue 与 Spec 系列文档。上述设计尚待实施；截图与代码调查不能替代真实持久化和浏览器验收。

## 2026-10-11 决策：模型归纳理由与来源核对分离

- **决策**：服务端以 `check_mode` 和真实来源类型识别模型归纳；当前核对的具体 `reason` 可在有效旧结果缺少 `ai_reason` 时作为同版本解释，后续结果明确保存 `ai_reason`。侧栏只展示可核查的原文依据到当前结论说明。
- **理由**：H3S 材料家族旧结果已经解释“富氢材料 → 氢基超导体”，但 `ai_reason` 为空且 `source_kind=paper_quote`，前端因此显示固定直接记载文案。逐个字段修补会继续漏掉其他归纳字段。
- **备选**：只改前端兜底不能保证新核对产生具体理由，也不能覆盖提交后的正式来源；另建理由表增加不必要的持久化复杂度。
- **边界**：作者原列关键词、确定性派生值和人工改写各用自身来源说明；不暴露模型内部逐字思维，也不以理由代替可定位本文证据。


## 2026-10-16 调查：无关编辑导致程序派生项临时失效

### 已验证事实

- `frontend/src/lib/evidenceFields.ts::evidenceFieldAffected` 把 `structure_optimization`、压强等识别为材料上下文；只要同状态记录带 `provenance.kind=derived` 就返回受影响，不检查该派生规则的实际输入。
- 用本机 Node 加载 TypeScript 编译器、转译并执行工作区的真实函数，构造状态 2 的元素数、群号与晶系三条派生记录。分别传入 `structure_optimization`、`pressure_value_gpa`、`reported_space_group_symbol` 和 `material` 的变化，四次均返回这三条记录全部受影响；另一状态的核处理变化返回空。前两次已直接证明本次误失效，符号变化也错误波及元素数。
- `MaterialStatesEditor.emitStates` 用 `changedScientificFields` 通知实际变化，上传与管理页均接入 `EvidenceWorkflow.invalidate`。`EvidenceFieldMarkers` 还从原生 input/change 通知；`invalidate` 没有先验证该事件对应的规范化值是否真正变化，并会清除受影响项的理由、建议与人工确认，设置 `stale=true`。
- `EvidenceFieldMarkers.evidenceProblem` 将 stale 作为问题，控制标签和边框；工作流 issues 同时进入材料卡片问题计数，因此这不是三个控件自己的数值校验错误。
- `UploadTaskEditor` 等待 5000ms 自动保存，成功且版本未变化后调用 `refreshAfterSave`，重新读取服务端结果。后端 `public_snapshot` 再执行 `apply_derived`，可以根据仍有效的输入恢复支持状态。这条调用链解释用户描述的几秒后恢复；未在用户真实登录会话测量该时序。
- 服务端 `scientific_evidence.state_records` 已保存明确 `dependency`：元素数指向化学式；群号和晶系在确为程序派生时指向报告空间群符号。`public_snapshot` 返回包含这些信息的记录，前端类型与影响计算尚未使用它。单位换算同样有原始输入依赖。
- 后端物性 `record_claim` 包含材料科学条件，真实条件变化可能使数值未变的物性断言过期。因此不能简单改成“只有目标输入框的值变化才核对”，也不能取消所有跨字段失效。

### 已确认设计及取舍

复用已有字段值比较、稳定身份和服务端 `dependency`，由共享影响范围计算统一处理真实输入依赖及科学上下文；派生字段不再使用“同状态全部 derived”的分支。前端事件负责通知实际更改，工作流在清除理由前再次过滤无效通知；原生与程序事件合并处理，不能靠等待自动保存纠错。

不新增数据库表、第二套永久核对存储或新的 AI 调用。优先扩展已有 `EvidenceRecord` 可选依赖类型并消费既有响应。旧响应缺失依赖时，按已知规则明确解析输入并验证，不能直接认定全状态派生项失效或全都有效。遇到未知规则应先记录具体限制与保守状态，再修订设计，不能猜测科学依赖。

验收需要同时覆盖真实受影响项仍会失效和无关项不误伤；仅截图颜色、纯源码匹配或单个模拟函数不能证明浏览器与持久化修复完成。


### US11 实施结论

依赖误扩散已修复；实际值变化在事件完成后统一计算，前端失效不会靠后续保存恢复来纠错。服务端部分派生项原 claim 含整个状态上下文，现明确其输入/单位与材料身份，避免无关条件进入自身摘要；旧摘要不自动获得新资格。来源实际失效仍由 apply_derived 判定，物性科学条件契约不改。专项与基线结果见[字段隔离验证](field-isolation-validation.md)。


## US12调查与方案理由

问题跨越前端定位与后端断言粒度：draft_records/complete_snapshot默认构造整条物性记录，EvidenceFieldMarkers在没有细项paths时回退record，再复用第一个可见标签；只删除红色CSS会掩盖问题，不解决归属。历史旧快照缺独立事件作者/时刻，EvidenceWorkflow又flatMap展开多记录，不能仅换排版就承诺完整审计。

采用独立Demo验证细项入口及事件行：方法只审核方法，共用设置和每个结果分别定位；父标题不做集合入口。主字段名维持#94设置语义，核对标记进入同字段来源/历史。新数据未来记录真实事件元数据；旧缺失信息明确降级。具体存储方案/API与兼容成本待正式设计，不在Demo阶段改变数据库或伪造历史。
