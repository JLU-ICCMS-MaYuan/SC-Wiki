## 摘要

Makefile 保留薄入口；Bash 负责最初的系统检查与 Conda 引导，Python 负责配置、清单、导出恢复和阶段状态。复用 `scripts/dev.sh` 的服务定义，修复环境路径假设，避免再维护一份服务启动表。两个命令使用同一版本清单和数据清单。

## 技术上下文

- **语言**：Bash、Python 3.12；现有 Go 服务要求 Go 1.25 系列；前端 React 19/Vite 5，使用 Node 22 LTS。
- **存储**：MySQL 8.4、Redis、Neo4j 5.26.29、Qdrant 1.19.0；GROBID 0.8.1 容器。
- **依赖入口**：`docker/requirements.txt`、`frontend/package-lock.json`、`goserver/go.mod` 与 `go.sum`。补充本地部署的版本与校验清单，不复制整套依赖定义。
- **平台**：Ubuntu 22.04 x86_64 为验收基线，含 WSL2；用户已取消 Ubuntu 24.04 的必需验收，不把该平台测试作为提交门槛。
- **测试**：pytest、现有隔离 MySQL 迁移测试、Shell 语法检查、真实数据库导出恢复、浏览器/API 冒烟和干净机器演练。
- **规模**：本地单实例全量迁移；不设置固定时长保证。逐文件流式导出和散列，避免整库或完整压缩包常驻内存。
- **资源预检**：按导出/恢复清单估计数据和临时副本空间，再加依赖安装空间及 20% 余量；对无法估算的导出先落临时区计量，再发布包。运行时磁盘不足仍须失败收尾。

## 环境与配置流程

1. 检查系统前置条件、平台、目标状态及包完整性，汇总错误。Docker 必须存在且当前用户可调用；不修改系统用户组。
2. 按 Research 的顺序定位 Conda；无 Conda 时将经校验的 Miniforge 安装到 `.local/miniforge`。环境创建和依赖安装只操作选中的 `sc-wiki`；已有 Python 非 3.12 则失败。
3. 验证/安装固定版本基础服务，Python 使用选定环境的 `python -m pip`，前端使用 `npm ci`，Go 使用模块校验。完成后执行 `pip check`、关键模块导入和各服务版本检查；把实际版本写入部署记录。
4. 缺少 `.env` 时，生成独立 MySQL/Neo4j/JWT 凭据和本机绝对数据目录；`DATABASE_URL` 与 `RAG_DATABASE_URL` 指向同一业务库，分别使用同步/异步驱动。URL 密码正确编码，凭据不进入进程参数或普通日志。
5. 保持当前默认端口，不自动寻找替代端口：MySQL 3307、Redis 6379、Neo4j 17687/7474、Qdrant 6333/6334、Python 8000、Go 8080、前端 5173、GROBID 8070。端口冲突应明确阻断；即使健康端点返回成功，也要验证进程/容器属于本项目。
6. 便携部署的应用与数据库监听回环地址；前端通过启动参数覆盖现有 Vite `0.0.0.0` 默认。不改防火墙、系统 PATH 或 shell 初始化文件。

## 打包流程

1. 要求源码工作树干净，记录 `HEAD`；读取当前项目连接与路径配置，拒绝非本地数据库目标。读出业务库全部表和对象、全部迁移 revision、图和向量集合、可恢复草稿和引用文件清单。
2. 获取项目操作锁，记录进程状态；暂停调度/请求入口，优雅结束应用请求并检查后台作业。遇到排队、执行中、延迟重试作业即退出，不自动清队列。确认停写后停止其余写入进程。
3. MySQL 使用事务一致逻辑导出，包含二进制字段、例程、触发器和事件，禁用 GTID 导入副作用；不含 MySQL 系统库。Neo4j 停止业务数据库后使用原生 dump；Qdrant 导出各集合快照、配置和别名。
4. Redis 仅导出 [数据模型](data-model.md) 的业务键；复制允许目录和已登记引用文件。输出数量、结构摘要与文件 SHA-256。打包前不修改源记录的路径，路径映射另存清单。
5. 源码来自 `git archive HEAD`，归档顶层为 `sc-wiki/`，数据在该目录的 `.deployment/`。先写临时产物，所有组件成功后原子发布压缩包及外部 SHA-256 文件。
6. 无论成功或失败，尝试恢复原运行状态；不得调用旧迁移步骤改变源库。源恢复失败返回非零，输出已生成包的位置和服务失败清单，避免把“包存在”误报为整个操作成功。

## 恢复与无包初始化

1. 自动发现 `.deployment/manifest.json`；若用户指定 `BUNDLE`，要求代码摘要与当前包源码匹配，否则指示从该包解压目录执行。没有包才走新实例初始化，不把损坏包当作无包。
2. 核验格式、清单、摘要、容量、版本、目标配置、数据目录和进程归属；拒绝不属于本次部署的非空目标。持有操作锁，记录阶段后创建本次专属临时数据目录。
3. 先启动临时基础服务，生成独立数据库账号；原生导入 MySQL/Neo4j/Qdrant，恢复草稿、附件并做路径映射。所有导入必须限制为本次项目库与临时目录，不能用系统数据库管理员凭据操作其他实例。
4. 恢复模式要求导入库 revision 集合与包及源码一致，结构摘要、约束及数据清单通过。无包模式仅对空业务库执行源码声明的全部 revision 迁移与元素种子；不得在非空库自动 `stamp`。
5. 在启动业务进程前完成表、图/向量、草稿和文件检查；把临时目录提升为正式 `.data`，更新运行配置的目标路径，原子记录恢复已提交。记录和目录提升之间中断时，通过包标识与数据目录内的完成标记判定，不再次导入。

路径转换还包含一个有界适配：恢复前确认仍有效的返修草稿，转换后仅重算这些草稿的并发
基线。原有冲突保持冲突，科学核对指纹和审批记录不变。Redis 草稿恢复后同步保存 RDB，
便携实例正常停止也必须保存，不能使用旧实例的 `shutdown nosave`。
6. 启动全部本地基础服务和应用，验证认证连接、真实读查询、前端到 Go/Python 链路和 Worker 注册。便携实例的 `make start` 只核验受测 schema，不重放历史迁移。
7. 输出本机地址、部署报告、缺少的外部配置和恢复统计。无包模式额外提示使用既有管理员创建脚本；恢复模式保留原账号。

## 阶段与依赖

按 [Tasks](tasks.md) 执行：事实与版本核验 → 共享环境/配置 → 新实例部署 → 一致打包 → 恢复/重试 → 真实演练与文档更新。同一共享文件串行修改。打包与恢复共用清单契约；任何依赖下载、迁移或数据回读失败均阻断交付。

## 必要复杂度

临时目录、分阶段记录和草稿白名单是为了保护现有数据、跨存储一致性及不重放任务。首版不增加合并恢复、通用插件框架或远程部署协议，控制维护范围。
