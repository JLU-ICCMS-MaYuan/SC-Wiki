## 决策及理由

### 1. 保留宿主机应用和 GROBID 容器

复用 `dev.sh` 的服务编排，修正环境定位和初始化边界。避免为本需求另建一套全 Docker 部署方式，满足用户复用 `sc-wiki` 的要求。保留 Docker 前置检查，不自动安装系统服务。Node 采用 22 LTS，Python 采用 3.12，Java 采用 21，MySQL 采用 8.4 系列；具体构建版本统一进入受测版本清单。

当前脚本记录 Go 1.25.14、Neo4j 5.26.29、Qdrant 1.19.0、GROBID 0.8.1，这些是实现时优先核验的基线，不代表本轮验证了下载源可达。实施先验证版本和校验和，再固定官方来源/镜像摘要；不使用浮动 `latest` 或未经校验的代理下载。

### 2. 一份部署配置事实来源

Conda 查找顺序为显式 `CONDA_EXE`、`PATH`、已有 `CONDA_ROOT`、常见安装位置、项目私有安装。通过 `conda env list --json` 获取环境前缀；多处同名且无法唯一定位时要求显式选择，不猜路径。所有 Python/pip 调用使用选定环境的绝对路径；Node、Java、MySQL、Redis 优先在同一环境提供，Go/Neo4j/Qdrant 放项目运行目录。

配置生成器使用标准库解析和渲染，拒绝命令替换、反引号和任意 shell 代码；保留普通 dotenv 的引号与 `${NAME}` 引用语义。服务启动同样改用解析后的环境，不继续 `source .env`。新 `.env` 权限为 0600，旧 `.env` 字节保持不变；不兼容配置需要用户修正后重试。

### 3. 可校验源码包加数据库原生导出

源码采用干净 `HEAD` 的归档，不携带 `.git`、依赖安装目录、日志、PID、旧配置或整个 `.local`。MySQL 使用逻辑导出，Neo4j 使用停库后的业务数据库 dump，Qdrant 使用各集合快照及别名清单；不要复制运行中的存储文件。

只导出业务 MySQL 库，不导出 `mysql` 等系统库和数据库登录账号。携带业务例程、触发器、事件的定义；恢复时将旧 DEFINER 映射为目标项目服务身份，不授予全局权限。带有无法处理的跨库引用或启用事件调度等情形预检拒绝，不能悄悄丢对象。

Neo4j 只迁移业务数据库，不搬运 `system` 库的认证状态；目标初始化新密码。向量库恢复集合配置、点和别名，不调用 Embedding 重建索引。

### 4. 停写窗口和草稿保留

打包记录原服务状态，暂停调度与应用入口，等待已有请求结束；检测 Redis/RQ 运行、排队、延迟重试作业和数据库侧未完成工作。存在作业则恢复原状态并失败，不强杀。完全停写后再导出各存储；等待宽限期为 300 秒，超时不发布包。仅停止/恢复确认属于本项目的进程。

Redis 采用上传业务键白名单导出结构化 JSON，只保留状态、草稿与有效索引；不导出 RQ 序列化任务、锁、会话、验证码或 `upload:llm:*`。保留绝对到期时刻和业务清理时刻，不因搬迁延长原有保存期限；恢复时跳过已经过期的记录并报告数量。草稿重新发起解析时需重新提供模型凭据。

### 5. 同版本恢复和明确迁移模式

迁移包要求源库版本集合与该源码受测头集合相等，且真实结构符合迁移/模型约束。不一致时停止打包，列出差异，让独立维护流程处理；打包本身不升级源库。

恢复 SQL 后只核验版本集合和真实结构，不执行历史升级，也不 stamp 伪造完成。新空库则按源码固定头集合执行从零迁移并填充基础数据。`dev.sh` 对已经验证的便携部署走同一版本检查入口，不能又调用旧迁移逻辑改变数据。旧部署未带便携记录时保留其原行为，本 Feature 不批量迁移旧实例。

明确不把 `create_all` 加 `stamp` 当作完整迁移，不自动合并 Alembic 分支，不把全部历史迁移的破坏性动作搬到普通启动步骤。

### 6. 空目标和有限恢复重试

先预检，后在项目所有的临时目录恢复；未验证成功前不开放应用或 Worker。完成后把数据目录提升为本次实例，记录包摘要。中断发生在提升前时，只重建本次带所有权标记的临时目录；提升后重试只检查和启动，不重新导入。

不实现合并或覆盖恢复。配置或已有数据无法判定归属时直接拒绝。此限制降低误覆盖成本，也使重复执行的行为可验证。

### 7. 敏感配置与能力报告

迁移业务账号及密码哈希，重新生成目标 JWT 和数据库凭据，旧登录令牌不继承。外部模型与 SMTP 凭据、运行时模型覆盖配置不装入普通包；目标可通过部署后的本地配置或已有管理界面补充。

报告分别列“基础服务”“AI/Embedding 配置”“SMTP 配置”“实际外部调用验收”；有配置不等于验收通过。普通健康检查不发模型请求、不发邮件。

## 被拒绝的方案

- 压缩整个仓库目录：会混入旧路径、密钥、数据库裸目录及不可搬迁的运行环境。
- 只导出已有 JSON 导入器覆盖的用户/论文：遗漏动态表单、审核历史、社区、版本草稿等表。
- 把 Redis 直接当缓存丢弃：会丢失仍保存在 Redis 的草稿。
- 原样恢复 Redis RDB：可能携带用户 API Key，重放旧队列和锁。
- 所有失败都跳过：无法保证最终实例完整，也难以定位错误。

## 实施前必须验证的事实

这些是技术验证任务，不是已完成验收：固定依赖的实际下载/安装、MySQL 从零多头迁移、源数据库结构一致性、Neo4j/Qdrant 原生导出恢复、所有持久路径字段登记、RQ 与新闻队列的停写行为。对应任务见 [Tasks](tasks.md)，任一失败都不得以静态检查代替。
