# Feature 规格：本地实例打包与本地、Docker 部署

**GitHub Issue**：[ #112](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/112)

**创建日期**：2026-09-21

**状态**：实现与隔离验证中；协作状态以 GitHub Issue 为准，证据见 [验证记录](validation.md)。

## 背景与目标

新机器没有旧 `.env`，也可能没有 `sc-wiki` Python 环境。现有 `make setup` 要求这两者已存在，`make start` 只负责启动已准备好的服务。现有迁移脚本面向原开发机器的 Docker 数据卷，不能作为通用搬迁工具。

源机器运行 `make pack` 得到包含源码与业务数据的通用迁移包；同一份包可以用于本地或 Docker 部署。本地目标执行 `make deploy`，完成依赖准备、配置生成、数据恢复、服务启动和检查；Docker 目标通过专用恢复入口使用同一份包。源码仓库没有迁移包时，本地部署入口也支持建立空的新实例。当前 Docker 恢复入口尚未实现，不能把已有 Docker Compose 启动能力当作包恢复能力。

规划已建立，用户继续指令后进入实现。验证使用人工数据和隔离实例，不对当前业务数据库执行导出、迁移或覆盖。

## 用户场景与验收

### 用户故事 1：准备新机器（US1，P1）

部署者不需要寻找旧 `.env`，也不需要记住各服务的安装顺序。

**优先级理由**：解决首次部署的直接阻塞。

**独立验收**：在支持的平台和系统前置条件就绪后，从源码建立一个没有业务数据的新实例。

1. **假如**没有 Conda 和 `.env`，**当**执行部署，**那么**在用户可写目录准备 Conda、创建 `sc-wiki`、安装依赖并生成配置。
2. **假如**已有兼容的 `sc-wiki`，**当**执行部署，**那么**复用实际路径并补齐依赖；不要求环境必须在 `~/miniconda3`。
3. **假如**已有环境的 Python 版本不兼容，**当**执行部署，**那么**停止并说明版本差异，不删除、重建或原地升级 Python。
4. **假如**没有迁移包，**当**部署完成，**那么**数据库结构与基础元素就绪，输出既有管理员创建命令；不生成默认网站账号。

### 用户故事 2：打包当前实例（US2，P1）

部署者得到一个可搬迁的源码与数据包，不必逐项查找数据库和附件。

**优先级理由**：数据库记录、附件和索引必须一起保留，才能复现现有实例。

**独立验收**：在隔离源实例生成包，检查其源码版本、完整清单、数据数量和文件校验信息。

1. **假如**本地实例可访问且没有未完成后台作业，**当**打包，**那么**短暂停止应用写入，导出全部业务表、图和向量数据、可恢复草稿及附件，结束后恢复原有运行状态。
2. **假如**有正在执行或等待执行的作业，**当**打包，**那么**不强制终止或搬运作业，给出待处理原因，不发布可用包。
3. **假如**任一必要数据源或引用文件缺失，**当**打包，**那么**失败而不是静默省略。明确的空数据库或空集合可以记录为零。
4. **假如**源码有未提交改动，**当**打包，**那么**要求先完成提交；不把工作树与另一提交的数据契约混装。

### 用户故事 3：恢复并验证（US3，P1）

部署者在不同用户名、不同路径的目标机器运行一个部署命令即可使用已迁移数据。

**优先级理由**：这是整个功能的最终用户结果。

**独立验收**：使用 US2 的固定测试包，在全新目标实例恢复，并通过真实页面和 API 访问数据。

1. **假如**目标没有 `.env`、依赖和业务数据，**当**在解压后的目录部署，**那么**自动发现包内数据，建立本机配置并恢复。
2. **假如**包包含用户、动态表单、论文版本、审核历史、草稿和附件，**当**恢复完成，**那么**保留业务身份和关系，原账号密码可登录，附件在新路径可访问。
3. **假如**再次执行同一部署，**那么**保留本机配置和新增业务数据，不重复导入，也不旋转已生成的密码。
4. **假如**没有外部 AI 或邮件凭据，**那么**可启动基础服务，但清楚列出 AI、Embedding、邮件等未就绪能力，不声称全功能验收通过。

### 边界与异常场景

- 目标目录存在其他数据或其他包的恢复记录时拒绝覆盖；首版不提供强制覆盖参数。
- 包损坏、版本不兼容、跨目录符号链接、未知数据路径、磁盘不足、端口被其他实例占用时，在导入前拒绝操作。
- 恢复中断后保留明确的失败阶段；只恢复本次创建的临时目录，不清理原有目录。
- 有效上传草稿需要保留；会话、验证码、限流、任务锁和可执行队列不迁移。
- 源实例限于当前项目管理的本地服务。外部程序直接写库不在一致性保证范围内，打包前必须停止这类写入。

### 用户故事 4：同包部署到 Docker（US4，P1）

部署者从本地实例生成一次包后，在目标选择本地或 Docker 运行，不需要重新导出或手工转换业务数据。

**独立验收**：把同一份固定包分别恢复到空本地实例和空 Docker 实例；两者均满足 SC-002、SC-003，原包及其校验信息保持不变。

1. Docker 目标保留业务表结构、动态表单定义、账户、论文、审核历史、草稿、图、向量和附件；不另造 Docker 专用业务表或数据包。
2. 数据库地址、凭据和附件路径由目标部署方式配置；容器内路径与宿主机路径分别处理，不对 SQL 或 JSON 全文替换。
3. Docker 恢复只接受新实例；数据校验通过前不启动应用和 Worker；正常启动不得对恢复数据重放历史迁移。
4. 本轮不增加从 Docker 实例打包的能力，也不扩展跨版本升级或已有数据库合并。

## 需求

### 功能需求

- **FR-001**：提供 `make deploy` 与 `make pack`，保留已有启停入口，并让缺少初始化的错误指向新入口。
- **FR-002**：预检操作系统、架构、基础工具、Docker 可用性、网络、端口、磁盘与目录权限；先报告阻塞项，再进行安装或恢复。
- **FR-003**：定位并复用兼容的 `sc-wiki` Conda 环境；不存在则创建；没有 Conda 时使用项目私有安装，不修改全局 shell 配置或系统 Python。
- **FR-004**：安装并检查 Python、Node/npm、Go、MySQL、Redis、Java、Neo4j、Qdrant 和 GROBID 的所需版本；对版本冲突明确失败，不以“文件存在”代替可用性检查。
- **FR-005**：首次生成可用的本地连接配置和随机凭据，已有配置不覆盖；读取配置不得执行其中的 shell 表达式。
- **FR-006**：迁移包绑定一个已提交的源码版本，携带完整数据清单、数据格式版本、依赖版本、校验信息及包标识。
- **FR-007**：完整导出项目业务 MySQL 数据库的表、约束、数据、触发器、例程、事件及迁移版本；不得只挑选少数已知业务表。
- **FR-008**：保留 Neo4j 业务图、Qdrant 集合与别名、必要应用文件和可恢复上传草稿；不把图或向量库假定为空，不把 Redis 全部视为缓存。
- **FR-009**：在受控停写窗口内形成一致数据包；运行和排队作业阻断发布；成功或失败后均尝试恢复打包前的进程状态，并报告恢复失败。
- **FR-010**：包中排除源 `.env`、外部 API/SMTP 凭据、本机认证配置及 Redis 瞬态执行数据；数据库中的网站账号、密码哈希与权限属于迁移业务数据，必须保留。
- **FR-011**：恢复只写入新的项目实例；导入前验证包、目标和版本；同一包成功部署后重跑不得导入或改写已有业务数据。
- **FR-012**：恢复后保留全部迁移分支和原表单/审核语义；核验真实结构，不盲目标记迁移完成，不自动对导入数据执行历史破坏性迁移。
- **FR-013**：将受支持的本机路径引用重定位到目标数据根；只改已知路径字段，不能对论文正文、证据、JSON 或 SQL 做全局字符串替换。
- **FR-014**：记录安装与恢复阶段；失败退出非零且不启动消费任务的进程；中断可在核验本次临时目录所有权后重试。
- **FR-015**：完成数据库认证、图/向量查询、应用请求链路、后台进程与数据清单检查后才报告基础部署成功；外部能力另列配置及真实验收状态。
- **FR-016**：无包部署时建立全新空业务库和基础元素，沿用既有管理员创建方式；不重置恢复包中的网站账号。
- **FR-017**：提供隔离集成测试和干净机器验收步骤，覆盖跨路径搬迁、草稿保留、凭据排除、多迁移分支、失败重试和不覆盖已有数据。
- **FR-018**：同一个本地源迁移包支持本地和 Docker 两种目标；共用格式、数据范围及校验规则，分别适配运行环境、连接和路径。Docker 目标沿用 FR-010–FR-015 的凭据、空目标、版本核验、重定位、中断恢复和验收要求；不要求目标安装 Conda。

### 关键实体

- 迁移包：对应一个源码提交和一次一致数据导出的可校验交付物。
- 部署清单：描述源版本、数据范围、数量、文件摘要和兼容要求，不保存凭据。
- 本机部署记录：描述本目录的包标识、依赖路径和执行阶段，不承担 GitHub Issue 的协作状态。
- 可恢复上传草稿：没有执行中作业、尚未过期的上传状态及草稿；保持原业务归属和生命周期。

## 成功标准

- **SC-001**：在 Ubuntu 22.04 x86_64 的干净测试环境，以及 WSL2 Ubuntu 验收环境中，无旧 `.env`、无 `sc-wiki` 时，仅需一个部署命令完成基础启动；所需系统前置条件单独列明。按用户要求，Ubuntu 24.04 不列为必需验收平台。
- **SC-002**：恢复前后业务表清单、逐表行数、规范化结构摘要、图节点/关系数量、向量集合及精确点数、可恢复草稿数量一致；全部包内文件校验通过。
- **SC-003**：换用户名和目录后的实例能够登录原账号、读取表单定义与审核历史、打开 PDF/结构附件、继续编辑尚有效的草稿；不自动重放旧作业。
- **SC-004**：重复部署和全部故障测试不覆盖既有 `.env` 或业务数据；损坏包及中断导入不显示成功。
- **SC-005**：测试植入的 API Key、SMTP 密码、JWT 密钥、Redis 凭据键及运行时模型配置不会出现在包与普通日志中。
- **SC-006**：记录真实干净环境验证结果和外部能力的已配置/未配置/已验证状态；文档更新后才允许关闭 Issue。
- **SC-007**：同一个包在隔离本地和 Docker 目标均完成恢复，全部数据清单核验通过；两端原账号登录、表单、审核历史、附件和有效草稿访问通过，并验证 Docker 重跑不重复导入、不执行历史迁移。

## 假设与依赖

- 用户在平台建议后要求“继续”，本版按可联网 Linux x86_64（含 WSL2 Ubuntu）推进；这不是已经完成的平台验收。
- Bash、GNU Make、系统 Python 3、curl、tar、Git（源端）和可用 Docker 为系统前置条件；脚本不使用 sudo 安装 Docker 或修改防火墙。
- 支持当前本地实例导出和同版本源码恢复；依赖安装需要网络，不承诺离线包。
- 默认迁移全部业务数据，包括账户信息和未公开论文；包是私有备份，不作为公开示例数据发布。
- 外部凭据在目标端重新配置；基础部署成功不代表收费模型或 SMTP 实际调用成功。

## 范围外事项

- 原生 Windows/macOS/ARM、生产集群部署、域名证书、开机自启、数据库合并、覆盖恢复、零停机备份、跨版本升级和自动修复历史坏数据。
- 复制整个 Conda 环境或旧机器数据库物理目录；打包正在运行的 RQ 作业；批量重建向量所产生的外部模型调用。
- 对当前业务实例执行真实数据迁移、自动发布或推送；命令实现及隔离人工数据验证由 [实施任务](tasks.md) 跟踪。

## 澄清记录

### 2026-09-21

- 用户要求将本地部署命令由 `make locallydeploy` 更名为 `make deploy`；仅改变命令名称，参数、包格式和部署行为不变。

- 原始需求：复用或创建 `sc-wiki`，自动配置依赖；提供数据库打包与另一机器一键本地部署；创建 Issue 和 Spec。
- 用户明确取消 Ubuntu 24.04 验收要求，并要求先提交当前实现；本次按已有隔离验证提交 Git 记录，其他未验收项继续追踪，不等同于关闭 Issue 或授权推送。
- 用户纠正目标并确认：本地实例打包，同一份包可用于本地或 Docker 部署；Docker 仅作为恢复目标，不作为本轮打包来源。原先只设计本地恢复属于需求理解遗漏。Docker 适配设计见 Plan/Research，实施与真实验收尚未完成。
- 平台建议后用户回复“继续”：采用上述首版平台默认值，继续创建 Issue 与完整规划。
- 工程默认值：空目标恢复、不覆盖已有数据；外部凭据不随普通包迁移；需要 Docker 的部分明确列为前置条件。这些是本版设计选择，不表述为用户逐项确认。
