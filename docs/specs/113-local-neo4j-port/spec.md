# 修复规格：本地 Neo4j 端口冲突

**GitHub Issue**：[#113](https://github.com/JLU-ICCMS-MaYuan/SC-Wiki/issues/113)

**创建日期**：2026-09-21

**文档性质**：补录已确认修复的需求与验收；协作状态以 GitHub Issue 为准。

## 背景与目标

执行 `make start` 时，Neo4j 因本地 7687 端口被占用而退出，脚本最终显示等待 120 秒超时。
本次将本地连接端口固定调整为 17687，使开发者能够保留 Windows 向日葵运行并启动 Neo4j。
实现提交为 `7a614bb3`，本规格不扩大该提交的修复范围。

## 用户场景与验收

### US1：恢复本地数据库连接（优先级：P1）

开发者启动本地 Neo4j 后，应用使用现有账号连接数据库，无须停止占用旧端口的软件。

**优先级理由**：解除本次启动失败的直接阻塞。

**独立验收**：单独启动 Neo4j，完成认证连接、只读查询及管理入口的连接地址检查。

1. **假如**旧端口被占用且 17687 可用，**当**开发者启动本地 Neo4j，**那么**服务在 17687 就绪。
2. **假如**服务已就绪，**当**客户端使用现有账号连接新地址，**那么**认证通过且只读查询成功。
3. **假如**管理入口可访问，**当**客户端获取数据库连接地址，**那么**得到 17687 而非旧端口。

### US2：保持本地配置一致（优先级：P2）

开发者生成本地配置或查阅启动说明时，获得与服务实际监听一致的端口。

**优先级理由**：避免配置重新生成后恢复旧地址。

**独立验收**：配置生成结果、启动参数和文档中的本地地址一致。

1. **假如**源配置含旧 Neo4j 地址或缺少该项，**当**生成本地配置，**那么**生成结果使用 17687。
2. **假如**使用已有本地安装，**当**应用此次端口调整，**那么**服务与客户端配置同步，不依赖重新安装数据库。

### 边界与异常场景

- 17687 必须可用；本次不保证任意机器均无端口冲突，也不自动寻找替代端口。
- 已有运行进程需要加载新配置；仅修改文件不会改变已启动客户端的连接地址。
- 旧端口被占用的软件及其生命周期不由本项目管理。
- 只验证 Neo4j 链路，不能据此判断完整 `make start` 或 AI 问答已可用。

## 功能需求

- **FR-001**：本地 Neo4j 必须使用 `127.0.0.1:17687` 接收 Bolt 连接。
- **FR-002**：本地应用连接地址及服务公布的 Bolt 地址必须与 FR-001 一致；HTTP 管理端口保持 7474。
- **FR-003**：现有本机配置和本地配置生成默认值必须同步到新地址。
- **FR-004**：端口调整不得重置账号、迁移或清空业务数据，也不得调整 Docker 生产端口。
- **FR-005**：启动说明、Spec 和验证记录必须关联实际实现，并区分已提交修复与 #112 未提交的部署脚本同步。

## 成功标准

- **SC-001**：本机 Neo4j 启动后，使用现有凭据在新地址完成一次认证连接及一次只读查询。
- **SC-002**：本地配置生成、监听和公布地址全部使用 17687，管理入口仍可通过 7474 访问。
- **SC-003**：每项需求均可追踪到设计、任务和验证证据；不将其他服务或跨机器部署记为本次验收成果。
